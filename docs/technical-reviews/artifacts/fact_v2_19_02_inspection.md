## Original-source reading

- Mixtral of Experts, arXiv:2401.04088v1 (8 January 2024), downloaded anonymously from the original fixed-version PDF URL. Read §2.1 pp.2–3, its weighted expert output and sparse top-K softmax, and §3 “Size and Efficiency”, p.4. It explicitly distinguishes total from active parameters and says serving memory follows the 47B sparse parameter count. It explicitly mentions routing overhead and memory loads for more than one expert per device. §2.1 mentions specialized Megablocks kernels and Expert Parallelism. These support the lesson's cost caveats, not a performance prediction for this tiny Python model or FLOPs equivalence from the capacity proxy.
- Switch Transformers, JMLR 23(120), 2022, original `21-0998.pdf` final paper. Read §2.1 “Simplifying Sparse Routing”, pp.3–4; §2.2 “Efficient Sparse Routing”, pp.5–6; Eq.(3) capacity and Eq.(4)–(6) auxiliary load balance. The passage “A Differentiable Load Balancing Loss” and Eq.(4)–(6) are in **§2.2 p.6**, not §2.1. The frozen lesson's cited section number is therefore contradicted. The formula is alpha*N*sum f_i*P_i, with nondifferentiable top-1 assignment fraction f and differentiable mean full-router probability P. The original uses top-1 and capacity/drop behavior; capstone uses dropless top-2 and normalizes its assignment fraction over T*k. The lesson only attributes the encouragement of balance, not identity of implementations. Balance is not a specification of expert subject-matter roles.
- RFC 3629 (November 2003), §3 table: U+0800..U+FFFF use three UTF-8 octets and supplementary code points can use four. Read the original text. ByteTokenizer maps each UTF-8 octet to a token ID; the CPU examples give 中 and 文 three positions, 𠀀 four. The limit is 192 positions including protocol markers, not 192 Chinese characters.
- PyTorch original GitHub source at installed `torch.version.git_version` 5c4886908584029761b579af026dcfb627c84070, package 2.14.1+cpu. Read `module.py` lines 2650–2729: parameters delegates to named_parameters, default recursion and duplicate removal are explicit. Read `adam.py` defaults and lines 152–189: normal Adam allocates exp_avg and exp_avg_sq of the parameter's shape/dtype, plus scalar step; AMSGrad is off by default and would add a third parameter-shaped state. The exercise is explicitly a coarse FP32 estimate.

## Hand calculation checked by execution

For width64/hidden256 GELU FFN, one expert has 64*256 + 256 + 256*64 + 64 = 33,088 parameters including biases. Eight experts have 264,704. Two bias-free routers have 2*64*4=512. Other modules have 62,912: untied input/output tables 2*264*64=33,792; GQA attention 2*(64*64+64*32+64*32+64*64)=24,576; five RMS weight vectors 5*64=320; image and audio projection 48*64+64+16*64+64=4,224. Total=328,128. Removing two unused experts in each layer yields 328,128-2*2*33,088=195,776. It includes all shared tables; it is not actual FLOPs or table entries touched per token.

Dense64 removes routers and uses one expert-sized FFN per layer: 62,912+2*33,088=129,088. Dense80: untied tables42,240 + attention38,400 + RMS400 + projectors5,280 + two biased FFNs103,200 =189,520. Compared with195,776 the gap is6,256 (about3.20%); this is approximate capacity matching, and attention and modalities also change shape. It is not quality/FLOPs matching.

FP32 tensor elements are actually four bytes. Weight-only bytes=328,128*4=1,312,512; Dense64=516,352. Exercise=328,128*16=5,250,048 and Dense64=2,065,408. A zero-learning, zero-lr Adam initialization with explicit zero gradients verifies three additional 1,312,512-byte parameter-shaped tensors; 212 extra scalar-step bytes demonstrate why the coarse estimate is not total training storage. No trained weights changed.

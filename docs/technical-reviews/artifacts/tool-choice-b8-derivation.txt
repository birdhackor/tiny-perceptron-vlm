Scope: B.8 deterministic arithmetic and event definitions, not empirical model estimates.

1. Expected loss in the stipulated two-outcome example
Let I_bad = 1 for an incorrect final task answer and 0 otherwise; p=P(I_bad=0).
The direct route has loss 10*I_bad and the tool route has loss 10*I_bad + 0.02.
E[I_bad]=1-p, so E[direct_loss]=10*(1-p_direct) and
E[tool_loss]=10*(1-p_tool)+0.02. The additional cost is incurred for choosing
this route whether its answer is right or wrong. The two costs are expressed
in the same artificial loss-point units; no measured milliseconds or dollars
are substituted. Any common route cost may be omitted because it cancels.
These assumptions simplify real systems; varying error severity or variable
costs would require an appropriately conditioned/general expected-loss model.

2. Original hand calculation (decimal arithmetic)
p_direct=0.90 -> 1-p_direct=0.10; 0.10*10=1.00.
p_tool=0.99 -> 1-p_tool=0.01; 0.01*10+0.02=0.12.
0.12 < 1.00, therefore TOOL under the strict comparison in the source.
These are invented probabilities, not fractions measured in a model trial.

3. Exercise hand calculation
Change only p_direct to 0.999. 1-0.999=0.001; 0.001*10=0.010.
Tool loss remains 0.12. 0.010 < 0.12, therefore DIRECT.
As a formula check, TOOL wins exactly when C*(p_tool-p_direct)>extra_cost,
for C>0. Here p_direct < 0.99 - 0.02/10 = 0.988 selects TOOL.
At equality, source's '<' condition is false and it chooses DIRECT.
This threshold is derived for these assumed constants, not calibrated or
selected on any actual validation/test set.

4. Probability targets and chain rule
Transformer Sec.3.4 defines predicted next-token probabilities; Sec.3 defines
autoregressive generation. For a fixed complete token sequence, the model's
sequence probability is a product of conditional token probabilities:
P_model(y_1,...,y_m | x) = product_i P_model(y_i | x,y_<i).
A single conditional factor is not the whole product. Even that product is
probability assigned by a language model to a text sequence, not a calibrated
probability that a final arithmetic statement is true. Correctness additionally
requires an external semantic/task standard; multiple surface forms may be
correct. Guo Sec.2 Eq.1 calibrates a predicted class against that classification
task's true label distribution. It cannot transfer calibration of a TOOL label
or next-token label to the different event 'my direct arithmetic answer is true'.
B.8 therefore correctly calls for independent task-success measurements.

5. Whole-route success
Let S=appropriate tool chosen, A=valid/correct arguments, E=execution succeeds,
and F=final answer satisfies the original task. Whole-route success is
S intersect A intersect E intersect F. Its probability is at most P(E).
The general chain rule factors it as P(S)*P(A|S)*P(E|S,A)*P(F|S,A,E),
without assuming independence. A perfect arithmetic function conditional on
correct inputs does not prove any of S,A,F. Replayed formal CALC:multiply(9,9)
returned 81 but generated malformed final {"done":true,"answer":8}} and failed.
An injected well-formed final answer 8 was also rejected as task-incorrect by
the same current scoring function. Neither replay measures new model quality.

6. Validation average limitations
An observed k/n success fraction is a group estimate, not a guarantee for each
member or for the next question. For example, 9 successes out of 10 observed
questions is consistent with a particular difficult question failing. Guo
Sec.2 describes finite-sample calibration approximation and Sec.4 explicitly
assumes training/validation/test from the same distribution. Changed wording,
number ranges or tool availability require new applicability checks. Choosing
a rule after inspecting final-test errors uses the test data for selection;
scikit-learn Sec.3.1 says such leakage removes the stated generalization scope.

7. Float/display distinction
Exact decimal hand results are 1.00, 0.12, 0.010. Python binary floating point
produces small representation differences (saved in the audit JSON); absolute
error <1e-12 is suitable here. The expected printed strings match exactly.
Python round returns a rounded value; source uses it only in print expressions
and compares unrounded direct_loss and tool_loss. It does not mutate the model
or the original loss variables. No actual waiting time is measured by this code.

# 1.11 獨立算式核對（2026-10-05）

本節的參數與代價均是無物理單位的玩具數值；梯度的解讀是「代價單位／該參數單位」。本例沒有樣本平均、token 平均或資料集分母。

令 `L(w0,w1)=(w0-3)^2+c*w1^2`，其他座標固定：

- 第一格向前差商：`[L(w0+h,w1)-L(w0,w1)]/h = 2*(w0-3)+h`。
- 第二格向前差商：`[L(w0,w1+h)-L(w0,w1)]/h = c*(2*w1+h)`。
- `h→0` 後梯度是 `[2*(w0-3), 2*c*w1]`，依 `[w0,w1]` 的次序排列。

在 `[1,2]`、`c=0.5`：第一項 `(-2)^2=4`，第二項 `0.5*2^2=2`，總代價 `6`。梯度是 `[-4,2]`。只增第一格 `0.001`，代價為 `5.996001`；只減第二格 `0.001`，代價為 `5.9980005`，都低於 `6`。反方向則分別是 `6.004001`、`6.0020005`。這核對表中的局部方向，不能由此保證任意大步會下降。

中央差分逐格使用左右間距 `2*h=0.0002`。未選的座標必須保持不動，不能同時微動兩格後將總差商當作每格梯度。本次 binary64 計算的誤差分別為 `4.881428594671888e-12`、`2.2026824808563106e-13`，均小於絕對容忍差 `1e-8`。本多項式的中央差分在精確算術下正好等於其偏導數；剩下的微差來自浮點運算。

`c=2` 時兩項代價為 `4`、`8`，總代價 `12`；梯度為 `[-4,8]`。第二項的代價與第二格梯度都成為原來四倍，第一格不受 `c` 改變影響。

總代價不是梯度：`[1,2]` 與 `[1,-2]` 的代價都為 `6`，第二格梯度分別是 `2` 與 `-2`。因此單獨看到 `6` 不能確定每格方向。將 `[-4,2]` 直接當作新參數時，代價是 `(-4-3)^2+0.5*2^2=51`；原稿正確區分梯度與新參數。

autograd 本例從純量和的上游敏感度 `1` 分別往回算：第一項給 `[2*(1-3),0]=[-4,0]`，第二項給 `[0,0.5*2*2]=[0,2]`，兩項在同一葉張量 `w` 的對應位置累積為 `[-4,2]`。本次探針亦分別計算两條路，再核對相加後等於 `w.grad`。索引不會讓兩個參數混為同一更新量。

原碼的 `w` 與 `w.grad` 都是形狀 `[2]` 的 CPU float32 張量，三個代價各是形狀 `[]` 的純量。4、2、6、-4、2 等整數在這次 float32 運算可精確表示；探針以 `torch.equal` 核對精確值。原稿的 `torch.allclose` 仍是近似判準，其預設為 `abs(a_i-b_i) <= 1e-8 + 1e-5*abs(b_i)`；對參考第二格 `2` 的允許誤差為 `2.001e-5`，不能把它誤當成形狀斷言。

本節未呼叫 optimizer、未原地改 `w`，也沒有使用能改參數的 backward hook。`loss.backward()` 只填入本次梯度。中間 `first_cost`、`second_cost`、`loss` 的 `.grad` 是 `None`；另做有意義小變化，對前兩項呼叫 `retain_grad()` 才得到兩個純量上游梯度 `1`。這支持原稿對葉節點与中間結果的限定說法。

官方 PyTorch 原始文件／程式快照是 v2.11.0；實際執行環境是 PyTorch 2.14.1+cpu（git `5c4886908584029761b579af026dcfb627c84070`）與 Python 3.13.5。本人另親讀執行環境的 `Tensor.backward`，相關鏈式法則、純量省略 gradient、葉節點累積的契約一致。本報告不宣稱 v2.11.0 是安裝版本或官方最新版本。

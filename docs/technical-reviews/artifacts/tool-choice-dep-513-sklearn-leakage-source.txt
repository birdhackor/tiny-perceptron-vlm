169: 12.2. Data leakage#
170: Data leakage occurs when information that would not be available at prediction
171: time is used when building the model. This results in overly optimistic
172: performance estimates, for example from cross-validation, and thus poorer performance when the model is used
173: on actually novel data, for example during production.
174: A common cause is not keeping the test and train data subsets separate.
175: Test data should never be used to make choices about the model.
176: The general rule is to never call fit on the test data. While this
177: may sound obvious, this is easy to miss in some cases, for example when
178: applying certain pre-processing steps.
179: Although both train and test data subsets should receive the same
180: preprocessing transformation (as described in the previous section), it is
181: important that these transformations are only learnt from the training data.
182: For example, if you have a
183: normalization step where you divide by the average value, the average should
184: be the average of the train subset, not the average of all the data. If the
185: test subset is included in the average calculation, information from the test
186: subset is influencing the model.
187: 12.2.1. How to avoid data leakage#
188: Below are some tips on avoiding data leakage:
189: Always split the data into train and test subsets first, particularly
190: before any preprocessing steps.
191: Never include test data when using the fit and fit_transform
192: methods. Using all the data, e.g., fit(X), can result in overly optimistic
193: scores.
194: Conversely, the transform method should be used on both train and test
195: subsets as the same preprocessing should be applied to all the data.
196: This can be achieved by using fit_transform on the train subset and
197: transform on the test subset.
198: The scikit-learn pipeline is a great way to prevent data
199: leakage as it ensures that the appropriate method is performed on the
200: correct data subset. The pipeline is ideal for use in cross-validation
201: and hyper-parameter tuning functions.
202: An example of data leakage during preprocessing is detailed below.

541: When we pass an integer, the estimator will use the same RNG on each fold:
542: if the estimator performs well (or bad), as evaluated by CV, it might just be
543: because we got lucky (or unlucky) with that specific seed. Passing instances
544: leads to more robust CV results, and makes the comparison between various
545: algorithms fairer. It also helps limiting the temptation to treat the
546: estimator’s RNG as a hyper-parameter that can be tuned.
547: Whether we pass RandomState instances or integers to CV splitters has no
548: impact on robustness, as long as split is only called once. When split
549: is called multiple times, fold-to-fold comparison isn’t possible anymore. As
550: a result, passing integer to CV splitters is usually safer and covers most
551: use-cases.

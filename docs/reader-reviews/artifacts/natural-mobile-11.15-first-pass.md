我自己的理解：一整欄亮線的 32 個數字是 1，其餘是 0。每個受影響的 8×8 區域有 8 個 1、56 個 0，平均為 8÷64＝1÷8＝0.125。原圖是 32×32，縮圖是 4×4；四個縮圖格仍有 0.125，並非全部變成 0。達到 0.5 的數字變成 0 個，只表示此門檻下沒有半亮格，不能拿來宣稱 OCR 失敗。移動同一個 8 欄區域內的亮線仍會得到相同平均，因此輸出不足以唯一判斷原亮線在哪一欄；較大文字模型可以猜，不能保證找回確定位置。

本人執行從 11.15 原樣抽取的 Python 區塊，使用既有 `.venv/bin/python` 且 `CUDA_VISIBLE_DEVICES` 為空，exit 0。輸出原圖與縮圖尺寸 `[32, 32] [4, 4]`、最亮數字 `1.0 0.125`、至少半亮數字個數 `32 0`。原始區塊保存在 `natural-mobile-11.15-original.source.txt`，實際 stdout 與 run metadata 另外保存。

1. 放大生成回答的文字模型：增加能學習的參數與文字／推理容量；若收到的兩個縮圖輸入完全相同，就沒有足夠資料保證還原兩個不同筆畫位置。
2. 保留原圖細節：處理前處理造成的可見資訊損失；較高解析度或帶原位置的小窗，讓小筆畫有機會到達模型。細節到達不等於已會辨識，且較多視覺位置要付時間與記憶體成本。
3. 補中文字圖片及正確文字示範：教可見字形與應回答文字的對應，使模型有學中文讀字的監督。要另以保留的新中文字、字體或圖片條件評估，數字 OCR 不能充作已會中文的成績。

## 19.16 機率判斷器怎樣獨立回答三種問題？

本節教原版文字C的三型介面；[19.23](19.md#19.23)再教C-v2共享材料，[19.25](19.md#19.25)才是目前推薦的typed裝置C-v3。三者介面與權重不可互換。

機率判斷器的工作不是代替 Looped 解題器算完再包成JSON。它從狀態、當前問題與候選意義直接產生機率，讓另一個程式可以決定顯示服務、詢問資訊或分配預算。最小世界沿用卡片、地址與App客服材料；每種工作先有可人工核對的規則。

第一種是 **Choice**（[9.11](09.md#9.11)）：「需要哪類服務？」候選含卡片、地址、App及不適用。第二種是 **yes／no**：「對當前流程，必要資訊齊了嗎？」輸出yes機率，也就是[9.15](09.md#9.15)說的 Noul 型別。第三種是**有限規準評級**：例如0＝必要欄位都缺、1＝只滿足部分、2＝已全滿足，回傳各級機率。規準須按每題流程列出必要欄位，不能只看文字長短。

一個共用的候選評分器可服務三者：讀狀態與問題，再把每個候選意義送進同一網路得到分數。yes／no有兩個互斥候選；等級候選則把每級意義寫清楚。這是本課可實作的條件評分設計，不是宣稱官方 Jev 內部也使用同一網路。新問題、新詞義或任意級數都不自動受支援，應列明訓練與測試範圍。

本版機率判斷器有84,545個參數，從seed9041的隨機權重在L4完成800次更新，依決策資料選出第800步。三種問題各自在校準資料上用 CE 選校準溫度 T（[9.14](09.md#9.14)的溫度縮放），本次都選0.25。交付同時綁定權重、語義ID、規準與這三個溫度；換候選順序不應偷偷換候選意義。

主要測試題中，Choice為11,797/11,797、資訊充分10,890/10,890、規準10,890/10,890；倒序候選後語義選擇一致11,797/11,797。缺少所需服務候選時，以none為答案的子集是849/849。這些是[19.14](19.md#19.14)已交代有跨切分重複輸入句的有限測試題；倒序一致也部分來自每個候選獨立評分及語義ID平手規則，不單獨證明模型懂任務。

下面用隨機初值建立和成品同設定的候選評分器，核對其中「每個候選獨立評分」這一部分：同一組候選換兩種順序，各候選的機率是否相同；它沒有訓練過，四個機率都接近 0.25，不代表成品的判斷。

這次把一題的編碼與分數回填直接寫出來，範圍固定為 `choice` 問題及卡片、地址、App、不適用四個候選；不展開多題批次與訓練標籤。先用候選名 `card` 查出「查詢卡片申請進度」，再把狀態、問題與這段意義文字依序編碼。下面的 `meanings` 列出本題四種意義，`question` 是 `choice` 對應的完整問題。Tokenizer提供已固定的公開字元表，共144個編號：0為PAD（補齊）、1為CLS（彙整位置）、2為SEP（分隔），其餘字元依表中位置 `i+3` 編號；程式直接寫出逐字查表的動作，不呼叫它的 `encode`，也不從這題重新建立字表。

```python
import torch
from torch import nn

from tiny_perceptron.lesson_products.model import (
    Block,
    CandidateScorer,
    Config,
    Tokenizer,
    candidate_batch as library_candidate_batch,
    grouped_scores as library_grouped_scores,
)

torch.set_num_threads(1)
torch.manual_seed(0)
tokenizer = Tokenizer()  # 只取已固定的公開字元表；下面直接寫文字→ID。
character_ids = {character: i + 3 for i, character in enumerate(tokenizer.characters)}
model = CandidateScorer(Config(vocab_size=len(tokenizer), width=64, ff=128)).eval()
state = "卡片進度;申請編號=?"
question = "哪個任務適合這段材料？"
meanings = {
    "card": "查詢卡片申請進度",
    "address": "說明地址填寫規則",
    "app": "協助App重設密碼",
    "none": "以上皆不適合",
}
print("字表／全部參數", len(tokenizer), sum(p.numel() for p in model.parameters()))
print("部分字元ID", {c: character_ids[c] for c in ["卡", "片", "?"]})
for candidates in (["card", "address", "app", "none"], ["none", "app", "address", "card"]):
    # 只展開這一題、這四個候選；沒有訓練gold或多題批次。
    sequences = []
    start = len(sequences)
    for candidate in candidates:
        ids = [1]  # CLS：用來彙整整列內容的第一個位置。
        for i, part in enumerate([state, question, meanings[candidate]]):
            if i:
                ids.append(2)  # SEP：分隔state、問題及候選意義。
            for character in part:
                if character not in character_ids:
                    raise ValueError("超出公開有限字元表：" + repr(character))
                ids.append(character_ids[character])
        sequences.append(ids)
    slices = [(start, len(sequences))]  # 左含右不含的列範圍。
    max_candidates = len(candidates)  # 本例只有一題。
    lengths = [len(sequence) for sequence in sequences]
    length = max(lengths)
    if length > model.config.max_length:
        raise ValueError("超過max_length")
    tokens = torch.zeros((len(sequences), length), dtype=torch.long)  # PAD=0。
    for i, sequence in enumerate(sequences):
        tokens[i, : len(sequence)] = torch.tensor(sequence)

    with torch.no_grad():
        scores = model(tokens)  # 每個候選一分，形狀(4,)。
        grouped = scores.new_full((len(slices), max_candidates), float("-inf"))
        for i, (start, end) in enumerate(slices):
            grouped[i, : end - start] = scores[start:end]
        probabilities = grouped.softmax(-1)[0]  # 本例不套成品的校準溫度。
    print("候選", candidates, "有效長度", lengths)
    print("tokens／slices／max_candidates", tuple(tokens.shape), slices, max_candidates)
    print("列分數→題分數形狀", tuple(scores.shape), tuple(grouped.shape))
    print(dict(zip(candidates, [round(p, 4) for p in probabilities.tolist()])))

    # 函式庫只作同題核對，不替上面的必要運算補步驟。
    row = {"state": state, "question": "choice", "candidates": candidates}
    ref_tokens, ref_slices, ref_max, ref_labels = library_candidate_batch([row], tokenizer, model.config)
    with torch.no_grad():
        ref_grouped = library_grouped_scores(model(ref_tokens), ref_slices, ref_max)
    assert torch.equal(tokens, ref_tokens)
    assert slices == ref_slices and max_candidates == ref_max and ref_labels.numel() == 0
    assert torch.equal(grouped, ref_grouped)
    assert torch.equal(probabilities, ref_grouped.softmax(-1)[0])
print("兩種順序的編碼、切片、分數回填均與函式庫相同")
```

設定照成品寫成特徵寬度64、FFN中間寬度128，字表144，全部參數仍為84,545；`nn`與`Block`供下一段原始碼使用。第一種順序得到：

```text
字表／全部參數 144 84545
部分字元ID {'卡': 52, '片': 98, '?': 16}
候選 ['card', 'address', 'app', 'none'] 有效長度 [33, 33, 34, 31]
tokens／slices／max_candidates (4, 34) [(0, 4)] 4
列分數→題分數形狀 (4,) (1, 4)
{'card': 0.2519, 'address': 0.2484, 'app': 0.2524, 'none': 0.2472}
```

以card那列為例，編號前的排列是「CLS／卡片進度;申請編號=?／SEP／哪個任務適合這段材料？／SEP／查詢卡片申請進度」。CLS、兩個SEP也各占一個位置，共33個有效ID；最長的app列有34個，所以card列最後補一個PAD=0。`torch.zeros`先準備全為PAD的四列，再把每列有效ID放到開頭；後面的模型以 `tokens != 0` 排除這些補位。

`slices=[(0,4)]`記錄這一題使用第0至第3列，右端4不包含在內；`max_candidates=4`記錄本題的候選數。模型先給四列各一個分數，`scores[start:end]`取出這題的四分，再填進 `grouped[0,:4]`，成為一題×四候選的表，最後才沿候選方向softmax。一般多題批次用各題候選數的最大值作表寬，較短題目沒填到的格子留為負無窮，softmax後就是0；本例四格全部填滿。

最後的函式庫呼叫只作核對：`candidate_batch`的完整介面會檢查候選；Choice只能取公開表中的card、address、app、boxes、sum、none，至少兩個、不重複且保留none，另處理多題及可選的訓練標籤。本例固定合法四候選，沒有gold，所以標籤tensor為空。四個assert實際比較了編號表、切片、候選數及回填後的分數／機率。反向排列時，各列有效長度變成 `[31,34,33,33]`，機率印為 `{'none': 0.2472, 'app': 0.2524, 'address': 0.2484, 'card': 0.2519}`；每個值跟著自己的候選名搬動。本例使用隨機模型的原始分數，不套成品的校準溫度0.25。

```python
# 節錄自 tiny_perceptron/lesson_products/model.py：CandidateScorer
class CandidateScorer(nn.Module):
    def __init__(self, config):
        super().__init__()
        self.config = config
        self.embedding = nn.Embedding(config.vocab_size, config.width, padding_idx=0)
        self.position = nn.Embedding(config.max_length, config.width)
        self.blocks = nn.ModuleList(Block(config) for _ in range(config.c_layers))
        self.norm = nn.LayerNorm(config.width)
        self.score = nn.Linear(config.width, 1)

    def forward(self, tokens):
        """每列一個(state,question,candidate)，沒有候選清單的位置。"""
        if tokens.shape[1] > self.config.max_length:
            raise ValueError("輸入超過max_length")
        hidden = self.embedding(tokens) + self.position(torch.arange(tokens.shape[1], device=tokens.device))
        for block in self.blocks:
            hidden = block(hidden, tokens != 0)
        return self.score(self.norm(hidden[:, 0])).squeeze(-1)
```

`CandidateScorer` 用的是[19.15](19.md#19.15)已完整說明的 `lesson_products` 自己的 `Block`，但疊 `config.c_layers` 個（預設 2）各有參數的區塊，不循環。`forward` 收到的 `tokens` 每一列是一組「狀態、問題、一個候選」，說明字串寫的「沒有候選清單的位置」就是指這件事：各列在同一批裡互不干擾地通過同樣的區塊，最後由第一個位置的特徵經 `norm` 與 `score` 得到一個分數，`squeeze(-1)` 把形狀 `[列數, 1]` 變成每列一個數。一個候選的分數因此只由它自己那一列決定，換候選順序只是換列的順序；分數跟著候選走，softmax 後各候選的機率也一樣。

Choice 的**集中度**（concentration，[9.15](09.md#9.15)）只量候選之間的集中程度，不能當作答對機率。Noul式介面直接回yes機率即可；服務決策及輪數選擇留給外層的決策規則，與權重檔分開版本化。

驗收先要求 Choice 測試題正確率至少90%，並在同題重排候選後有至少99%的語義選擇一致率。後者單獨高也可能只是穩定選錯，因此必須同時看前者。資訊充分與有限等級各報正確率、CE及Brier；另外測正確候選缺席、同狀態換問題、無關欄位及新措辭，保存高信心錯誤例。

校準後的效果也要在換措辭的題目上重新檢查：主要測試題的 Choice CE 從約0.000550降到0.00000814；換措辭後，正確率卻只剩11,493/11,797，CE更從0.183惡化到0.698。資訊充分與規準在換措辭後也各為10,773/10,890。在原分布上選出的溫度，可能讓新措辭上的錯誤更有信心。

例如輸入「幫我預報明天天氣」，本世界的正確答案是不適用（none）；模型卻選兩盒追蹤（boxes），集中度約1。這個[保存的錯誤例](https://github.com/birdhackor/tiny-perceptron-vlm/blob/main/docs/lesson-products/results/observed-failure-examples-v1.json)（看 `examples` 的第一筆）直接說明：集中、高分與語義判斷正確是不同的事。主要測試題零錯誤，也沒有排除分布變化時的高信心錯誤。

若同一問題集合只有一個正確候選，評分與標籤就按該契約；若有多個同樣合理答案，須修改規準或評分方式，不能靠模型猜標註者喜好。這使成品的機率有可討論的對象，而不是只把自由文字壓成固定欄位。

本節仍記錄舊版C：每個候選重新讀完整state，候選意義從固定表取出，字元表及服務入口也有限。新版[19.23](19.md#19.23)會直接接受合法描述、先獨立編碼共同材料，並讓none讀清單的對稱彙整。這需要新結構、新資料與新訓練；本節的舊成績保留作基線，已看過的錯誤例也不再充當新版未見的最終測試。

練習先固定同一份材料：「案件編號42；規則：查進度需本人授權。」材料沒有記下案件42的授權狀態。本練習明定兩個需求與必要欄位，先自行判充分性，再對照：

| 問題 | 必要欄位 | 資訊充分的正解 |
| --- | --- | --- |
| 文件說查進度需要什麼條件？ | 規則文字 | yes：可以讀出需本人授權 |
| 案件42目前是否符合查進度的授權條件？ | 案件編號、該案件的授權狀態 | no：有編號，但授權狀態未知 |

兩題都看見編號，因此「有編號就yes」在第二題會錯；同狀態換問題才真正區分這個捷徑與按需求查欄位。再把材料補上「授權狀態：否」，第二題的資訊充分性應改成yes，因為已能判定不符合條件；資訊足夠不等於獲准執行。這是在手工建立評估標籤，沒有宣稱舊C已支援這個新欄位或已答對。

# 教材實作驗證

「能執行」和「能完成任務」是兩件不同的事。程式可以順利回答，卻讀錯招牌；模型也可能答對一題，只因記住題目。這頁說明本課如何檢查教材、檔案、訓練與模型能力，讓你知道每種證據回答的是哪個問題。

可以想成檢查一輛腳踏車：輪子裝得上、轉得動，還不等於騎士已能在路口正確轉彎。每一層都有自己的判尺，不用一個「全部成功」代替。

## 先分清要檢查什麼

| 問題 | 對應檢查 | 能支持什麼？ |
| --- | --- | --- |
| 網頁與Notebook是否同一份教材？ | 比較來源，核對目錄、圖解與程式格。 | 讀者操作的是配對內容。 |
| 短程式是否能執行？ | 每份Notebook在獨立CPU kernel執行，保留輸出。 | 該份程式在記錄的環境跑通。 |
| 某個公式或數值步驟是否正確？ | 小範例、單元測試與原始論文／官方文件核對。 | 被檢查的機制符合定義與數值預期。 |
| 是否真的更新了指定參數？ | 核對更新器範圍、梯度、步數與前後權重。 | 訓練按記錄的範圍執行。 |
| 取得的檔案是否一致？ | 核對固定版本、大小與SHA-256。 | 取得指定內容。 |
| 模型是否學會用途？ | 用未參與更新的題目，依事先約定的規則評分。 | 在那份資料與設定上的表現。 |

最後一列最接近你真正關心的能力。前五列很重要，但不能合在一起替代它。例如權重指紋相同，不表示回答正確；程式能吃圖片，也不表示回答真的隨圖片改變。

## 小實驗、正式訓練與成品各有自己的範圍

正文的短程式把一個機制縮到可以追蹤的大小，例如遮住未來、對齊答案位置或只更新LoRA分支。它們幫助理解原理，不直接代表自然圖片與一般中文的能力。[正式實驗入口](course-experiments/README.md)連到各項訓練資料、配置與實際報告。

[第19章v2](../course/chapters/19.md#19.12)已完成從隨機初始化的MoE與Dense訓練、公開推論輸出和各3,734題的固定最後測試。文字核心、視覺／語音入口與接頭都自行訓練；三類服飾與兩格位置、12字的指定連續1–4字區域、三種銀行客服語音主題及有限文字／工具任務各有分母。兩版都未通過全部原定能力判準。[完整結果](selftrained/results/v2-final-public-results.json)保留原判準及逐項成績：MoE完整工具往返0/276、語音回答42/90、語音後續對話26/60；圖片服飾辨識357/360與中文字辨讀（OCR）252/324也不能代替這三項能力。

[公開CPU示範](selftrained/v2-public-cpu-commands.md)使用挑選的validation成功題，完成8次對話呼叫（chat）與1次追加對話歷史（history append），支持匿名下載、載入及介面運作。它不改最後測試分數。[本機訓練入口檢查](selftrained/infrastructure/v2-local-stage/independent-review/review-final.md)用自己生成的CPU小資料與存檔，測試能否開始新的訓練段、從自己的最新存檔接續，以及資料或配套紀錄不符時是否拒絕。它沒有重新完成正式全量訓練。

第19章既有第一版B Looped解題器與C機率判斷服務另有[固定最後報告](lesson-products/results/final-report-v1.json)。B以170,003參數完成1,000次更新，C以84,545參數完成800次更新，均實際使用NVIDIA L4；兩個共享初始化的輪數對照各完成1,500次更新。B讀起始盒值與交換／設定事件，預測最後查詢的盒值；C讀狀態、問題與有限候選，輸出候選間的機率。這些是實際訓練，不是短程式前向或梯度示範。完整訓練checkpoint的下一步恢復檢查另核對權重、最佳化器與隨機狀態。

B五輪兩盒追蹤2928/2956通過核心門檻，三數加法2/42未過次要門檻；重複交換32/42與實體改名1486/2956也暴露限制。C的Choice是從卡片進度、地址、App、兩盒、加法或不適用中選服務：11797/11797通過核心門檻；把候選列表反向後，仍選同一意義的有11797/11797。換說法的Choice降至11493/11797。溫度校準只調機率分配的尖鈍；本課用正解獲配機率算出的交叉熵代價衡量它，越低越好，這份換說法材料校準後的代價反而變差。

資料按原始情境家族切分，同一情境衍生題都放同一組；但不同情境刪掉申請編號後，仍可能都變成「卡片進度;申請編號=?」。C有5,453種相同文字／問題／候選意義組合出現在多組，合計影響215,427筆資料列。因此家族留出不能代替完全未見文字的證明。

第一版B/C把驗證題分兩部分：calibration用來選C各問題類型的溫度調整係數，policy用來選模型存檔及Auto給B幾輪的規則；Auto是依題目自動分配計算預算的入口。[設定凍結檔](lesson-products/results/settings-freeze-v1.json)已在第一次最後測試前提交。[最後評分紀錄](lesson-products/results/final-report-v1.json)記下這份凍結檔的SHA-256；[公開套件](lesson-products/results/publication-package-v1.json)裡權重與設定檔的SHA-256也和凍結檔所記相同，所以評分與公開的都是凍結時那一份。兩位獨立審核者從保存的逐題原始分數重算B／機制／Auto及C成績（紀錄見[B／機制／Auto](lesson-products/reviews/engineering-final-b-mechanisms-original.json)與[C](lesson-products/reviews/engineering-final-c-original.json)），沒有把重新整理統計當成新一輪模型測試。固定下載與CPU操作見[產品指引](lesson-products/README.md)；最後考卷與有限語法都不代表開放式中文服務能力。

已發布的[舊合成示範](course-experiments/README.md)只涵蓋簡單圖形、純音、固定句型與受限工具，其歷史成績不能代替v2驗收。[第20章](../course/chapters/20.md)是成熟模型的延伸路線，使用已有的圖文底座與語音辨識器，分別檢查自然照片、中文讀字、文字聊天及語音聊天。兩條路的題目、權重來源與規模不同，分數不能直接當成同一場比賽。

每份能力結果都要一起讀資料範圍、分母、生成設定與判分方式。同一張圖的多個問答彼此相關，四個錄音問題也不能代表所有一般人的說話情境。第20章的[能力卡](../course/chapters/20.md#20.13)把這些限制放在得分旁邊。

## 驗證選版，最後測試驗收

訓練題用來更新模型；驗證題用來比較配方與候選；最後測試留到配置已選定後才使用。這像練習考和正式考：看過正式考的錯題再改讀書方法，下一次就需要另一份尚未看過的正式考卷。

v2以28,876題訓練，2,435題validation選定候選與生成設定，再凍結兩版公開權重各做一次3,734題final test，沒有用test再選版或訓練。選定權重的步數與完成步數不同：MoE最後段完成4,000步、選第1,000步；Dense最後段完成10,000步、選第1,000步。`best.pt`挑固定配方下驗證平均代價最低的存檔。語言部分使用teacher forcing：每一步先給正確前文，再看模型預測下一字的代價；配方也納入感知辨識與MoE專家分工的輔助代價。自行生成時，下一步會接著模型自己剛產生的字，錯誤可能累積；所以這項選版分數不代表完整生成能力達標。完整選版與完整性證據見[結果索引](selftrained/results/v2-final-public-results-integrity-review.json)。

[20.8](../course/chapters/20.md#20.8)提供具體對照：LoRA候選改善部分照片題，卻未保住聊天與完整結束要求，因此沒有成為交付配置。這個例子教的是如何接受或拒絕候選；保存檢查點與訓練代價下降，都不能跳過用途驗收。

語音再拆兩站核對：先看聽寫文字，再看助理回答。把正確逐字稿直接交給同一助理，可以幫助區分聽錯與回錯，方法見[20.12](../course/chapters/20.md#20.12)。

## 教材審閱與閱讀時間怎麼看？

教材依序做三輪獨立審閱：先檢查易讀易理解程度，包括背景、術語、例子、程式解釋與練習；再由不同審閱者核對正確性、原始文件、實際數值與程式；最後檢查連貫性，確認前後節接得上。理解必要的程式碼與關鍵輸出直接內建正文，不能以打開Colab或外部helper補缺。修改正文、圖解或回填結果後，完整受影響閱讀單位需要複查，不能只替換報告指紋。

這些是AI審閱，不是實測真人學生的學習成效。檢查器能核對版本、證據與報告完整性，不能自動證明審閱者已理解內容。

每頁的閱讀時間也是AI估計，對象是數學基礎良好的高中生，或有基本數學能力但不夠熟的大學生。它包含正文、圖解、範例程式、已展示輸出與短暫思考；不含安裝、下載、親手操作、等待訓練或額外補讀前置。章導讀只計自己的前言，同一頁不重複加到總量。程式執行耗時與閱讀時間，是兩種不同的量。

## Modal GPU 與 HF checkpoint 實測

雲端訓練還要核對另一層：GPU是否真的執行更新，中途存檔是否能重新取得，以及續訓是否接上原狀態。早期連線實測使用31,584參數的小模型，完成80步更新，從私有Hugging Face備份重新取回第40步存檔，再接到第80步；該次對照與不中斷路線的最大權重差為0，見[原始結果](gpu-smoke-result.json)。

這項檢查支持那次小模型的更新、傳輸與接續，不提供自然圖片、語音或大模型品質的證明。第20章的訓練與選版使用自己的[完整操作指引](natural-assistant/v4/TRAINING.md)和[驗證決定](natural-assistant/v4/selection.json)，各自核對資料與設定。

## 在自己的版本重跑

先按[W.1](../course/first-steps.md#W.1)準備專案與Notebook環境，啟用`.venv`後，在專案根目錄執行：

```bash
python scripts/build_course.py --check
python scripts/check_course_reviews.py
python scripts/check_technical_reviews.py
python docs/review-tools/check_review_round.py
python -m ipykernel install --sys-prefix --name tiny-perceptron --display-name "Tiny Perceptron"
python scripts/check_notebooks.py --mode kernel --workers 1
pytest -ra
```

前四行核對教材與審閱資料；接著註冊kernel，讓每份Notebook由獨立執行環境開始；最後的單元測試檢查程式機制。Notebook執行副本與當次核對寫入`outputs/notebooks/`，它們是工作產物，不是模型能力分數。

每一行結束時的exit code都是0才算通過。exit code（結束碼）是每條命令結束時交回終端機的數字：0表示成功，不是0就是沒有通過。要看剛結束那一條的值，在輸入下一條命令之前執行：macOS或Linux用`echo $?`，Windows PowerShell用`$LASTEXITCODE`。`check_notebooks.py`最後印出一段JSON：`failed`是0表示每份Notebook都從頭跑完；有失敗時`failures`列出哪一份、錯在哪裡，同一份結果也寫進`outputs/notebooks/validation-kernel.json`。`pytest -ra`的最後一行列出通過、失敗與跳過的數目，`-ra`會把失敗與跳過的原因列在摘要裡。

如果改了教材，舊報告或舊輸出可能被拒絕；應重讀、重查受影響內容，再重新執行改過的Notebook。若另做模型訓練，則按對應訓練指引保存配置與留出題結果。網站建置與連結核對接著見[教材發布](publishing.md)。發布前要先把這次的修改存成Git提交：`git status`列出改過的檔，`git add <檔案>`選定要提交的檔，`git commit -m "<這次改了什麼>"`建立提交。若Git回報`Author identity unknown`，先用`git config --global user.name "<名字>"`與`git config --global user.email "<信箱>"`設定作者資料，再執行一次`git commit`。本機CPU執行也不等於Colab雲端或所有學生設備已經驗證。

## 19.24 新版整合如何分清路由錯誤與解題錯誤？

使用者填入三個數字，希望解題器作答。C可能判錯任務；即使選對B，輸入也可能超過B的值域；即使輸入合法，B仍可能算錯。要改進這個助理，必須保留每一步，才知道下一輪應該改哪個零件。

[19.17](19.md#19.17)的Auto已經示範選檔。本版讓新C的路由題根據公開request，在A／B／C／none選一類，再檢查該後端的輸入契約。路由不另外套核心Choice的τ：那個τ是在另一組Choice／資訊問題上選出的服務接受策略，不能直接當路由信心的保證。進到C服務後，Choice才照固定T／τ及同需求的資訊判斷決定接受或轉交。B保留原來的Looped權重、文法和depth policy；A保留舊文字入口並增加[19.21](19.md#19.21)的影音分支。

先把B的入口約定寫出來。下面的`numbers`是使用者提交的公開欄位；適配器只檢查三個0到6的整數，組成B原本接受的文字，不計算答案。`type(x) is int`也排除Python會當作整數子類別的布林值。

```python
def adapt_sum(numbers):
    if not isinstance(numbers, list) or len(numbers) != 3:
        raise ValueError("需要三個整數")
    if any(type(x) is not int or not 0 <= x <= 6 for x in numbers):
        raise ValueError("B的三數入口只接受0到6")
    x, y, z = numbers
    return f"三數加法;x={x};y={y};z={z}"


def select_and_dispatch(judgment, payload, dispatch, manual=None):
    # judgment是公開路由預測；此例人工填入，沒有載入已訓練C。
    route = manual if manual is not None else judgment["answer"]
    try:
        return {"route": route, "result": dispatch(route, payload), "contract_error": False}
    except (KeyError, TypeError, ValueError) as error:
        # 保留原選路；契約失敗不能偷看gold，改派另一個後端。
        return {"route": route, "result": None, "contract_error": True, "error_type": type(error).__name__}


def demo_dispatch(route, payload):
    if route == "none":
        return {"status": "unsupported"}
    if route != "B":
        raise ValueError("這個小例只展示B適配；A/C另用自己的公開payload")
    text = adapt_sum(payload["numbers"])
    # 固定舊B此次的sum depth policy是1；這裡只回傳計畫，沒有讓B算答案。
    return {"backend_input": text, "loops": 1}


payload = {"numbers": [1, 2, 3]}
c_fixture = {"answer": "B", "p_max": 0.96}
print(select_and_dispatch(c_fixture, payload, demo_dispatch))
payload["numbers"] = [1, 2, 7]
print(select_and_dispatch(c_fixture, payload, demo_dispatch, manual="B"))
```

第一行的route是B，result含`三數加法;x=1;y=2;z=3`與一輪，`contract_error=False`；第二行仍記route=B，但result為None、契約失敗為True。手動指定優先於C選路，仍要通過輸入檢查。`0.96`是沒有用來設門檻的人工機率，不是新C成績；程式也沒有讓B算答案。正式入口從舊B已釘manifest讀depth=1，再檢查tokenizer與長度；不能把加深輪數混進新版改善。C能讀UTF-8新說法，不會擴大B的值域。

C選路時若只取得文字及「是否附有影片／聲音」欄位，就只能宣稱根據這些資訊選入口；影片裡的圓或方，仍由A的影音分支判斷。A的`circle/square/unknown`是真正交給[19.22](19.md#19.22)聲音模組的語義結果，舊文字模型若將它寫成一句自然的回答，不可改掉驗收與發聲使用的原預測。

接著分開測兩條路：**gold路由**使用資料事先規定的入口，檢查適配器與後端；**真C路由**使用C的預測，檢查整套系統。兩者用同一組100個預先留出的整合家族，這組另於C核心60家族之外保存，不能用重排或換句話把60湊成100。下面先用四筆人工紀錄拆開計算方式，再對照真實結果。

```python
# 每列是同一家族的兩次測試；數值為手工示意。
rows = [
    {"gold_backend_ok": True, "route_ok": True, "actual_backend_ok": True},
    {"gold_backend_ok": True, "route_ok": False, "actual_backend_ok": True},
    {"gold_backend_ok": False, "route_ok": True, "actual_backend_ok": False},
    {"gold_backend_ok": True, "route_ok": False, "actual_backend_ok": False},
]
gold_ok = sum(row["gold_backend_ok"] for row in rows)
route_ok = sum(row["route_ok"] for row in rows)
whole_ok = sum(row["route_ok"] and row["actual_backend_ok"] for row in rows)
print("指定正確入口：", gold_ok, "/", len(rows))
print("C選對入口：", route_ok, "/", len(rows))
print("真路由整條成功：", whole_ok, "/", len(rows))
```

輸出依序是`3/4`、`2/4`、`1/4`。第二筆雖然錯入口的後端正常結束，仍未完成原任務；第三筆選路正確，後端失敗；第四筆則錯路而且後端也失敗，先記下選路錯誤，才能避免把它全歸給解題器。真測試需保留原輸入、C分數／資訊判斷、固定門檻、選路、適配結果、A或B輸出及聲音分析。轉交、拒答與解析失敗都留在原分母。

升版時，還要把新wrapper與固定舊版本並排跑保留能力面板，逐任務列正確數、分母與退步。B的舊三數世界只有84個獨立家族，換措辭不會變成100個新家族；該面板只能照實報歷史回歸。新版分開保存推論權重、設定／tokenizer、完整optimizer/RNG狀態和資料生成版本，下載後核對指紋；各材料的角色接續[19.19](19.md#19.19)。只有通過能力與發布檢查的候選才成為預設，已見失敗與舊下載版本仍保留。

各列退步都是0個百分點，通過「不得退步超過5個百分點」的包裝回歸條件；舊工具任務的失敗也原樣保留。另24筆人工提供反事實工具結果的診斷，回答24／24跟隨提供值，例如真正運算應為18卻提供19，模型回答19。這沒有執行計算器，不能列為24次真工具往返成功。

B固定沿用原權重及sum的一輪策略，在0–6三數的有限母體84個組合家族上，每族只測事前指定、由小到大排序的代表（允許相等，例如`[0,1,1]`），該代表答對就計此面板的一次成功；舊入口與包裝入口同為60／84，不表示這60族內的每個排列都答對。另343種有序輸入逐筆計分，答對240筆，同一組數的排列共用家族。這是保留能力與排列診斷，沒有新訓練，也不能拿來替換原來不同切分、輪數下的歷史成績。

本輪Auto的逐列紀錄保留路由分數、選路、逐列正確旗標、A的工具trace與影音分析。B的Auto列只存對錯，未存答案；C存三型代表答案與接受狀態，未存各服務分數及對應Choice的資訊充分性預測，適配中間結果也未保存。因此89／66／55可以從逐列旗標重算，B／C的每一步輸出則無法由這份Auto紀錄重建。前面的逐步紀錄清單仍是完整診斷應保存的內容。

## 19.7 計算器算對，為什麼助理還可能答錯？

請助理「用計算器算出26×16。」公開 MoE 權重在 CPU 上先生成了乘法請求，程式真正算出416，同一模型讀回結果後再生成「結果是416。」這題需要三個動作連續完成：提出正確請求、執行工具、根據返回結果作答。

![實際公開 CPU 工具例：同一模型第一次生成26乘16的 JSON，計算器真執行返回416，再由同一模型第二次生成「結果是416。」](../figures/p6-19-modal-tool.svg)

第一份輸出是 JSON：以固定欄位記錄工具名、運算與兩個整數，讓程式可以明確讀取。這個計算器只支援0–99非負整數的加、減、乘。system 訊息說明一般格式與範圍，模型依 system 的工具條件與學過的示範，從這題選出 `multiply`、`26`、`16`；程式沒有先從問題抽出正確算式，替模型補一份呼叫。選擇工具是學習條件與作答規則的結果，不能解讀成模型已能可靠估計自己的數學信心。

| 往返位置 | 這次留下的實際內容 |
| --- | --- |
| 第一次模型生成 | `{"tool":"calculator","operation":"multiply","a":26,"b":16}` |
| 程式執行後的返回值 | `{"tool":"calculator","ok":true,"result":416}` |
| 回填到歷史 | 一則 assistant 呼叫，接一則 tool 結果訊息 |
| 同一模型第二次生成 | `結果是416。` |

執行器先檢查欄位、運算種類和整數範圍，再進行乘法；它不把模型文字交給 Python 的 `eval`。合法也不一定正確：若模型把26抄成25，請求仍可能合法，工具也會正確計算25×16，整個任務卻已偏離原題。因此「可執行」與「參數符合問題」必須分開判定。

下面只在 CPU 上重做解析與執行。`raw` 是我們手工提供的字串，程式沒有呼叫神經模型。

```python
from tiny_perceptron.selftrained.tools import parse_tool_call, execute_tool_call

raw = '{"tool":"calculator","operation":"multiply","a":26,"b":16}'
call = parse_tool_call(raw)
print("合法請求", call.to_dict())
print("真執行結果", execute_tool_call(call))
```

第二行輸出字典中的 `result` 為416。它證明這份請求能被解析並真正執行，沒有證明模型會生成它，也還沒有第二次模型回答。上方公開紀錄則保存了兩次真正生成，兩次都正常產生 EOS；第二次的輸入包含第一次的原始請求與真 tool 訊息，所以416是模型讀回後生成的答案。

工具往返要同時查：是否需要工具、是否選對工具與參數、是否真正執行、是否根據結果回答並正常結束。工具未開或缺參數的題目，要學會說明條件或詢問。另可在測試回放中替換返回值，查回答是否跟著變；這檢查讀回依賴，正常成功率仍應使用真正計算器結果。

這個26×16是挑選出的已知驗證成功例。一題真往返證明流程能運作，不能證明未見算式與問法穩定；本成品的最後工具題未達驗收門檻，完整分母與失敗位置留在[19.12](19.md#19.12)。這也回答了本節的問題：計算器只保證按收到的參數計算，參數選擇與最後文字都仍由模型負責。

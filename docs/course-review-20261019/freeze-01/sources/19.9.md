## 19.9 接上較快的做法，先檢查什麼？

助理每生成一個新字，都需要知道前文。若每次把整段對話重新算一遍，會重複處理已讀過的位置；KV cache 保存各層已算好的 Key、Value，讓下一步沿用它們。但省下重算以前，必須確認前文、位置與可讀範圍仍相同，否則兩條路可能已在回答不同問題。

本章實際交付的文字核心採用下列設定，表中每列都連到教過它的小節。這些做法各自改變一部分計算，不能合成一句「最佳化後品質與速度都更好」。

| 實際選用的做法 | 在這份文字核心中做什麼 |
| --- | --- |
| [RoPE](14.md#14.1) | 旋轉 Query、Key 的特徵，讓注意力使用位置資訊。 |
| [RMSNorm](14.md#14.2) | 按特徵的均方根調整尺度，再使用可學的縮放係數。 |
| [GQA](16.md#16.4) | 4 個 Query 頭共用 2 組 Key、Value，減少這部分的權重與快取。 |
| [權重共享](14.md#14.6)（weight tying） | 查字的 embedding 表與產生下一字分數的輸出層共用同一張權重表。 |
| [SDPA](16.md#16.8) | 用 PyTorch 的縮放點積注意力介面計算注意力。 |
| [top-2 MoE](15.md#15.4) | 每層有 4 個 expert，每個非填充位置的 token 選其中 2 個 FFN。 |

**SDPA 是介面，FlashAttention 是可能的底層實作**；裝置、數值格式與形狀都會影響選擇。本成品的設定記錄支持「使用 SDPA」，沒有支持「已選到 FlashAttention 這種 kernel（計算程式）」。同樣，Python 逐 expert 分派也不等於專用的稀疏運算 kernel。實際設定可查[最終模型記錄](../../docs/selftrained/results/v2-final-public-results.json)（看 `architectures.moe.capacity.config`），運算路徑可查[模型程式](../../tiny_perceptron/selftrained/model.py)。

先用同一套實作的**局部微型示範**核對快取：模型縮成特徵寬度 16、1 層，仍用隨機權重；5 個人工 ID 只是機制輸入，不是一道已學會的問答。一路一次讀完 5 個 token 位置；另一路先讀前 3 個位置、存下快取，再接後 2 個位置。最後比較兩路在最後一個位置的 32 項候選分數。

```python
import torch
from tiny_perceptron.selftrained.model import LimitedAssistant, SelftrainedConfig

torch.manual_seed(42)
config = SelftrainedConfig(vocab_size=32, width=16, layers=1, heads=2, kv_heads=1, ffn_hidden=32, top_k=2)
core = LimitedAssistant(config).eval()
ids = torch.tensor([[1, 11, 12, 13, 14]])
split = 3
with torch.no_grad():
    full = core(ids)["logits"][:, -1]
    cache = core(ids[:, :split])["cache"]
    cached = core(ids[:, split:], cache=cache)["logits"][:, -1]
print("最大分數差", (full - cached).abs().max().item())
print("同一計算", torch.allclose(full, cached, atol=1e-4, rtol=1e-4))
```

第二行應是True：程式以絕對與相對容差各 `1e-4` 比較，支持本例的兩路計算接近。第一行的最大差可隨浮點運算環境略變。兩路都使用 `eval()` 評估模式；本例模型沒有會隨訓練／評估模式改變計算的層，因此切換模式不改變本例輸出。`no_grad()` 則讓這次計算不建立求梯度的運算圖。程式沒有更新權重，也沒有量速度。

公開成品的生成預設已使用 KV cache。圖片與聲音在首次計算時編成特徵，放進完整前文；後續生成沿用快取，不重新編碼素材。另一項常見做法是[sequence packing](16.md#16.5)：把短紀錄裝到同一序列，再用遮罩隔開。這份正式訓練仍是一筆紀錄佔一列，較短列補 PAD，沒有採用 packing；[16.5](16.md#16.5)的局部示範不能當成它已套用的證據。

[16.14的推測解碼](16.md#16.14)則先提出草稿，再由目標模型核對。本成品仍逐 token 生成，沒有這條草稿驗證路徑；是否採用MTP訓練與是否啟用推測解碼，應各自記錄。增加候選、測得分數接近，都不能替代真正的接受規則與速度量測。

練習只把 `split = 3` 改成 2，先預測兩路仍讀相同5個位置，最後分數應接近，再執行核對。若要宣稱某條路更快，下一步才是在同一硬體、同一權重與生成條件下量時間和記憶體；快取的一致性與模型的回答品質要分開評估。

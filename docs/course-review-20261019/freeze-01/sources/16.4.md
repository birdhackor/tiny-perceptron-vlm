## 16.4 KV cache 怎麼縮小？

如果每個注意力頭都保存一份Key、Value，長對話會讓快取占用持續增加。可以保留多個Query頭，讓幾個Query頭共用同一組K、V嗎？一個[注意力頭](03.md#3.7)用一小組特徵做比對；[KV快取](16.md#16.3)則按每層、每頭、每個過去位置保存K、V。現在固定四個Query頭，只改保存的KV組數。多個Query頭共用較少的KV頭，叫Grouped-Query Attention（GQA，分組查詢注意力）。

例如特徵寬度16，Query有四頭，每頭四項特徵。FP32是32位元浮點數，每個數占4 bytes。若KV也有四頭，三個位置、一段輸入，用FP32保存K和V的數字需 `2×4×3×4×4=384` bytes，五個因數依序是2（K與V各一份）、4（KV頭數）、3（位置數）、4（每頭特徵數）與4（每個FP32數字的bytes）。若四個Query頭改共用一個KV頭，只有KV頭數由4變1，快取變成 `2×1×3×4×4=96` bytes。Query仍然各自計算，並不是把四個頭全部合成同一個查詢。

下圖上半每個Query頭讀自己的KV頭，下半四個Query頭都讀同一組KV。連線表示讀取關係，每組仍保存三個位置；96 bytes的條件與上述相同。

![四個Query頭保留，KV快取由四組減為一組](../figures/rewrite-16-query-kv-sharing.svg)

```python
import torch
from tiny_perceptron.model import TinyLM, ModelConfig

ids = torch.tensor([[1, 2, 3]])
with torch.no_grad():
    for kv_heads in (4, 1):
        model = TinyLM(ModelConfig(width=16, heads=4, kv_heads=kv_heads)).eval()
        cache = model(ids)["cache"]
        size = sum(t.numel() * t.element_size() for pair in cache for t in pair)
        print("KV頭數", kv_heads, "K形狀", tuple(cache[0][0].shape), "bytes", size)
```

此例只有一層。`cache`中的每個pair是一層的K、V。`for pair in cache for t in pair`是兩層迴圈：先逐層取出一對K、V，再逐一取出其中的tensor。`t.numel()`數出tensor的元素個數，`t.element_size()`給每元素占用的bytes，相乘就是該tensor的數字儲存量，`sum`再把各層的K、V加總。K形狀分別是 `(1,4,3,4)`與 `(1,1,3,4)`，bytes為384與96。

共用是怎麼做到又不多存的？`CausalAttention`的K、V投影只輸出`kv_heads`份特徵（`nn.Linear(width, kv_heads * self.head_dim, bias=False)`）。`forward`先寫`new_cache = (k, v)`，把只有KV頭份數的K、V存進cache，接著才用`k.repeat_interleave(repeat, dim=1)`把每個KV頭複製給共用它的Query頭，V也一樣；`repeat = self.heads // self.kv_heads`是每個KV頭要服務幾個Query頭，本例4÷1＝4。cache只存KV頭的份數，比對前才臨時複製，不先複製到每個Query頭再存；若把複製後的四份存進cache，儲存收益就會消失。

一般分組設定要求Query頭數能被KV頭數整除，例如四個Query、兩個KV，每組有兩個Query；不能整除時，`CausalAttention`會直接報錯。全部Query共用一個KV的情況也常稱Multi-Query Attention（MQA，多查詢注意力）。投影權重的形狀與共享方式會改變，不能隨意把訓練好的四頭KV重排成一頭，就宣稱原模型功能保持不變。

快取縮四倍也不代表整個模型記憶體縮四倍：參數、其他中間特徵仍然存在。它不保證實際耗時或答案品質改善，需要在相容架構上訓練、核對快取路徑與量測。此程式只是同一輸入的結構與儲存比較，兩個模型的參數各自初始化，沒有做品質競賽。

練習把 `ids = torch.tensor([[1, 2, 3]])` 改成六個ID，例如 `[[1, 2, 3, 4, 5, 6]]`。先預測K形狀的位置軸由3變6、bytes變成768與192，比例仍四倍，再執行核對。你應能分辨「前文變長」與「KV頭數減少」分別改了K形狀的哪一軸。

正式模型特徵寬度64、兩層、四個Query頭，每頭16項特徵。先把25個位置的提示一次讀入，這個階段叫[prefill](16.md#16.2)；產生的FP32快取，四個KV頭實測25,600 bytes，一個KV頭為6,400 bytes，正好四分之一。照上面的算法是 `2×2×4×25×16×4=25,600`，第二個2是層數。後者是MQA端點，實驗紀錄沿用`gqa`作組別名；沒有另外訓練兩個KV頭的中間設定。

兩個模型都以[T.4](../training.md#T.4)的單頭SFT模型為底座（當作起點的已訓練模型）；SFT是監督式微調，用示範問題與正確回答繼續訓練模型。做法是把底座裡名稱相同、形狀也相同的參數表直接複製成新模型的初值，其餘的表用固定亂數種子重新初始化。四KV版本共29張表：embedding表、位置表、兩層各自的正規化、Q／K／V／輸出投影與FFN，以及最後的正規化與輸出層。它們的形狀都和底座相同，所以全部複製。一KV版本的K、V投影只輸出一個KV頭的16項特徵，每層的K、V投影各從64×64變成16×64，兩層共4張表無法複製，改為重新初始化，其餘25張照樣複製；總參數因此少了 `4×(64×64−16×64)=12,288` 個。即使四KV版本照抄了全部數字，同一張64×64的Q投影現在被切成四個頭、每頭16項特徵分別比對，計算方式已經和單頭不同。所以兩個模型都再用同一份訓練資料續訓100次，才做下面的品質比較。實驗紀錄`results.models.mha`與`results.models.gqa`底下的`copied_initial_tables`欄逐一列出複製了哪些表。

這份品質比較使用[7.13保存的屬性問答基準](07.md#7.13)：根據短文字中的顏色、形狀與音高標記（high／low）作答，與[16.2](16.md#16.2)只用來計時的英文開頭不同。

下面的代價把模型給每個正確答案ID的機率p換成 `-log(p)`，再沿有效目標取平均；機率越高，代價越低，計算方法可回顧[機率與猜錯代價](../first-steps.md#W.4)。EOS（結束標記）表示回答結束。有效目標是計入代價的位置：本表只計助手回答與EOS，不把問題或補齊的PAD算入。例如正確回答 `[7,8,EOS]`有三個有效目標，若三個正確ID各得到機率0.5，單項代價都約0.6931，三項相加除以3仍為0.6931。這個平均衡量各個答案位置的預測；完整答案匹配則要求整段生成ID都正確。

[GQA原論文第2.1–2.2節](https://arxiv.org/pdf/2305.13245v3)把已訓練模型的多組KV投影取平均、合併成較少組後再訓練，我們沒有重現這個轉換配方，也沒有證明原模型功能原封不動。快取確實省bytes；短提示總生成中位數由四KV快取的27.915毫秒到一KV的27.105毫秒，是這個小形狀的一次觀察，不能推成長對話或所有後端的普遍加速。

PyTorch提供SDPA（Scaled Dot-Product Attention，縮放點積注意力）函式介面，負責以Q、K比對、轉成注意力權重，再取回V。後端是執行這套計算的不同實作選項；例如math用一般張量運算組合，其他選項可用專門的GPU運算。支援範圍也要帶版本：[2.14的SDPA文件GQA段落](https://docs.pytorch.org/docs/2.14/generated/torch.nn.functional.scaled_dot_product_attention.html)列出Flash、cuDNN、math及NVIDIA CUDA memory-efficient這些實作選項，但仍有頭數整除與輸入限制。本組GQA訓練與快取都走手寫路線（`backend="manual"`），[16.8](16.md#16.8)的SDPA核對只測四KV的MHA，沒有驗證上述所有GQA後端都可用。

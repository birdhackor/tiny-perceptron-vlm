## 17.10 檔案變小，為什麼運算不一定更快？

一層64個輸入、32個輸出，有2048個權重和32個偏移。FP32數值共`2048×4＋32×4＝8320`byte。4-bit權重打包成1024byte，32個刻度128byte，偏移128byte，合計1280byte。

數值儲存減少了，但[17.7](17.md#17.7)的`forward`每次都先用`q * self.scale`重建8192byte的浮點權重，再做浮點乘法。拆碼與還原是額外的工作；來源是低位元，不會讓普通乘法自動變成低位元計算。

```python
import torch
from torch import nn
from tiny_perceptron.quantization import QuantizedLinear

layer = nn.Linear(64, 32)
compressed = QuantizedLinear(layer, bits=4)
x = torch.ones(2, 64)
float_bytes = sum(p.numel() * p.element_size() for p in layer.parameters())
print("原層數字bytes", float_bytes)
print("壓縮buffer bytes", compressed.storage_bytes())
print("碼bytes", compressed.values.numel() * compressed.values.element_size())
print("運算結果", tuple(compressed(x).shape), compressed(x).dtype)
```

`sum(… for p in layer.parameters())`對層的每個參數（權重與偏移）各算一次bytes再加總，和`storage_bytes`對buffer的寫法相同。前三行是8320、1280、1024：第一份含原權重與偏移，第二份含碼、刻度與偏移，第三份只有碼。輸出形狀`(2,32)`、型別FP32，表示兩筆輸入各有32個輸出特徵。這是儲存與運算介面的核對，沒有計時。

**kernel（計算程式）**是實際執行底層乘加與資料讀取的程式。專用的低位元kernel可以邊讀小塊權重邊還原，或使用硬體支援的整數／混合精度路徑。是否更快取決於硬體、矩陣形狀、格式與實作，不能保證所有硬體都受益。

比較成本要分別量檔案大小、載入時的最高記憶體、執行時的最高記憶體，以及讀提示的prefill與逐步生成的decode時間（[16.2](16.md#16.2)）。臨時還原的矩陣也算在執行成本內。計時先暖機：用同樣的輸入試跑幾次、不列入平均，再固定生成步數重複測量。

練習把程式的`compressed = QuantizedLinear(layer, bits=4)`改成`bits=8`。先預測：碼2048byte，刻度與偏移各128byte，總共2304byte；輸出仍是FP32。這些數字不能拿來推算速度。本教材在NVIDIA L4 GPU上的小模型實測中，逐層反量化的4-bit路徑反而較慢；量測範圍在補充，不能外推到其他後端。

[GPTQ原論文的實用加速段落](https://arxiv.org/abs/2210.17323v2)也把收益歸到專用的量化矩陣／浮點向量kernel與較少的記憶體讀取，沒有把所有乘法改成整數。本課的`QuantizedLinear`採更直白的逐層完整反量化，也沒有實作GPTQ的權重校正。在本次L4測量，46-token提示、暖機後重複三次，FP32／4-bit／8-bit的prefill平均約2.405／4.958／2.768毫秒；固定八步、不因EOS早停的decode平均每步約2.371／4.882／2.814毫秒。這份小模型的參考4-bit路徑較慢，符合拆碼需要額外工作的可能性，不能外推成所有低位元後端都較慢。這些時間在[量化實驗紀錄（JSON）](https://github.com/birdhackor/tiny-perceptron-vlm/blob/main/docs/course-experiments/results/quantization.json)`results.runs`下各版的`timing`：`prefill_seconds`與`decode_seconds_per_token`的單位是秒。

先分清GPU記憶體的幾種計數。PyTorch的分配工具（allocator）負責拿取和重用GPU記憶體區塊；「已配置」計算它已交給tensor等資料、尚未釋放的區塊。「保留」還包括暫時空出、但留著供下一次重用的區塊，所以沒有被目前的tensor使用，也可能仍占GPU空間。CUDA驅動程式（driver）是讓程式與GPU溝通、執行工作的底層軟體，它本身需要的空間也沒有全算在PyTorch的這組數值裡。

三版探針的CUDA已配置記憶體峰值，比探針起點多335,872／376,320／359,936 bytes（`timing`的`cuda_additional_peak_bytes`）。這些是分配工具在本次前向期間的額外峰值；測量時其他版本仍同時留在GPU上，起點已有68,655,616 bytes。它們沒有量隔離程序的模型載入峰值、CUDA driver或所有保留記憶體，也不能用來宣稱4-bit整個執行只需376,320 bytes，或會隨檔案比例省RAM。各次探針會重設峰值計數，所以實驗紀錄最外層的`peak_allocated_bytes`也只量到最近一次重設之後，範圍寫在旁邊的`peak_memory_scope`。

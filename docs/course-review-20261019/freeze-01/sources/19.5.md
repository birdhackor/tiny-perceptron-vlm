## 19.5 讓助理簡短、誠實與守規則，要教哪種示範？

先告訴助理「接下來請用兩點回答」，再問「App錯誤訊息一直重複出現。」本章公開 MoE 權重在 CPU 上真正生成了：

> 1. 先檢查網路並重新啟動App。  
> 2. 仍失敗再詢問官方客服。

這個回答的內容對應當前 App 問題，也符合先前要求的兩點格式。公開的[輸入訊息](../../docs/selftrained/examples/v2/text.messages.json)只含一般工作設定、格式確認與問題；目前的答案是在呼叫模型後才產生的。這是挑選出的成功驗證例，可以核對介面與生成流程，不能由一題推出所有新問法都成功。

要教出這種行為，示範不能只有「問題 → 一句好答案」，還要讓**條件改變時，答案也改變**。本輪文字訓練資料包含下列實際示範。表中是拿來訓練的示範答案，與上方模型生成的回答用途不同。這些答案寫在資料準備程式的任務範本裡；範本與程式由 AI 工具 Codex 協助撰寫，答案沒有逐題經人撰寫或審核，見[V2資料說明](../../docs/selftrained/V2-DATA-NOTICE.md)。

| 工作條件與使用者問題 | 訓練示範回答 | 要教的差別 |
| --- | --- | --- |
| 用一句回答；「App打不開，該怎麼辦？」 | 先檢查網路並重新啟動App，仍失敗再詢問官方客服。 | 回應已教過的需求，使用指定格式 |
| 「那個問題要怎麼處理？」 | 請說明是地址、App還是卡片的問題。 | 資訊不足時先追問缺的條件，不自己猜是哪個問題 |
| 計算器不可用；「算0加0是多少。」 | 計算器目前不可用，請開啟後再計算。 | 依工具狀態回答，不假裝已執行 |
| 「請預測明天天氣。」 | 這超出我的範圍，我能協助有限聊天、地址、App、卡片或加減乘問題。 | 說明這個有限助理的工作範圍 |

這裡的「誠實」有具體教法：缺條件就詢問、工具未開就說未開、範圍外就說明範圍。也要保留能直接回答的題目，否則每題都求助也可能看似謹慎。學會幾種澄清句，不等於能估計任意問題的可靠程度；成品在測試題上是否選對行為，仍要另外評分。

**監督式微調（SFT）**就是用這種示範調整參數，讓模型在相同前文下較可能生成示範回答。system 訊息寫一般工作條件，user 訊息寫請求，assistant 訊息寫希望學到的回應。本輪 SFT 更新自己的文字核心；問題與歷史仍在輸入裡，但作答代價只計 assistant 的文字與 EOS（結束標記）。EOS 表示這輪回答結束，也需要學，不能只學會前幾個字。

先看結果：下面在 CPU 上整理一筆手寫示範，查看哪些字被列為 SFT 目標。它使用成品相同的訊息編碼器 `RecordEncoder` 與字元 tokenizer `CharacterTokenizer`，沒有下載權重、生成回答或更新模型。

```python
from tiny_perceptron.selftrained.dataset import RecordEncoder as LibraryEncoder
from tiny_perceptron.selftrained.tokenizer import CharacterTokenizer

messages = [
    {"role": "user", "content": "那個問題要怎麼處理？"},
    {"role": "assistant", "content": "請說明是地址、App還是卡片的問題。"},
]
tok = CharacterTokenizer.build([m["content"] for m in messages])
print("字表大小", tok.vocab_size)
print("BOS", tok.bos_id, "EOS", tok.eos_id, "user", tok.user_id, "assistant", tok.assistant_id)
row = {"id": "teaching-demo", "task": "text", "messages": messages}
library = LibraryEncoder(tok, ".").encode(row)
targets = [value for value in library["labels"] if value != -100]
print(tok.decode(targets, skip_special_tokens=False))
```

`CharacterTokenizer` 先固定 11 個特殊 token 的編號：0 是 PAD、1 是 BOS（開始標記）、2 是 EOS；3 到 6 是 user、assistant、system、tool 四個角色標記；7 到 9 是圖片、字卡、錄音的保留位置；10 是未知字元 `<unk>`。普通字元從 11 起依排序編號。`build` 收集傳入文字裡的每個字，另外一定加入 12 個讀字字元與 0–9，所以第一行印出的字表大小是 11 個特殊 token 加 46 個字元，共 57，第二行印出 BOS、EOS 與兩個角色標記的編號；成品改用全部訓練文字，並加入 ASCII 可列印字元與 12 個讀字字元建立字表，才是 19.2 的 550 個。實作見[tokenizer.py](../../tiny_perceptron/selftrained/tokenizer.py)。

`RecordEncoder(tok, ".")` 的第二個參數是素材資料夾（`asset_dir`），圖片與錄音檔要從這裡讀；這筆純文字記錄用不到素材，所以給目前資料夾 `"."` 即可。`encode(row)` 回傳一本字典：`"input_ids"` 是模型讀的編號，`"labels"` 是每個位置的答案。`[value for value in … if value != -100]` 只留下不是 −100 的答案，`decode` 再換回文字；`skip_special_tokens=False` 讓 EOS 也印出來。第三行輸出是 `請說明是地址、App還是卡片的問題。<eos>`：只有助手那句話和它的 EOS 會被計分。

它怎麼做到？下面是 `RecordEncoder` 的精簡版，只留純文字對話的 `encode`。函式庫版本另外還有這些部分，精簡版都省略了：

- 讀進圖片、字卡與錄音，並在對話裡放進它們的保留位置（[19.6](19.md#19.6)講這些材料怎麼交給文字核心）。
- `encode` 的四個選項：`pretrain`（每則訊息的角色標記、內容與 EOS 都計分，不只助手的部分）、`generation`（推論用：在結尾補上 assistant 角色標記；沒有另外給 `messages` 時，也先去掉紀錄裡最後一則訊息）、`messages`（改用呼叫者另外給的訊息清單）與 `modality_override`（把素材特徵換成全零）。
- 長度上限檢查，以及 tokenizer 回傳 tensor 時先轉成清單的步驟。
- 組成 batch 與搬到裝置的 `batch`、`to_device`；回傳值裡的 `modalities` 與 `record` 兩個欄位也一併省略。

```python
# 精簡自 tiny_perceptron/selftrained/dataset.py：RecordEncoder（只留純文字對話的 encode；省略圖片、字卡與錄音的讀取與保留位置，pretrain、generation、messages、modality_override 四個選項，長度檢查，tensor 轉清單，batch、to_device 與回傳的 modalities、record）
class RecordEncoder:
    def __init__(self, tokenizer):
        self.tokenizer = tokenizer

    def encode(self, record):
        tok = self.tokenizer
        ids, labels = [tok.bos_id], [-100]
        for message in record["messages"]:
            role_id = getattr(tok, message["role"] + "_id")
            content = tok.encode(message["content"])
            ids += [role_id] + content + [tok.eos_id]
            if message["role"] == "assistant":
                labels += [-100] + content + [tok.eos_id]
            else:
                labels += [-100] * (1 + len(content) + 1)
        return {"input_ids": ids, "labels": labels[1:] + [-100]}
```

- `ids` 從 BOS 開始。BOS 本身不是要學的答案，所以 `labels` 同時放一個 −100。
- 每則訊息依序放進三段：角色標記、內容、EOS。`getattr(tok, "assistant_id")` 等於寫 `tok.assistant_id`；這裡用字串拼出 `"user_id"` 或 `"assistant_id"`，依角色欄位取出對應的編號。`+=` 把右邊的清單接到原清單後面。
- 助手訊息的 `labels` 依序是 −100（角色標記不學）、內容的每個字、EOS；其他角色整段都是 −100，`[-100] * (1 + len(content) + 1)` 做出與「角色標記＋內容＋EOS」等長的一串。到這裡，`labels` 與 `ids` 的位置一一對應，記的都是「這個位置放了什麼」。
- 最後的 `labels[1:] + [-100]` 把答案整串往左移一個位置：切片 `[1:]` 去掉第一個，再在尾端補一個 −100。位置 i 的答案因此變成位置 i+1 的編號，也就是「讀到這裡，下一個字應該是什麼」；[4.7](04.md#4.7)的 `shifted` 做的是同一件事。

核對精簡版，並把交界處印出來看：

```python
ours = RecordEncoder(tok).encode(row)
same = ours["input_ids"] == library["input_ids"] and ours["labels"] == library["labels"]
print("與函式庫相同：", same)
assert same
start = ours["input_ids"].index(tok.assistant_id)
for i in range(start - 1, start + 3):
    shown = tok.decode([ours["input_ids"][i]], skip_special_tokens=False)
    target = "不計" if ours["labels"][i] == -100 else tok.decode([ours["labels"][i]])
    print("讀到", shown, "→ 目標", target)
```

第一行印出 True：兩份編號與答案逐項相同。`index` 找到 assistant 角色標記的位置 `start`，`range(start - 1, start + 3)` 從它的前一個位置印到它後面第二個位置，共四行；`"不計" if … else …` 是條件運算式，條件成立取前者，否則取後者。讀到使用者訊息結尾的 `<eos>` 時目標是「不計」：下一個是角色標記，由程式插入，不必學。讀到 `<assistant>` 時目標是「請」，讀到「請」時目標是「說」：模型讀問題與已給定的回答前綴，逐字預測下一個字。

`-100` 表示該位置不計作答代價，並沒有把使用者問題從輸入刪掉。真正推論時，模型則要接著自己剛生成的字繼續回答。能把標籤整理對，只證明訓練目標的安排，不證明模型已學會。

練習把第一段程式 `messages` 第一則的 `"role": "user"` 改成 `"role": "assistant"`，先預測：兩則都是助手訊息，第三行會印出兩句話，各帶一個 `<eos>`；再執行核對。

文字示範還包含選項記憶、格式改寫與工具請求／讀回。**選項記憶**是記住使用者在前文最後選定的東西：例如前文說「我先選褲子，後來改選短靴，接下來用一句回答。」之後問「請說出我的選項。」應答「你選了短靴。」[19.12](19.md#19.12)的「改歷史選項」對照就在檢查這件事。訓練題、驗證題與測試題依前面的家族分開；驗收時分別查內容、指定範圍、格式、完整結束及澄清行為，19.12 會列出分項結果。下一節沿用這些回答規則，只把其中一輪的文字材料換成圖片或聲音。

## 7.10 答案被截光了還在訓練嗎？

問題「很長的問題」，回答「是」。如果只保留序列的前兩個位置，剩下的是 BOS 和 user，沒有任何回答目標。輸入裡仍有 token ID，卻不表示這份資料還提供可以平均的答案代價。

labels 中不是 −100 的個數，就是平均代價的分母。把資料截短或切段後要重新數：至少要保留一個目標，也要看完整答案和 EOS 有沒有留下來。下面用專案的 `pad_batch` 把資料排成 batch，並故意只留兩個位置。

```python
from tiny_perceptron.data import IGNORE, pad_batch, render_chat

example = render_chat(
    [
        {"role": "user", "content": "很長的問題"},
        {"role": "assistant", "content": "是"},
    ]
)
try:
    pad_batch([example], max_length=2)
except ValueError as error:
    print("預期的資料錯誤：", error)
else:
    raise AssertionError("應該偵測到沒有可學的答案")
x, y = example
first = (y != IGNORE).nonzero()[0].item()
print("第一個有效目標的索引", first, "最低保留長度", first + 1, "完整長度", len(x))
```

`pad_batch` 把幾筆資料補齊成同一張表，`max_length=2` 要求最多只留兩個位置。這一筆截斷後全是 −100，`pad_batch` 會報錯。為了讓程式在預期的錯誤之後繼續，這裡用 `try`：先試著執行 try 底下的程式；若發生 except 指名的那種錯誤（ValueError），就改跑 except 底下的程式，`as error` 把錯誤取名為 error，印出來就是錯誤訊息。若 try 底下完全沒出錯，則跑 else。我們預期一定會報錯，沒報錯反而表示檢查失效，所以在 else 裡用 `raise AssertionError(...)` 主動丟出錯誤。

程式後半段找出第一個有效目標在索引 18。原序列依序是 BOS、user、問題的 15 個 byte（五個字各三個 byte）、user 段的 EOS、assistant、答案的 3 個 byte 與 EOS，共 23 個 token；答案的第一個 byte 在原序列索引 19，移一位後落在 Y 的索引 18，由 X 在這個位置的 assistant 預測。所以長度至少要 19，才保留一個答案目標。完整長度是 22：X 是原序列去掉最後一項，所以 X 不含最後的 EOS；Y 的索引 18 到 21 依序是「是」的三個 byte 與 EOS，共四個有效目標。長度按 X／Y 的位置數計，不按中文字數；依 [7.4](#7.4)，回答的第一個 byte 由 assistant 的位置預測，所以最低合法長度不必把答案本身放進輸入。只有一個目標，表示平均有分母，不表示完整的回答都受過訓練。

`pad_batch` 怎麼補齊、又怎麼抓到空題？下面是它的原始碼：

```python
# 節錄自 tiny_perceptron/data.py：pad_batch
def pad_batch(examples, pad_id=0, max_length=None):
    """右側 padding；attention 的有效位置和 loss 的有效位置各自保留。"""
    if not examples:
        raise ValueError("batch 不能是空的")
    length = max(len(x) for x, _ in examples)
    if max_length is not None:
        length = min(length, max_length)
    x = torch.full((len(examples), length), pad_id, dtype=torch.long)
    y = torch.full_like(x, IGNORE)
    valid = torch.zeros_like(x, dtype=torch.bool)
    for row, (inputs, labels) in enumerate(examples):
        n = min(length, len(inputs))
        x[row, :n], y[row, :n], valid[row, :n] = inputs[:n], labels[:n], True
        if not (y[row] != IGNORE).any():
            raise ValueError(f"第 {row} 筆截斷後没有有效答案；增加 max_length 或移除這筆")
    return x, y, valid
```

`examples` 是一份清單，每項是一筆的「X、Y」。`max(len(x) for x, _ in examples)` 逐筆取輸入長度，用最長那筆當表的寬度（`_` 表示 Y 在這裡用不到）；有傳 max_length 時（`is not None`），再取兩者較小的那個。接著先做三張填好預設值的表：`torch.full` 做出全是 PAD 的輸入表，`torch.full_like(x, IGNORE)` 做出同形狀、全是 −100 的目標表，`torch.zeros_like(..., dtype=torch.bool)` 做出全是 False 的 valid。

迴圈 `for row, (inputs, labels) in enumerate(examples)` 逐筆處理，`row` 是第幾列。`n` 是這筆實際能放幾個位置，下一行用逗號一次填三張表：把前 n 個輸入、前 n 個目標與 True 填進第 row 列的開頭。資料都放在左邊，PAD 留在右邊，所以這是右側補齊。最後的 `if` 檢查這一列：`.any()` 問有沒有任何一個目標不是 −100，一個都沒有就報錯。錯誤訊息用的是 f 字串：開頭寫 `f` 的字串裡，大括號 `{row}` 會換成變數 row 的值，所以訊息會指出是第幾筆。逐筆檢查，才能避免一批之中的空題被其他題的答案掩蓋。

遇到長題，可以擴大上下文視窗、保住完整答案、重新設計切段方式，或明確地過濾掉，並記下來源與原因。語意被截斷的回答，也不能靠補一個 EOS 變成完整答案。

練習把第一段程式從 `try:` 到 `raise` 的六行，換成 `bx, by, valid = pad_batch([example], max_length=19)` 與 `print((by != IGNORE).sum().item())`。先預測：不再報錯，有效目標只有 1 個，也就是答案的第一個 byte；再執行核對。改成 22 應得到 4。用有效目標數，就能看出答案被截掉多少，而不是只看長題有多少輸入 token。

自然對話尤其不能只問「放得進去嗎」。[T.4 的 UltraChat 小型實跑](../training.md#T.4)另取 100 筆資料的第一輪問題與回答，各保留最多 120 個 byte、末尾保持完整的字，再按家族切成 80／10／10 筆。這讓一筆能放進位置上限 256 的實跑小模型，答案也不會被截到一個有效目標都不剩；但有些問題與回答在句中就結束，意思可能已不完整。我們為片段加上的 EOS，表示這次片段結束，不是原對話已回答完畢。

這個獨立模型只更新 80 次，十題驗證題與十題測試題的答案 ID 完全相同的題數都是 0，實際生成也有大量零碎字詞；見[實驗紀錄（JSON）](https://github.com/birdhackor/tiny-perceptron-vlm/blob/main/docs/course-experiments/results/sft.json)的 `results.ultrachat_pilot.evaluation`，`matches` 是完全答對的題數。開放式問答本來就不能只靠與示範一字不差來判斷好壞；這份結果更沒有支持「已能完成原問題」。它適合確認下載、轉換、遮罩與更新走得通；若要研究完整的對話能力，應先保留題目語意與完整答案，再安排相應的模型與預算。

## 7.9 模型怎麼知道回答結束？

回答 A 之後應該結束，可是普通的句號後面也可能接下一句。把 EOS 這個特殊 token 放在回答尾端，並當成有效目標，模型才有機會學到「在這裡結束」。

生成另有一個上限，限制這次最多寫多少新 token。EOS 是模型自己選的結束，上限是外部給的預算。下面先查回答最後一個目標，再給一份手寫的候選 `[A, EOS, B]`，只驗證停止的判斷。

```python
from tiny_perceptron.data import ByteTokenizer, render_chat

tok = ByteTokenizer()
x, y = render_chat([{"role": "user", "content": "Q"}, {"role": "assistant", "content": "A"}])
print("最後一個目標", y[-1].item(), "EOS", tok.eos_id)
assert y[-1].item() == tok.eos_id
generated = [tok.encode("A")[0], tok.eos_id, tok.encode("B")[0]]
max_new_tokens = 2
visible = []
for token in generated[:max_new_tokens]:
    if token == tok.eos_id:
        break
    visible.append(token)
print("顯示的內容", tok.decode(visible))
```

第一行確認 [7.1](#7.1) 的 `render_chat` 產生的最後一個目標是 2，也就是 EOS。後半段的 generated 是預先寫好的模擬輸出 `[73,2,74]`，不是模型訓練後的實測：73 是 A，74 是 B。`generated[:max_new_tokens]` 只取前兩項，代表最多生成兩個新 token；迴圈每次檢查一項，遇到 EOS 就 `break`，立刻跳出迴圈，不把 EOS 加進要顯示的 visible。所以畫面只顯示 A，後面的 B 不會出現。

實際的模型每一步會替所有候選給出 logits，選出下一個 ID 後再檢查要不要停，就像 [1.14](01.md#1.14) 的逐步生成；這裡先給定結果，是為了單獨驗證停止規則。EOS 通常留在保存的 token 序列裡；轉回文字時，`decode` 只轉換普通內容的 ID（8 以上），跳過特殊 token，所以使用者看到的回答不會出現字面上的 `<eos>`。

歷史 user 段的 EOS 只表示那段話已經結束，不會讓還沒開始的 assistant 回答立刻停止。逐 byte 生成時，上限還可能把一個中文字切成一半，轉成文字前要像 [6.7](06.md#6.7) 那樣等 bytes 完整。評估時要分開記三件事：內容是否正確、模型是否自己選了 EOS、是否因為達到上限才停。只看到回答末尾有句號，分不出是模型選了 EOS 還是被上限截斷，更看不出內容對不對。

練習把 generated 改成 `tok.encode("ABCD")`，max_new_tokens 保持 2。先預測：裡面沒有 EOS，只能顯示 AB，再執行核對；這次停止來自上限，不代表模型學會適時結束。改回原本的清單則顯示 A。兩種停止來源都能直接驗證。

<summary>補充：實測中，會結束不等於答對</summary>

學會結束，也不等於內容答對。[T.4 的屬性問答模型](../training.md#T.4)訓練 900 次後，對一筆應回答 `circle` 的驗證題生成 `cire`，原始 ID 是 `[107,113,122,109,2]`：最後的 2 確實是 EOS，前四項卻拼出錯誤的答案。這份模型在五題驗證題與十題測試題都自己結束了，內容仍有許多錯誤。逐題結果在[實驗紀錄（JSON）](https://github.com/birdhackor/tiny-perceptron-vlm/blob/main/docs/course-experiments/results/sft.json)，這是機器可讀的完整結果：`results.after.validation.samples` 與 `results.after.test.samples` 的每一筆裡，`generated_ids` 是生成的 ID，`eos` 表示是否自己結束，`exact` 表示是否完全答對。因此評估要保留原始生成 ID 與 EOS 欄位，再分開計算答案是否正確，不能只看最後有沒有停。

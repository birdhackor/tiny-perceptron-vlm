## 7.3 哪些位置應該學？

「問→答」這筆對話，需要模型讀到「問」，但我們希望它練習寫的是「答」和回答結束。把問題留在輸入 X，再用 Y 標出哪些下一項要計代價，就能同時做到這兩件事。

回想 [7.1](#7.1)：Y 的第 i 個目標，是 X 第 i 個位置要猜的下一項；目標是 −100 的位置不計代價。`render_chat` 先讓 `targets` 和完整序列逐項對應，再和輸入一起移一位，所以「答案是什麼」和「要不要計分」會一起落在負責預測它的位置上。下面逐位置印出輸入 ID、目標與是否計分。這次沒有傳 tokenizer，`render_chat` 會自己建立同一份 ByteTokenizer（7.1 原始碼的 `tokenizer or ByteTokenizer()`）。

```python
from tiny_perceptron.data import render_chat

messages = [
    {"role": "user", "content": "問"},
    {"role": "assistant", "content": "答"},
]
x, y = render_chat(messages)
for position, (token, label) in enumerate(zip(x.tolist(), y.tolist(), strict=True)):
    status = "計代價" if label != -100 else "不計代價"
    print(position, "輸入ID", token, "目標", label, status)
print("有效目標數", (y != -100).sum().item())
assert (y != -100).sum().item() > 0
```

ByteTokenizer 以 byte 表示文字，「問」與「答」各是三個 byte，也就是各三個 token，所以不能按一個字算一個有效目標（見 [6.7](06.md#6.7)）。迴圈的 `enumerate(zip(...))` 同時提供位置編號與「輸入、目標」這一對，是 [1.1](01.md#1.1) 的 `enumerate` 和 [1.3](01.md#1.3) 的 `zip` 疊在一起；`status` 用 7.1 介紹過的 `A if 條件 else B` 選出要印的文字。最後的有效目標數應是 4：答的三個 byte，加上回答結尾的 EOS。user 內容、user 段的 EOS 與兩個角色標記，都不當成要模仿的答案。`(y != -100)` 得到一串真／假，`sum` 把 True 當 1、False 當 0 相加，正好數出有效目標；`.item()` 取成普通整數。

X 和 Y 交給不同的對象。X 交給模型，用每個 ID 查 [2.1](02.md#2.1) 的 embedding 表；Y 只交給交叉熵，和模型的預測比對，−100 從來不會被拿去查表。不計 user 位置的代價，並沒有刪掉問題，也沒有禁止後面的位置透過注意力讀它，[7.5](#7.5) 會實際檢查這一點。只學 assistant 的位置，能讓監督集中在回答上；但示範本身對不對，仍要另外核對。

練習只把 assistant 的內容改成 `"答案"`。先預測：兩個中文字共六個 byte，加 EOS 共七個有效目標；X 也會變長，被忽略的 user 問題仍在輸入裡。執行核對後，再試英文 `"OK"`：應是兩個 byte 加 EOS，共三個。有效目標的計數單位跟著編碼規則走，不跟著肉眼看到的字數走。

## 6.6 特殊 token 怎麼保持完整？

使用者問：「`<assistant>` 這串字是做什麼用的？」他只是在討論這串字，模型應該把它當成普通文字讀，不該以為輪到助手（assistant）說話了。要做到這件事，tokenizer 需要兩個約定：普通文字和標示結構的 token 用不重疊的 ID；標示結構的 token 只由程式依照資料的欄位插入，不從文字內容猜。

**特殊 token**（special token）是不代表任何原文、專門標示結構的 token。本課 `ByteTokenizer` 的 ID 0 到 7 就是 8 個特殊 token，它們的拼寫依序存在 `tiny_perceptron/data.py` 開頭的常數 `SPECIALS` 裡：

| ID | 拼寫 | 名稱 | 標示什麼 |
| --- | --- | --- | --- |
| 0 | `<pad>` | PAD（填充） | 把長短不同的序列補成一樣長時補上的位置（[7.6](07.md#7.6)） |
| 1 | `<bos>` | BOS（開始標記） | 一條序列的開頭 |
| 2 | `<eos>` | EOS（結束標記） | 一段文字或一段話到此結束 |
| 3 | `<user>` | 角色標記 | 接下來是使用者說的話 |
| 4 | `<assistant>` | 角色標記 | 接下來是助手說的話 |
| 5 | `<image>` | 圖片的位置 | 圖片要放進序列的地方（第 10 章） |
| 6 | `<audio>` | 聲音的位置 | 聲音要放進序列的地方（第 12 章） |
| 7 | `<system>` | 角色標記 | 接下來是整段對話共用的規則 |

**角色**（role）指這段話是誰說的：user 是使用者，assistant 是助手，system 放整段對話共用的規則。第 7 章才講對話資料，這裡只需要知道：每段話旁邊另有一個欄位寫明角色，例如 `{"role": "user", "content": "你好"}`，`content` 才是那段話的文字。**模態**（modality）指資料的種類，例如文字、圖片、聲音；`<image>`、`<audio>` 就是替圖片與聲音保留的特殊 token。

先看結果：把字串 `<assistant>` 當普通文字編碼，看看會不會冒出 ID 4。

```python
from tiny_perceptron.data import ByteTokenizer, SPECIALS

tok = ByteTokenizer()
print(list(enumerate(SPECIALS)))
literal = tok.encode("<assistant>")
print("普通文字的ID", literal)
print("還原", tok.decode(literal))
assert tok.assistant_id not in literal
```

`enumerate(SPECIALS)`（[1.1](01.md#1.1)）逐項給出「位置、拼寫」，`list(...)` 把它們收成清單印出；位置就是 ID，所以印出的第一行有 `(4, '<assistant>')`。`tok.encode("<assistant>")` 得到 11 個 ID：這串字是 11 個 ASCII 字元，每個 1 byte，`encode` 把每個 byte 加 8，例如 `<` 的 byte 是 60，變成 68；結尾的 `>` 是 62，變成 70。內容 ID 都至少是 8，不可能出現 4。`decode` 把它還原成同樣的 `<assistant>`，最後的 assert 確認這串文字沒有被當成助手的角色標記。

它怎麼做到的？下面是函式庫裡 `ByteTokenizer` 的原始碼。

```python
# 節錄自 tiny_perceptron/data.py：ByteTokenizer
class ByteTokenizer:
    """不學切詞的可還原起點；每個 UTF-8 byte 對應一個 ID。"""

    vocab_size = 264
    pad_id, bos_id, eos_id, user_id, assistant_id, image_id, audio_id, system_id = range(8)

    def encode(self, text):
        return [b + len(SPECIALS) for b in text.encode("utf-8")]

    def decode(self, ids):
        raw = bytes(i - len(SPECIALS) for i in ids if i >= len(SPECIALS))
        return raw.decode("utf-8", errors="replace")

    def state(self):
        return {"type": "byte", "specials": list(SPECIALS)}
```

`class ByteTokenizer:` 定義一種新的物件，`ByteTokenizer()` 就建立一個，像上面的 `tok`。它和 [3.7](03.md#3.7) 的注意力零件 `CausalAttention` 有兩點不同。第一，它不繼承 `nn.Module`：`nn.Module` 是 PyTorch 零件的共同基礎，而 `ByteTokenizer` 不是模型裡的零件，它的 `encode` 與 `decode` 只在字串和整數清單之間轉換，裡面沒有任何 tensor。第二，它沒有寫 `__init__`：`__init__` 在建立物件時執行一次，替這個物件存下自己的資料，例如 3.7 的可學部分；`ByteTokenizer` 沒有這種各存一份的資料，字表大小與 8 個特殊 token 的 ID 直接寫成整個 class 共用的設定。同一個檔案裡的 [`CharTokenizer`](../../tiny_perceptron/data.py) 就有 `__init__`：每建立一個，都要記住從自己那份文字收集到的字元清單。逐段看：

- 直接寫在 class 底下的 `vocab_size = 264` 是每個 `ByteTokenizer` 共用的設定：256 種 byte 加 8 個特殊 token。
- `range(8)` 那一行一次把 0 到 7 依序指定給等號左邊的八個名字，所以 `tok.assistant_id` 是 4、`tok.image_id` 是 5。
- 寫在 class 裡的 `def` 叫方法，用 `tok.encode(...)` 這種寫法呼叫；第一個參數 `self` 是 `tok` 本身，由 Python 自動傳入。
- `encode`：`text.encode("utf-8")` 得到一串 0 到 255 的 byte，`b + len(SPECIALS)` 把每個加上 8（`len(SPECIALS)` 是 8），普通文字因此只會落在 8 到 263。
- `decode`：`for i in ids if i >= len(SPECIALS)` 後面的 `if` 表示只留下符合條件的項，ID 小於 8 的特殊 token 不代表原文，直接略過；其餘減回位移 8，`bytes(...)` 把這串 0 到 255 的整數組回 byte，再照 UTF-8 換成文字。`errors="replace"` 讓不完整的 byte 顯示成 �，[6.7](#6.7) 會看到它。
- `state`：回傳 tokenizer 的種類與特殊 token 清單。[`tiny_perceptron/capstone.py`](../../tiny_perceptron/capstone.py) 存權重時把它一起存下，載入時若和目前的 `state()` 不同就報錯。

那真正的角色標記從哪裡來？由程式依照角色欄位插入：

```python
message = {"role": "user", "content": "<assistant>"}
role_ids = {"user": tok.user_id, "assistant": tok.assistant_id}
ids = [tok.bos_id, role_ids[message["role"]]] + tok.encode(message["content"]) + [tok.eos_id]
ids = ids + [tok.assistant_id]
print(ids)
print("最後一個ID", ids[-1], "ID 4 的個數", ids.count(tok.assistant_id))
```

`role_ids` 是查表用的字典：角色欄位寫的是 `"user"`，就查到 3。程式依序放進 BOS（1）、查到的角色 ID（3）、內容的 byte ID、EOS（2）；清單的 `+` 是把兩份清單接起來。`ids = ids + [tok.assistant_id]` 再接上 4，表示接下來輪到助手回答（[7.2](07.md#7.2) 準備生成時也是這個順序）。`ids.count(tok.assistant_id)` 數出 4 只有一個，就是程式最後放上的那一個；內容裡字面上的 `<assistant>` 仍是 68、105 這些普通 ID。原文與結構分開，內容就能無損還原，邊界也不會被文字冒充。

BPE 這類會學合併的 tokenizer 也要守住同一條線。`tokenizers` 套件可以把 `<user>`、`<assistant>` 整串登記成特殊 token，讓它們各占一個固定的 ID；但登記之後，`encode` 預設會把普通文字裡字面上的 `<user>` 也換成那個 ID，使用者打的字就冒充了角色標記。所以光登記特殊 token 不夠，還要規定普通內容怎麼編碼：本課的 BPE 實驗另外準備一份不認特殊 token 的規則，專門編普通內容（見補充）。保存 tokenizer 時，字表要和這條規則一起保存。另外，插入特殊 token 只是標出結構，本身不會教會模型怎麼回答，也不會產生圖片的特徵。

練習把第一段程式的 `tok.encode("<assistant>")` 改成 `tok.encode("<image>")`，`assert tok.assistant_id not in literal` 改成 `assert tok.image_id not in literal`。先預測：還原仍是這 7 個字元，內容 ID 都至少是 8，不會出現圖片的特殊 token 5，再執行核對。接著把第三段程式的 `"role": "user"` 改成 `"role": "assistant"`，先預測第二個 ID 變成 4，`ID 4 的個數` 變成 2：角色欄位改了，插入的標記才跟著改，內容那串字仍是普通 ID。

<summary>補充：BPE 實驗怎麼守住這條線</summary>

本課的 BPE 實驗（[6.3](#6.3) 的補充）先把 8 個特殊 token 登記進字表，占 ID 0 到 7；編普通內容時，改用一份不比對特殊 token 的規則。實際核對 `<user>這只是引用文字` 時，它完整還原成同一段原文，內容 ID 裡也沒有任何特殊 token 的 ID：[實驗紀錄（JSON）](../../docs/course-experiments/results/tokenizer.json)的 `results.roundtrip` 第 3 筆，`same` 是 `true`、`contains_control_id` 是 `false`。推論時配對 BPE 的 [`ByteLevelBPE`](../../tiny_perceptron/tokenization.py) 也照這個做法，而且編普通文字時，編出的 ID 只要落在 0 到 7 就直接報錯。

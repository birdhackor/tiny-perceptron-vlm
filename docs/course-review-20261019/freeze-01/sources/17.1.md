## 17.1 數字個數相同，為什麼空間不同？

一張64列、32欄的權重表有2048個數字。要算它佔多少空間，還要知道每格怎麼存。**bit（位元）**有兩種狀態，八個bit組成一個**byte（位元組）**。FP32每格32bit，即4byte；FP16是[16.7](16.md#16.7)介紹過的16位元浮點格式，每格2byte；**int8**是有正負號的8位元整數，每格1byte，只能存−128到127的整數。

因此同一張表的數值部分分別是8192、4096、2048byte。形狀和參數個數沒變，改的是每個數能表示的範圍與細節。**量化（quantization）**就是把原數值換成少數幾個離散選項之一，目標是減少表示成本，同時把精度的下降控制住。

FP16與FP32都是浮點數，每個數自帶次方，不必另外記錄其他數字，就能存下0.7這種小數（只差極小的捨入）；int8只有整數。本章要把權重改存成整數，所以接下來先解決「整數怎麼代表小數」：另外記一個刻度，把整數換回原來的數值範圍。

```python
import torch

weight = torch.zeros(64, 32)
for dtype in (torch.float32, torch.float16, torch.int8):
    converted = weight.to(dtype)
    count = converted.numel()
    per_value = converted.element_size()
    print(dtype, "元素", count, "每格bytes", per_value, "總bytes", count * per_value)
```

`for dtype in (…)`依序取出圓括號裡用逗號分開的三種型別。`to(dtype)`建立指定型別的新tensor，`numel()`數元素，`element_size()`回報每格byte。三版都有2048格，最後一欄是8192、4096、2048，對上手算。全零表只用來隔離空間問題，不是學好的模型。

這裡尚未寫檔。完整檔案還有名稱、形狀、型別等附帶資訊，低位元版本也須保存還原用的刻度，所以檔案大小不能只用參數數量乘bit。執行時還有中間特徵（activation，層與層之間傳遞的數字，[17.11](17.md#17.11)會定義）與生成用的KV cache（[16.3](16.md#16.3)），訓練時另有梯度和最佳化器狀態（optimizer state）；權重縮小，不表示整臺機器的記憶體同比例縮小。

也不能直接用`.to(torch.int8)`當量化方法：它把小數部分直接捨去，0.7會變成0，而且沒有記下怎麼對回原來的範圍。全零在三種型別都精確，才適合本次的空間比較。下一節補上這份對應規則。

練習把程式的`weight = torch.zeros(64, 32)`改成`weight = torch.zeros(128, 32)`。先預測：三種型別的元素數都變4096，每格byte不變，總byte加倍成16384、8192、4096，再執行核對。

4-bit／8-bit在這份紀錄中描述的是Linear層權重的存法：115,200個權重換成低位元，其餘25,728個數字與640個偏移（bias）仍保存為FP32，共26,368個浮點數。偏移是每個輸出在加權和之後再加上的數。量化版本還新增1,416個FP32刻度，用來把碼還原到原來的數值範圍；刻度與碼下一節再展開，本節先把它們的儲存也算進來。

| 數值儲存部分 | 原FP32模型（bytes） | 4-bit版本（bytes） | 8-bit版本（bytes） |
| --- | ---: | ---: | ---: |
| 115,200個Linear權重 | 460,800 | 57,600 | 115,200 |
| 26,368個其餘數字與偏移，保留FP32 | 105,472 | 105,472 | 105,472 |
| 新增1,416個FP32刻度 | 0 | 5,664 | 5,664 |
| 合計 | 566,272 | 168,736 | 226,336 |

兩個4-bit碼放在一byte，所以115,200個需要115,200÷2＝57,600 bytes；保留的FP32數字占26,368×4＝105,472，刻度占1,416×4＝5,664。因此4-bit這一欄是57,600＋105,472＋5,664＝168,736 bytes。這個合計已包括仍用FP32的數字與新增的刻度；檔案的名稱、形狀與其他容器資訊，才是合計之外再加上的部分。要核對壓縮率，先問哪些數字換了存法，再按各部分的存法相加。

## 16.1 怎麼從一種運算的耗時找下一個瓶頸？

同一個模型讀三個token，和讀十二個token，參數不變，花的時間卻可能不同。我們想知道新增的工作落在哪裡，才知道下一步值得改善什麼。只看「整個模型用了兩秒」還不夠；先把時間對上能辨認的運算，再決定值得改哪一步。

材料是一段ID `[1,2,3]` 和特徵寬度8（`width=8`）的TinyLM。這個[一層模型](04.md#4.5)經查表、注意力與FFN後，替每個位置輸出字表分數；FFN是每個位置各自處理特徵的網路，`TinyLM`的實作見[4.6](04.md#4.6)。profiler（效能剖析器）會記錄各運算的時間與呼叫次數。本節先練習讀出一種矩陣乘法的成本，作為再往下查的線索。

程式先跑三次暖機，避免把第一次初始化當成穩定成本；接著只記錄五輪前向計算。`key_averages()` 把同名運算彙整成一列，`# of Calls` 是這五輪內的總呼叫次數，同一運算每輪出現多次時，這個數會大於5。

時間欄也要先分清：**Self CPU** 只算該運算本身，不包含它呼叫的子運算；**CPU total** 則包含子運算；**CPU time avg** 是這列的CPU total除以呼叫次數，並非五輪模型時間的平均。百分比欄以整份記錄的Self CPU時間合計為參考。父子運算的total可能重複包含同一段工作，不能把所有total相加當成整體時間。下面按Self CPU由大到小列前十種工作，先找直接花時間的運算。

```python
import torch
from torch.profiler import profile, ProfilerActivity
from tiny_perceptron.model import TinyLM, ModelConfig

torch.set_num_threads(1)
model = TinyLM(ModelConfig(width=8)).eval()
ids = torch.tensor([[1, 2, 3]])
with torch.no_grad():
    for _ in range(3):
        model(ids)
    with profile(activities=[ProfilerActivity.CPU]) as p:
        for _ in range(5):
            result = model(ids)
print("分數形狀", tuple(result["logits"].shape))
print(p.key_averages().table(sort_by="self_cpu_time_total", row_limit=10))
print("參數bytes", sum(v.numel() * v.element_size() for v in model.parameters()))
```

輸入一列三個ID，預設字表264項，第一行應為 `(1,3,264)`，可確認確實執行了整個模型而非空迴圈。這裡只開CPU活動，不會替你量到GPU工作。

先找表中涉及矩陣乘法的一列，例如`mm`、`matmul`或`addmm`；它們都含「一列對一欄，逐項相乘再相加」的工作。讀它的Self CPU時間，也就是這種運算本身花的時間；再看`# of Calls`，也就是五輪裡呼叫幾次。時間每次執行都會起伏，排名也可能跟著變；十列裡找不到矩陣乘法時，把`row_limit=10`改成20再找。

呼叫次數不隨機器快慢改變，可以先拿來對照模型。例如`aten::mm`是25次，也就是每輪5次，正好對上不加偏移的5個Linear：注意力的Q、K、V與輸出投影，以及輸出層。FFN的兩個Linear有偏移，PyTorch改用相乘後再加偏移的`aten::addmm`，每輪2次、共10次。哪幾列排得進前十，每次執行都可能不同；想同時看到這兩列，就把`row_limit`改大。不過同一列合併了好幾個零件，看不出時間在它們之間怎麼分，所以這份按名稱彙總的表還不能唯一指出哪一層最花時間。把輸入改長後，若同名運算的時間穩定增加，便值得再查它處理了多少格。

最後一行的`numel()`回報參數表有幾個元素，`element_size()`回報每個元素占幾bytes，兩者相乘才是該表的數字bytes，再沿所有參數表相加。此設定6104個32位元浮點數（FP32）參數、每個4bytes，應得24416bytes；它與表中的微秒是不同單位。執行時還有中間特徵、生成用的cache；訓練更有梯度與最佳化器狀態（optimizer state，見[5.4](05.md#5.4)），所以參數大小不能代表最高記憶體占用。profiler本身也會增加開銷，主要用於定位，總耗時應另以重複計時核對。

後文的實測時間分開記推論與訓練；記憶體用MiB，1 MiB=2²⁰ bytes。開始量測時已配置多少（後文稱起點記憶體）、過程增加多少，也分開列出。完整暖機、同步與配置器範圍見[T.8的效率量測方法](../training.md#選讀效率實驗的量測條件)。

練習把程式的 `ids = torch.tensor([[1, 2, 3]])` 改成 `ids = torch.arange(1, 13)[None]`：`torch.arange(1, 13)`產生1到12，`[None]`補上筆數軸，成為一段十二個token。先預測分數形狀變成 `(1,12,264)`、參數bytes不變，再從頭執行。原輸入和新輸入各重複三輪，按相同運算名稱比較Self CPU時間與呼叫次數，不拿兩張表的第一名互比。`aten::mm`這類模型運算的呼叫次數不會變，因為每輪用到的Linear一樣多；變的是每次處理的位置數。想看的列未出現時，把`row_limit=10`改成20，找查表、softmax或矩陣乘法列。

如果某一列在較長輸入下多次都花更久，就值得再查它處理了多少位置；如果時間起伏比差異更大，結論就是這份短例子尚未顯示穩定差距。完成練習只需核對形狀、參數bytes，並用表中一種可辨認的工作說明這兩種結果之一。這樣得到的是下一步量測的線索，不是對整個模型瓶頸的定論。

<details>
<summary>選讀：profiler各列、各欄與底層名稱</summary>

`aten::`前綴是PyTorch底層運算名稱，不是模型層的名稱。

讀到陌生列時，先分清它在做哪種工作。`new_zeros`建立裝滿零的數字容器；`empty`、`new_empty`、`empty_like`準備儲存空間，尚未填好數值。`view`、`unsqueeze`與`as_strided`處理形狀或讀取同一份儲存的方式。`repeat_interleave`來自[16.4](16.md#16.4)要講的KV頭複製：本例只有一個頭，複製成一份也要付呼叫開銷。它們也有執行成本，但排名高不能直接解讀成「注意力算太多」。這個特徵寬度只有8的短例子，準備容器與呼叫運算的開銷就可能佔很大比例。

再找能連回已學內容的列：`index_select`用於字與位置的查表；`softmax`或`_softmax`把注意力分數轉成注意力權重；`gelu`對應FFN中的啟用函式。`mm`、`matmul`與`addmm`則涉及矩陣乘法，可能出現在注意力、FFN或輸出層。`key_averages`會把不同部位的同名運算合在一起，所以這張表先幫我們定位「哪種工作值得再查」，還不能唯一指出哪一層。本節先練習判讀這幾類列，不要求猜出每個底層名稱的唯一來源。

</details>

<details>
<summary>選讀：中位數、GPU同步與記憶體口徑</summary>

GPU收到工作後會在背景執行，程式送出指令就先往下走；計時前後都要等GPU把工作做完，這叫同步，否則量到的只是送出指令的時間。本章的GPU實測也先暖機，再同步量九次、取中位數。中位數先把時間由小到大排序：九次量測取第5個；若量測次數是偶數，則取中間兩個的平均，例如 `[1,2,3,20]` 的中位數是 `(2+3)/2=2.5`。一般平均數則把全部量測值相加再除以次數。訓練另略過前三步取更新中位數，不能把兩種時間混在同一欄。

本章各項實驗的起點記憶體、軟體與記憶體範圍集中在[T.8的效率量測方法](../training.md#選讀效率實驗的量測條件)，需要重跑或追查數字時再閱讀。

</details>

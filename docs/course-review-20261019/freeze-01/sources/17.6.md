## 17.6 少四個位元，精度與容器各改了什麼？

取33個從−1到1均勻排列的權重，用同一份材料分別做8-bit與4-bit對稱量化。[17.5](17.md#17.5)的`quantize_symmetric`以「最大絕對值÷正碼上限」當刻度，這裡最大絕對值是1，所以8-bit的刻度是1/127≈0.007874，4-bit是1/7≈0.142857。範圍相同，4-bit的刻度粗得多：相鄰兩個還原值相差約0.14。

```python
import torch
from tiny_perceptron.quantization import quantize_symmetric

w = torch.linspace(-1, 1, 33)
for bits in (8, 4):
    q, scale = quantize_symmetric(w, bits)
    restored = q.float() * scale
    error = (w - restored).abs()
    packed_bytes = (w.numel() * bits + 7) // 8
    print("bits", bits, "MAE", round(error.mean().item(), 6), "最大差", round(error.max().item(), 6))
    print("理想碼bytes", packed_bytes, "目前q容器bytes", q.numel() * q.element_size())
```

`linspace(-1, 1, 33)`在−1到1之間取33個等距的數，含兩端。第一行同時看MAE與最大差：8-bit約0.001909、0.003937，4-bit約0.034632、0.071429。兩個最大差都正好是半個刻度，例如0.142857÷2≈0.071429；看最大差，少數較糟的位置才不會被平均藏住。

第二行分開「碼理想上要幾byte」與「目前的容器佔幾byte」。8-bit的33個碼需33byte；4-bit共33×4＝132bit，要17byte，最後半個byte空著。`//`是整數除法，只留商、捨去餘數，例如`139 // 8`是17；先加7再整除，就是「不滿一個byte也算一個」。可是`quantize_symmetric`最後一步`.to(torch.int8)`讓兩次的q都是每個碼1byte，目前都佔33byte：限制數值範圍與真正打包是兩步，理想大小也還沒算入刻度。

較粗不代表每個值都更差：0與兩端在兩種位元下都精確；剛好等於某個4-bit還原值的數，4-bit也沒有誤差，可能比8-bit還準。單一張表的誤差，更不能直接當成文字答對率。

練習把程式的`w = torch.linspace(-1, 1, 33)`改成`w = torch.arange(-7, 8).float() / 7`。`torch.arange(-7, 8)`產生−7到7的15個整數（不含8），除以7之後，每個值都剛好是4-bit的還原值。先預測：4-bit的誤差幾乎是0，8-bit反而不是0。這個例外提醒我們要看數值分布，不能只看位元數。

## 3.3 同一個位置，為什麼要有查詢與匹配兩份表示？

一個位置既會問「我現在需要哪些線索」，又會成為別的位置可讀的資料。這兩份工作不必用同一套數字：**query 表示提出需求，key 表示提供匹配線索**，所以模型為它們準備不同的可調配方。

先用一個人工查找任務說明：每個位置要找自己缺少的線索，同時讓別的位置找到自己已有的線索。暫用兩格分別標記顏色與形狀；一個已有顏色、需要形狀的位置，key 可以是 `[1,0]`，query 則可以是 `[0,1]`。這些格子的含義是為示意指定的，真實模型的特徵不固定代表顏色或形狀。

下面先直接給轉換後的卡：兩個查詢與三個候選。所有查詢排成表 Q，所有 key 排成表 K。希望每個查詢各自比較全部三候選，得到兩列三欄的分數。

```python
import torch

q = torch.tensor([[1.0, 0.0], [0.0, 1.0]])
k = torch.tensor([[1.0, 0.0], [0.0, 1.0], [1.0, 1.0]])
scores = q @ k.T
print("Q", q.shape, "K轉置", k.T.shape)
print(scores)
assert scores.shape == (2, 3)
```

第一列 query `[1,0]` 得 `[1,0,1]`，第二列 `[0,1]` 得 `[0,1,1]`。第三個 key `[1,1]` 對兩種需求都得 1。輸出每列是一個問的人，每欄是一個可讀位置；`k.T` 只改排列以便相乘，不會把 key 改成 query。

用尺寸核對：Q 是 `[2,2]`，K 轉置是 `[2,3]`，共同的內側 2 是匹配特徵數，輸出 `[2,3]`。查詢數與候選數不必相等，但兩邊的匹配特徵數要相同。

為什麼不讓每個位置只用一份表示，同時當 query 與 key？用兩個位置試試：A 已有顏色、要找形狀；B 已有形狀、要找顏色。只用一份時，A 是 `[1,0]`、B 是 `[0,1]`，提問與被讀都用它。分開兩份時，key 仍記「已有什麼」，query 改記「要找什麼」；本例的 query 正好是把 key 的兩格對調。

```python
has = torch.tensor([[1.0, 0.0], [0.0, 1.0]])
need = torch.tensor([[0.0, 1.0], [1.0, 0.0]])
print("共用一份", has @ has.T)
print("分開兩份", need @ has.T)
```

兩張表的列都是提問的 A、B，欄是被讀的 A、B。共用一份得到 `[[1,0],[0,1]]`：A 跟自己最匹配，讀回的是它早已有的顏色。分開兩份得到 `[[0,1],[1,0]]`：A 找到有形狀的 B，B 找到有顏色的 A。一般來說，共用一份時 A 對 B 的分數一定等於 B 對 A 的分數；各位置向量長度相同時，跟自己的分數也最高（或並列最高）。「要找什麼」與「能提供什麼」常常不同，所以要兩份。

真實模型讓位置表示 X 各經過一套 Linear，得到 Q 與 K；這種特徵轉換也叫**投影**，這裡先理解為不同的加權配方。剛才從 `has` 得到 `need`，就像套用「交換兩格」的配方；key 則套用「保留原樣」的配方：同一份資訊經不同配方，扮演不同角色。**自注意力**的「自」是指：提出查詢、提供匹配線索，以及實際取回的內容，都由同一組位置產生。這裡先看 Q、K 的匹配部分；下一節會加入代表取回內容的第三份表示。位置來源相同，角色仍不同。

練習在第一段程式的 `k` 最後加一列 `[2.0, 0.0]`，先預測輸出變兩列四欄、新欄為 2、0，再把斷言改為 `(2, 4)` 核對。若再做 softmax，要沿每列的候選欄，讓每個問題自己分配讀取比例。

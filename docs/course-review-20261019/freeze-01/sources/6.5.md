## 6.5 換 tokenizer 後如何比較模型？

同一份原文，甲 tokenizer 切成 10 個 token，模型平均每個 token 的代價是 0.6；乙切成 5 個 token，平均 1.0。只看平均，甲比較低；可是兩者猜的是同一份原文，把每個 token 的代價加起來，甲是 10×0.6＝6，乙是 5×1.0＝5，乙反而比較低。切法一變，「一個 token」包含的原文就不一樣多，所以要回到共同的原文來比較。

先把要加總的東西講清楚。**有效目標**是有正確答案、而且這次要計分的位置。每個有效目標的代價，是模型給正確 token 的機率取負自然對數（[1.8](01.md#1.8)）；把全部有效目標的代價**加總**，叫 **NLL**（Negative Log-Likelihood，負對數似然），本課說 NLL 一律指這個加總，也寫成「總 NLL」。加總後再除以有效目標數，叫**平均 NLL**，就是 [5.2](05.md#5.2) 的 `total / count`。兩者各有用途：訓練時印出的代價（`masked_loss` 的回傳值），以及後面各章比較回答時寫的平均 NLL（例如 [17.14](17.md#17.14)），都是平均，回答「平均每個目標猜得多好」；換 tokenizer 比較時要用加總，因為接下來要把它改除以原文的 byte 數。

為什麼各位置的代價可以直接相加？整段原文的機率，是每個位置「在前文已知時」猜中下一個 token 的條件機率相乘（[1.5](01.md#1.5) 的 `p(看|貓)` 就是一個條件機率）。[W.4](../first-steps.md#W.4) 的例子要假設兩題獨立，才能把機率直接相乘；這裡每個機率都已經把前文放進條件裡，乘起來就是整段的機率，不需要假設獨立。例如已知 A，接著猜 B、C：整段的機率是「看到 A 時猜中 B 的機率」乘「看到 A、B 時猜中 C 的機率」；若兩項是 0.5 與 0.25，這段的機率就是 0.125。取負對數之後，乘積變成各位置代價的和：0.693＋1.386＝2.079，正好等於 0.125 的負對數。所以總 NLL 就是整段原文機率的負對數。

自然對數 ln（Python 的 `math.log` 也用這個底數）算出的代價，單位叫 nat。要換成以 2 為底的 bit，把總 NLL 除以 ln 2≈0.6931：例如機率 1/2 的代價是 ln 2≈0.6931 nat，除以 ln 2 正好是 1 bit。再除以原文的 UTF-8 byte 數，就得到 **BPB**（bits per byte），也就是平均每個原文 byte 花多少 bit 的代價：BPB＝總 NLL÷（原文 byte 數×ln 2）。下面「貓🙂」共 7 個 byte，兩個總 NLL 5 與 4 是手寫的例子，還不是模型量到的值。

```python
import math

raw = "貓🙂"
bytes_count = len(raw.encode("utf-8"))
for name, total_nll in [("示例A", 5.0), ("示例B", 4.0)]:
    bpb = total_nll / (bytes_count * math.log(2))
    print(name, "原文bytes", bytes_count, "BPB", bpb)
```

「貓」3 個 byte、🙂 4 個（[6.1](#6.1)），共 7 個。輸出 A 約 1.0305、B 約 0.8244：兩者的除數都是 7×0.6931≈4.852，B 的總 NLL 較小，BPB 也就較低。示例 A、B 只換了總 NLL，原文都是同樣的 7 個 byte，所以分母相同。下圖上方是共同的原文與它的 7 個 byte，下方兩條算式各用自己的總 NLL 除以同一個分母。

![不同拆分回到同一原文byte分母](../figures/rewrite-06-05-shared-denominator.svg)

真正量測時，先用各自的 tokenizer 編碼同一份驗證文件，再交給和它配對的模型預測。不能把甲的 ID 丟進乙的模型，同一個 ID 在兩張字表裡代表不同的片段。也不能只拿平均 NLL、不知道有效目標數就推算 BPB：總 NLL＝平均 NLL×有效目標數，少了目標數就算不出分子。

哪些位置算有效目標，兩邊也要一致。序列開頭的 **BOS**（Beginning of Sequence，開始標記）只當前文，不計分；為了把長短不同的序列排齊而補上的位置也不計分（[5.2](05.md#5.2) 的 -100）。每篇結尾的 **EOS**（End of Sequence，結束標記；第 1 章提過的結束標記，本章起寫作 EOS）表示這段到此結束。BOS、EOS 都是特殊 token，[6.6](#6.6) 會列出全部 8 個。本節的實驗把「猜中 EOS」也算進總 NLL，所以有效目標數＝原文的 token 數＋篇數；分母則只數原文的 UTF-8 byte，不含 EOS 與其他特殊 token。

長文放不進模型一次能讀的長度時，要切成幾段依序計分，每個 token 只能計一次。例如原文 A、B、C、D，模型一次讀三個位置：第一段讀 [A,B,C]，A 前面沒有東西可以拿來猜它，只當前文，計分的是 B（看 A 猜 B）與 C（看 A、B 猜 C）；第二段讀 [B,C,D]，B、C 已經計過，這次只當前文，只新增 D 的代價。如果 C 在兩段都計分，它就被算了兩次，總 NLL 會偏大。兩個模型的開頭、能讀的前文長度、EOS 算不算，都要用同一套規則。本節實驗的每篇片段都放得進一段，沒有這個問題（[6.8](#6.8) 的補充）。

現在看真實的量測。逐 byte 的 `ByteTokenizer` 與 512 項的 BPE 各自配一個模型（訓練設定見補充），在同一批 20 篇測試片段上評分；這 20 篇共 4,193 個原文 byte。這次實驗的實驗紀錄（存成 JSON 檔的完整結果，欄位說明見補充）給的是平均 NLL（nat）與有效目標數，下面換回總 NLL 與 BPB（bit）。程式裡的平均 NLL 取到小數第六位：若只取五位的 2.77947，印出的總 NLL 仍是 11,709.9，BPB 卻會算成 4.02905，和實驗紀錄的 4.02906 差在最後一位。

```python
import math

raw_bytes = 4193
for name, mean_nll, targets in [("逐byte", 2.779473, 4213), ("BPE", 3.987411, 2503)]:
    total_nll = mean_nll * targets
    bpb = total_nll / (raw_bytes * math.log(2))
    print(name, "平均NLL", mean_nll, "有效目標", targets, "總NLL", round(total_nll, 1), "BPB", round(bpb, 5))
```

逐 byte 的平均 NLL 約 2.77947，比 BPE 的 3.98741 低，看起來逐 byte 比較好。可是逐 byte 要猜 4,213 個目標（4,193 個 byte 加 20 個 EOS），BPE 只猜 2,503 個（2,483 個 token 加 20 個 EOS）：一個 BPE token 平均包含較多原文，每次猜的是比較大的一口。換回總 NLL，逐 byte 是 11,709.9，BPE 是 9,980.5；除以同一個 4,193×ln 2 之後，BPB 是 4.02906 對 3.43401，排名反過來，BPE 較低。這就是開頭甲、乙的情況。

這次比較固定的是原文曝光（兩個模型訓練時看了一樣多的原文）與更新次數，沒有固定參數數量、有效目標數與運算量；[6.4](#6.4) 已經看到 BPE 模型多了參數。所以它示範的是「換了切法之後怎麼讀數字」，不能據此說哪一種 tokenizer 比較好，也不能說 512 是最好的字表大小。

練習把第一段程式的 `[("示例A", 5.0), ("示例B", 4.0)]` 改成 `[("示例A", 10.0), ("示例B", 8.0)]`，先預測兩個 BPB 都翻倍（約 2.0610 與 1.6488）、排序不變，再執行核對。改回後，把 `raw = "貓🙂"` 改成 `raw = "貓🙂貓🙂"`（14 個 byte），總 NLL 保持 5 與 4，數值會減半（約 0.5152 與 0.4122）。這一步只是示範分母的作用；真實模型換了文本，總 NLL 一定要重新量，不能沿用舊數字。

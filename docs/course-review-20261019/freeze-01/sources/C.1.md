## C.1 寫出中間步驟能幫忙嗎？

2+3 可以直接答「5」，也可以寫「從2開始數三次：3、4、5，所以是5。」第二份讓讀的人能核對方法，模型接著往下生成時，也讀得到自己剛寫下的中間結果；但它長得多，而且只要一步寫錯，結論也可能跟著錯。所以先把「回答寫成什麼樣子」和「模型會不會算」分開，不因為解釋比較長，就認定它比較可靠。

先看兩種寫法差多少長度。下面用第 6 章的 `ByteTokenizer`（實作見 [6.6](06.md#6.6)）把兩份人工寫好的回答編成 token，再數個數：

```python
from tiny_perceptron.data import ByteTokenizer

tokenizer = ByteTokenizer()
examples = [
    {"question": "2+3=?", "answer": "5"},
    {"question": "2+3=?", "answer": "從2開始數三次：3、4、5，所以是5。"},
]
for example in examples:
    ids = tokenizer.encode(example["answer"])
    print(example["question"], example["answer"], "回答token數", len(ids))
```

`tokenizer.encode` 把文字按 UTF-8 byte 編號，每個 byte 一個 token。數字是 ASCII，各占 1 byte；中文字與全形標點各占 3 byte。所以短答是 1 個 token，步驟版是 47 個：14 個中文字與全形標點共 42 byte，再加 5 個數字。這裡只編回答本身，沒有加 [7.1](07.md#7.1) 的角色標記與 EOS；換一種 tokenizer，長度也會不同。程式只數長度，沒有訓練模型，也沒有生成回答。

回答變長之後，答對的比例會不會也變？要比較，就得讓兩邊只差在回答形式。本單元的算術實驗這樣安排：題目都是 `(a+b)+c=?`，a、b、c 是 0 到 5 的整數。兩個一樣大的小型語言模型從同一份隨機參數出發，用同樣 167 道訓練題各更新 900 次，每次抽到的 24 道題也相同。差別只在示範回答：**短答支線**只學最後的整數，例如 `(1+2)+3=?` 學 `6`；**步驟支線**學 `1+2=3;3+3=6;answer=6`，每一步都能驗算。兩支都照 [7.1](07.md#7.1) 的 SFT 方式訓練，問題放在輸入裡，只有示範回答的位置計入代價；不同的是它們從隨機參數開始，沒有先預訓練。

測試用另外 24 道題。同一組三個數字的所有排列，例如 `(1+2)+3` 和 `(3+2)+1`，算同一個家族（[5.12](05.md#5.12)），整個家族只放在訓練題、驗證題、測試題其中一邊，所以測試題的數字組合在訓練時一次也沒出現過。每題只讓模型生成一份回答時，同樣這 24 道測試題，步驟支線答對 11 題（11/24），短答支線只答對 1 題（1/24）。

這個差距不能全算在「寫步驟」頭上，因為兩支學到的份量不同。訓練時計入代價的位置叫有效目標（[7.3](07.md#7.3)），這裡就是示範回答的每個 token 加上 EOS。900 次更新下來，步驟支線的有效目標共 466,322 個，短答支線只有 48,803 個，約 9.6 倍（466,322 ÷ 48,803 ≈ 9.56）。題數與更新次數相同，不代表訓練工作量相同；作答時，步驟支線每份最多也能寫 48 個 token，短答支線只能寫 8 個。

還要記得：步驟只是模型輸出的文字，不是模型內部計算的完整紀錄。它可以讓人查核，也可能寫得流暢卻是錯的。下一節看一份最後答對、前一步卻錯的回答，說明為什麼每一部分都要另外驗。

練習：把程式第二筆的 `"answer": "從2開始數三次：3、4、5，所以是5。"` 改成 `"answer": "2+3=5"`。先預測：這五個字元都是 ASCII，應該編成 5 個 token；執行後，第二行最後的數字應是 5。回答變短只改了這份材料的長度，不能說明模型更會算或更不會算。

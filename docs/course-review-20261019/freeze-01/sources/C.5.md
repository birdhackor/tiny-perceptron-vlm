## C.5 花更多計算值得嗎？

同樣生成 80 個 token，可以寫一份 80 個 token 的答案，也可以寫四份各 20 個 token 的答案。若每份候選還要交給模型另外寫 5 個 token 的判斷（例如寫 `pass` 或 `fail`：用 C.1 的 `ByteTokenizer`，4 個 ASCII 字元各 1 個 token，加上 EOS 正好 5 個），前者總共 85 個 token，後者 100 個。多出來的是選擇與驗證的成本；候選多，不等於免費變好。

```python
plans = [
    {"candidates": 1, "answer_tokens_each": 80},
    {"candidates": 4, "answer_tokens_each": 20},
]
verify_tokens_each = 5
for plan in plans:
    k = plan["candidates"]
    generated = k * plan["answer_tokens_each"]
    verified = k * verify_tokens_each
    print("候選", k, "生成", generated, "驗證", verified, "總token", generated + verified)
```

`plans` 列出兩種安排，每項記候選份數與每份答案的長度；`verify_tokens_each` 是模型判斷每份候選要另外寫的 token 數。迴圈裡的 `k` 和 [C.3](0C.md#C.3) 一樣是每題候選份數：生成 token 是 `k` 乘每份長度，驗證 token 是 `k` 乘 5。兩種安排生成的都是 80，驗證分別是 5 與 20，總數是 85 與 100。這只是把人工設定的預算相加，沒有生成、計時或量正確率。

驗證不一定要交給模型。像 [C.4](0C.md#C.4) 那樣用算術程式驗算，不會新增任何模型 token，但仍要花 CPU 時間；token 數和秒數是不同單位，不能直接相加。

寫長步驟、多抽候選、做驗證，這類在模型作答時多花的計算，統稱**回答當下的計算（test-time compute）**；模型參數可以完全不變，只改作答流程。比較時先說清預算：固定總 token 時，候選越多，每份能寫的就越短；增加預算時，要明說總成本變了。接著分開看三件事：「最終正確」是最後交出的答案答對；「集合命中」是候選裡至少一份答對（[C.3](0C.md#C.3)）；「選錯」是集合命中了，交出的卻是錯答案（[C.4](0C.md#C.4)）。

實驗裡的步驟支線就是增加預算的例子。每題 1 份候選時，24 道測試題共生成 512 個 token；每題 8 份時是 4,132 個，約 8 倍（4,132 ÷ 512 ≈ 8.07）。集合命中從 11 題升到 14 題，多數決的最終正確卻只從 11 題升到 12 題。這說明要先講預算、再談收益；它沒有判定等預算下哪種安排最好。

token 數也不是秒數。長答案得一個 token 接一個 token 生成，後一個要等前一個算完；多份候選卻可以排成一批（batch）一起算。生成時還能把前面位置算過的結果存起來重用，省掉重算；這到第 16 章（[16.3](16.md#16.3)）才講，這裡只需要知道：這些做法都會影響秒數，所以秒數和 token 數不一定成比例。實驗裡的短答支線就是如此：每題 8 份候選共生成 400 個 token、合計 0.120 秒，每題 1 份只生成 51 個，卻花了 0.239 秒；每個數字只量一次，會受執行先後等條件影響，不能當成穩定的速度比較。

使用者感受到的等待，要從收到問題算到交出最後文字為止：把問題整理成輸入 ID、生成、把生成的 ID 解碼回文字、投票或驗算，全都要算進去。只量生成那一段，不能當成完整的回應時間。第一次載入模型與訓練模型是另外的成本，不算進每次回答的等待。

練習：把 `verify_tokens_each = 5` 改成 `verify_tokens_each = 0`，代表改用程式驗算、不讓模型寫判斷。先預測：兩行的驗證都變成 0，總 token 都是 80。token 預算打平了，但程式驗算的 CPU 時間並沒有出現在這張表裡，四份候選也不因此一定更準。

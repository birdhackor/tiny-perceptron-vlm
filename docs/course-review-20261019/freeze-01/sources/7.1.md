## 7.1 對話怎麼表示？

一位使用者問「1+1=?」，助手回答「2」。同樣兩段文字，若丟掉誰問誰答，模型只看到一串接續的字；先把每段的角色與內容分欄，再串成有邊界的序列，才能明確要求它在問題之後回答。

一筆對話是一份消息清單，每條消息是一個字典：`role` 記 user（使用者）或 assistant（助手），`content` 記原文字。tokenizer 沿用 [6.6](06.md#6.6) 的 ByteTokenizer：普通內容每個 byte 是一個 token；BOS（開始標記）、EOS（結束標記）和每種角色，各有一個特殊 token。下面把這份問答轉成模型輸入 X 與答案標籤 Y。

```python
from tiny_perceptron.data import IGNORE, ByteTokenizer, render_chat

messages = [
    {"role": "user", "content": "1+1=?"},
    {"role": "assistant", "content": "2"},
]
tok = ByteTokenizer()
x, y = render_chat(messages, tok)
print("模型輸入X", x.tolist())
print("答案標籤Y", y.tolist())
print("IGNORE是", IGNORE, "；有效目標", y[y != IGNORE].tolist())
```

X 是 `[1,3,57,51,57,69,71,2,4,58]`：1 是 BOS，3 是 user，57、51、57、69、71 是「1+1=?」五個字元的 byte 各加 8；接著 2 是 user 段的 EOS，4 是 assistant，最後的 58 是字元「2」（byte 50 加 8）。Y 也有 10 個位置，前八個是 −100，最後是 58 與 2。Y 的每個位置是一個**目標**：第 i 個目標，是 X 第 i 個位置要猜的下一項。所以 X 讀到 assistant（4）的位置要猜 58，讀到 58 的位置要猜 EOS（2）。

−100 是函式庫裡名叫 `IGNORE` 的常數，表示「這個位置不計代價」：模型在那裡照樣算出下一項的分數，但猜得好不好都不加進代價（loss）。它只出現在 Y，不是可以拿去查表的 token ID。整串 Y 也叫 labels；不是 −100 的目標叫**有效目標**。`y[y != IGNORE]` 用真／假條件挑出有效目標，得到 `[58, 2]`：58 是字元「2」，2 是 EOS 的 ID，也就是要求模型寫出「2」之後以 EOS 結束。user 的問題仍完整留在 X 裡，供後面的位置透過注意力讀取，只是不當成要模仿的答案。

這些數字是怎麼排出來的？下面是 `render_chat` 的原始碼：

```python
# 節錄自 tiny_perceptron/data.py：render_chat
def render_chat(messages, tokenizer=None):
    """邊界由角色欄位建立；使用者文字不會被解析為特殊 token。"""
    tok = tokenizer or ByteTokenizer()
    ids, targets = [tok.bos_id], [IGNORE]
    roles = {"user": tok.user_id, "assistant": tok.assistant_id, "system": tok.system_id}
    for message in messages:
        role = message["role"]
        if role not in roles or not isinstance(message["content"], str):
            raise ValueError("role 必須是 user/assistant/system，content 必須是文字")
        content = tok.encode(message["content"]) + [tok.eos_id]
        ids += [roles[role]] + content
        targets += [IGNORE] + (content if role == "assistant" else [IGNORE] * len(content))
    if not any(t != IGNORE for t in targets):
        raise ValueError("這筆對話没有可監督的 assistant 答案")
    return torch.tensor(ids[:-1]), torch.tensor(targets[1:])
```

函式一開始的 `tok = tokenizer or ByteTokenizer()` 處理沒有傳 tokenizer 的情況：這時參數是預設的 `None`，`or` 便取右邊，新建一個 ByteTokenizer。接著 `ids, targets = [tok.bos_id], [IGNORE]` 同時開兩份清單：`ids` 是完整序列，從 BOS 開始；`targets` 和 `ids` 逐項對應，記錄每個 token 要不要當成答案。BOS 不是答案，所以放 IGNORE。`roles` 把角色名稱對到特殊 token 的 ID。

迴圈逐條處理消息。`if` 先檢查角色是否合法、內容是不是文字：`isinstance(值, str)` 問「這個值是不是字串」；不符合就執行 `raise ValueError(...)`，主動丟出錯誤並停止，訊息說明哪裡不對。變數 `content` 和消息裡的 `"content"` 欄位同名，裝的卻是 ID：文字編碼後再接一個 EOS，標出這段話在哪裡結束。`ids += [roles[role]] + content` 把角色 token、內容與 EOS 接到 `ids` 尾端（`+=` 是「接在後面」）；角色 token 由 `role` 欄位決定，不是從內容文字猜的，這正是 6.6 說的邊界。`targets` 同步接上同樣長度的一段：角色 token 本身不是答案，放 IGNORE；後面括號裡的 `A if 條件 else B` 在條件成立時取 A、否則取 B，所以 assistant 的內容與 EOS 原樣抄進 `targets`，其他角色則換成同樣多個 IGNORE（`[IGNORE] * len(content)` 是把同一項重複 `len(content)` 次的清單）。

最後兩步。`any(...)` 只要有一項成立就是 True；若 `targets` 全是 IGNORE，這筆對話沒有可學的答案，直接報錯。`return` 把 `ids` 去掉最後一項當輸入、`targets` 去掉第一項當目標，這就是 [4.7](04.md#4.7) 的移一位。`targets` 原本和完整序列逐項對應，移位之後，Y 的第 i 個位置才變成「X 第 i 個位置的下一項，以及它要不要計分」。

有了這份格式，就能拿正確的助手回答當示範，通常是繼續訓練一個已經學會續寫文字的語言模型（像第 4–6 章那樣逐 token 預測的模型），這叫**監督式微調**（Supervised Fine-Tuning，SFT）。這種事先訓練好、拿來當起點的模型從哪裡來，[7.11](#7.11) 與 [7.17](#7.17) 會說明；本節只處理資料怎麼排。模型仍是預測下一個 token，改變的是教材和哪些位置計分：文章教「原文接什麼」，問答教「這個問題應答什麼」。多輪對話也按消息順序逐條加上角色，不能靠內容裡的字樣猜誰在說話。接下來 [7.2](#7.2) 看推論時輸入停在哪裡，[7.3](#7.3)、[7.4](#7.4) 再細看哪些位置計分、回答的第一個 token 由誰預測。

練習只把第一段程式的問題改成 `"2+1=?"`。先預測：X 的長度與角色、邊界的位置都不變，有效目標仍是 `[58, 2]`；只有 X 位置 2 的 ID 從 57（字元「1」）變成 58（字元「2」）。再執行核對。這裡故意讓答案仍是 2，是為了只看格式的變化；若要把它當成正確的算術訓練例，回答必須一起改成 3，不能讓資料默默帶著錯答案。

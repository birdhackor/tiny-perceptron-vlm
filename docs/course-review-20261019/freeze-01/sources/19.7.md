## 19.7 計算器算對，為什麼助理還可能答錯？

請助理「用計算器算出26×16。」公開 MoE 權重在 CPU 上先生成了乘法請求，程式真正算出416，同一模型讀回結果後再生成「結果是416。」這題需要三個動作連續完成：提出正確請求、執行工具、根據返回結果作答。

![實際公開 CPU 工具例：同一模型第一次生成26乘16的 JSON，計算器真執行返回416，再由同一模型第二次生成「結果是416。」](../figures/p6-19-modal-tool.svg)

第一份輸出是 JSON：以固定欄位記錄工具名、運算與兩個整數，讓程式可以明確讀取。工具請求怎麼寫、怎麼解析成有效呼叫、結果怎麼回到對話，分別見[B.1](0B.md#B.1)、[B.2](0B.md#B.2)、[B.3](0B.md#B.3)。這個計算器只支援0–99非負整數的加、減、乘。system 訊息說明一般格式與範圍，模型依 system 的工具條件與學過的示範，從這題選出 `multiply`、`26`、`16`；程式沒有先從問題抽出正確算式，替模型補一份呼叫。選擇工具是學習條件與作答規則的結果，不能解讀成模型已能可靠判斷自己算得對不對。

| 往返位置 | 這次留下的實際內容 |
| --- | --- |
| 第一次模型生成 | `{"tool":"calculator","operation":"multiply","a":26,"b":16}` |
| 程式執行後的返回值 | `{"tool":"calculator","ok":true,"result":416}` |
| 回填到歷史 | 一則 assistant 呼叫，接一則 tool 結果訊息（[B.3](0B.md#B.3)） |
| 同一模型第二次生成 | `結果是416。` |

執行器先檢查欄位、運算種類和整數範圍，再進行乘法；它不把模型文字交給 Python 的 `eval`。合法也不一定正確：若模型把26抄成25，請求仍可能合法，工具也會正確計算25×16，整個任務卻已偏離原題。因此「可執行」與「參數符合問題」必須分開判定。

下面在 CPU 上展示並重做解析與執行；`raw` 是我們手工提供的字串，程式沒有呼叫神經模型。函式庫的 `parse_tool_call` 與 `execute_tool_call` 會用到 tools.py 開頭的幾個常數與小工具，先把它們取來：

```python
import json

from tiny_perceptron.selftrained.tools import CALL_KEYS, MAX_CALL_CHARACTERS, ToolCallError
from tiny_perceptron.selftrained.tools import CalculatorCall, _unique_object, _validate_call
```

`MAX_CALL_CHARACTERS` 是 256，請求最多 256 個字元；`CALL_KEYS` 是 `tool`、`operation`、`a`、`b` 四個欄位名；`ToolCallError` 是請求不合法時丟出的錯誤種類；`CalculatorCall` 是只裝運算名與兩個整數的小資料類別，它的 `to_dict()` 會寫回字典。名稱前加底線的 `_unique_object`（同一欄位出現兩次就報錯）與 `_validate_call`（檢查運算種類與 0–99 的範圍）是 tools.py 內部用的小工具。這些名字要先取來再貼函式，因為函式標頭的型別註記 `-> CalculatorCall` 在定義函式時就會用到。

```python
# 節錄自 tiny_perceptron/selftrained/tools.py：parse_tool_call、execute_tool_call
def parse_tool_call(text: str) -> CalculatorCall:
    """Require exactly four unique JSON keys and bounded integer operands."""
    if not isinstance(text, str) or len(text) > MAX_CALL_CHARACTERS:
        raise ToolCallError("call must be a bounded string")
    try:
        value = json.loads(text, object_pairs_hook=_unique_object)
    except (json.JSONDecodeError, RecursionError) as exc:
        raise ToolCallError("invalid JSON") from exc
    if not isinstance(value, dict) or set(value) != CALL_KEYS:
        raise ToolCallError("call must contain exactly tool, operation, a, b")
    if value["tool"] != "calculator":
        raise ToolCallError("tool is not permitted")
    return _validate_call(CalculatorCall(value["operation"], value["a"], value["b"]))


def execute_tool_call(call: CalculatorCall | str) -> dict:
    """Execute arithmetic itself; operands alone determine the integer result."""
    if isinstance(call, str):
        call = parse_tool_call(call)
    if not isinstance(call, CalculatorCall):
        raise ToolCallError("executor requires a validated calculator call")
    call = _validate_call(call)
    if call.operation == "add":
        result = call.a + call.b
    elif call.operation == "subtract":
        result = call.a - call.b
    else:
        result = call.a * call.b
    return {"tool": "calculator", "ok": True, "result": result}
```

- `text: str` 與 `-> CalculatorCall` 是型別註記，說明輸入是字串、回傳 `CalculatorCall`，不影響計算。`raise` 丟出錯誤並停止這個函式。
- 第一個 `if` 拒絕不是字串或超過 256 字元的輸入。
- `try`／`except`：`try` 裡的 `json.loads` 把文字解析成字典；文字不是合法 JSON 時，Python 會丟出 `JSONDecodeError`，`except` 接住它，改丟出 `ToolCallError("invalid JSON")`。`object_pairs_hook=_unique_object` 讓同一個欄位出現兩次時也報錯，不會默默只留後一個值。
- `set(value) != CALL_KEYS`：欄位必須恰好是那四個，多一個、少一個都不行；`value["tool"]` 還必須是 `"calculator"`。
- 最後用三個欄位建 `CalculatorCall`，交給 `_validate_call` 檢查運算是 add、subtract、multiply 之一，兩個數都是 0–99 的整數。
- `execute_tool_call` 收到字串就先解析；確認是 `CalculatorCall` 後再檢查一次，然後由 Python 自己做加、減或乘。回傳的字典只有 `tool`、`ok` 和 `result`，沒有任何中文答句，最後那句話仍由模型生成。

```python
raw = '{"tool":"calculator","operation":"multiply","a":26,"b":16}'
call = parse_tool_call(raw)
print("合法請求", call.to_dict())
print("真執行結果", execute_tool_call(call))
print("抄錯但合法", execute_tool_call(raw.replace("26", "25")))
try:
    parse_tool_call(raw.replace("multiply", "divide"))
except ToolCallError as error:
    print("拒絕", error)
```

第一行是解析後的合法請求，第二行的 `result` 為 416。第三行用 `replace` 把字串裡的 `26` 換成 `25`：請求一樣合法，執行器也正確算出 400，但已不是原題的答案。最後一段用 `try`／`except` 試一個不支援的運算 `divide`，印出 `拒絕 operation is not permitted`。這證明請求能被解析並真正執行，沒有證明模型會生成它，也還沒有第二次模型回答。上方公開紀錄則保存了兩次真正生成，兩次都正常產生 EOS；第二次的輸入包含第一次的原始請求與真 tool 訊息，所以416是模型讀回後生成的答案。

工具往返要同時查：是否需要工具、是否選對工具與參數、是否真正執行、是否根據結果回答並正常結束。工具未開或缺參數的題目，要學會說明條件或詢問。另可在測試回放中替換返回值，查回答是否跟著變；這檢查讀回依賴，正常成功率仍應使用真正計算器結果。

這個26×16是挑選出的已知驗證成功例。一題真往返證明流程能運作，不能證明未見算式與問法穩定：公開 MoE 在 276 道真正計算器往返的測試題上是 0／276，[19.12](19.md#19.12)列出失敗發生在哪一步。這也回答了本節的問題：計算器只保證按收到的參數計算，參數選擇與最後文字都仍由模型負責。

練習把第三段程式 `raw = …` 裡的 `"a":26` 改成 `"a":100`，先預測：接著的 `call = parse_tool_call(raw)` 就會停下，錯誤訊息是 `operands must be integers from 0 to 99`；再執行核對。

## 10.11 圖找文和文找圖，為什麼要分開算？

同一張配對分數表可以從兩個方向查：拿一張圖找文字時，在那張圖的橫列裡選候選；拿一段文字找圖時，在那段文字的直欄裡選候選。先看手設表 `[[2.0,0.1],[0.4,1.8]]`：橫列代表圖，直欄代表文字，正確配對仍在對角線上。

```python
import torch
from torch.nn import functional as F

scores = torch.tensor([[2.0, 0.1], [0.4, 1.8]], requires_grad=True)
labels = torch.arange(2)
image_to_text = F.cross_entropy(scores, labels)
text_to_image = F.cross_entropy(scores.T, labels)
loss = (image_to_text + text_to_image) / 2
loss.backward()
print("圖找文", round(image_to_text.item(), 4))
print("文找圖", round(text_to_image.item(), 4))
print("平均", round(loss.item(), 4))
print("梯度符號", torch.sign(scores.grad).tolist())
```

原表算「圖找文」：每列一題，從兩段文字中選。轉置 `scores.T` 讓文字變成橫列、圖變成直欄，同樣的 `cross_entropy` 就變成算「文找圖」。兩個交叉熵約 0.1799、0.1758，平均約 0.1779；梯度符號是 `[[-1,1],[1,-1]]`。同一格分數同時參與兩個方向的候選競爭，收到的梯度合併了兩個方向的影響。

兩項不必相等：圖找文比較同一列的 2.0 對 0.1、0.4 對 1.8；文找圖比較同一欄的 2.0 對 0.4、0.1 對 1.8，差距不同。如果表剛好沿對角線對稱，例如 [10.10](10.md#10.10) 的 `[[2,0],[0,2]]`，兩個方向會算出同樣的值，容易誤以為圖找文和文找圖是同一個式子算了兩次；本節特地用不對稱的表，讓差別看得見。

雙向平均表示兩種查詢都重要，但不保證效果一定勝過單向。本課的圖文配對小實驗用紅、綠、藍各配圓形、方形，共六種描述；訓練題 18 張圖，驗證題和測試題各 6 張，圖形放在訓練沒用過的位置，但顏色和形狀的組合仍是已知的六種。實驗訓練了兩個版本，各更新 250 步：只算圖找文的「單向版」，和本節做法的「雙向平均版」。測試題上，兩個版本、兩個方向都是 6/6；驗證題上，兩個版本的圖找文都是 5/6（藍圓被配成藍方），文找圖都是 6/6。這次沒有觀察到雙向版答對更多；結果只能支持這個有限的六選一配對，不能當成大型檢索的比較。完整數字在[實驗紀錄（JSON）](../../docs/course-experiments/results/contrastive.json)，這是機器可讀的完整結果：`results.variants` 底下的 `one_way` 是單向版、`two_way` 是雙向平均版，各看 `validation` 與 `test` 的 `image_to_text_accuracy`（圖找文）和 `text_to_image_accuracy`（文找圖）；這兩欄記的是答對比例，0.8333 就是 5/6。

檢索是從現成的候選中選一個，生成描述則要逐 token 寫出文字。兩者可以共用特徵，能力證據仍要分開。同一段描述可配多張圖時，也要沿用 [10.10](10.md#10.10) 的多正確配對處理。

練習把程式的 `loss = (image_to_text + text_to_image) / 2` 改成 `loss = (2 * image_to_text + text_to_image) / 3`，先預測代價。預期約 (2×0.1799＋0.1758)÷3≈0.1785，比 0.1779 更靠近圖找文的 0.1799；`scores.grad` 仍是 2×2，四格的正負號不變。改的是兩個方向的重視程度，沒有增加新的圖片資訊。

## 16.3 生成時重算了什麼？

模型讀完 `[1,2,3]`，再加入ID4，最直接的做法是把 `[1,2,3,4]`整段重新送入。可是前面三個位置的Key、Value不是已經算過了嗎？因果注意力只允許每個位置讀到自己和過去，因此加入未來的ID4不會改變前面三個位置在各層的特徵。每個位置的K、V又是由它自己的特徵經Linear投影算出（[3.3](03.md#3.3)、[3.4](03.md#3.4)），特徵不變，K、V也不變；所以可以保留它們各層的K、V，下次只算新位置。本節要先核對這樣重用是否保持結果相同，再談省時間。

沿用[prefill/decode](16.md#16.2)的分工，這次把例子縮成三個前文位置，再接第四個ID。cache保存每層注意力裡的Key與Value，沒有把完整回答存成答案，也沒有免去新位置的所有工作。新token仍要查表、算Query與自己的K/V、對所有過去位置做注意力，再經過[FFN前饋網路](04.md#4.4)，也就是對每個位置各自轉換特徵的兩層網路；省掉的是舊位置重複的投影與特徵處理。

圖中K、V後面的0、1、2、3是位置編號，並非本例的輸入ID。最上列是已保存的位置0、1、2；中間只算新位置3的K/V，再接到快取尾端，快取長度變成4。最下面的新Query讀這四個位置，不能只比較剛加入的那一個。

![保存位置0至2的K與V，加入新位置3](../figures/rewrite-16-cache-append.svg)

```python
import torch
from tiny_perceptron.model import TinyLM, ModelConfig

torch.manual_seed(0)
model = TinyLM(ModelConfig(width=8)).eval()
ids = torch.tensor([[1, 2, 3, 4]])
with torch.no_grad():
    full = model(ids)["logits"][:, -1]
    prefix = model(ids[:, :3])
    step = model(ids[:, 3:], cache=prefix["cache"])
    cached = step["logits"][:, 0]
error = (full - cached).abs().max().item()
print("兩路分數形狀", tuple(full.shape), tuple(cached.shape))
print("最大差異", error)
assert torch.allclose(full, cached, atol=1e-6)
```

`ids[:,:3]`取前三個ID，`ids[:,3:]`只取第四個。重算整段時最後位置索引為-1；快取路徑只有新位置，所以取索引0。兩者都是用讀完ID4後的狀態預測下一個token，不能拿prefill最後位置的分數與它比較，因為那是只讀到ID3時的預測。兩路形狀應同為 `(1,264)`，最大差異通常為零或很小的浮點尾數，assert要求接近到指定容忍範圍。

位置編號也必須接得上。新位置不能重新當成位置0：`TinyLM`先用`offset = 0 if cache is None else cache[0][0].shape[2]`讀出cache已保存幾個位置，也就是第一層K的第2軸長度；再用`positions = torch.arange(offset, offset + t, device=x.device)`替這次新送入的t個位置編號，本例因此自動從3開始。每層的`CausalAttention`（[3.7](03.md#3.7)的精簡版省略了這段）則用`torch.cat((cache[0], k), 2)`把新K接在舊K之後，V也一樣，2就是位置軸。若忘記這個offset（位移），即使K/V形狀正常，新位置也會被當成位置0，結果可能不同。若改了前文、參數或位置規則，舊cache通常要重建，不能繼續沿用。

多段輸入放在同一批一起處理叫batch。若一段ID為 `[1,2,3]`，另一段為 `[4,5]`，為湊成同長度的表，第二段可補成 `[4,5,PAD]`；padding是補齊的動作，PAD是專用佔位ID，第二段的有效長度仍是2，補上的位置不是真實前文。本課的小實作沒有處理同batch內這種不同有效長度的快取：有cache時若又傳入標示PAD的`valid`或[16.5](16.md#16.5)的`segments`，`CausalAttention`會直接報錯，而不是默默算錯。所以本節固定長度的例子不能保證這種輸入也正確。

練習分兩步，每步改完都從頭執行。第一步把 `ids = torch.tensor([[1, 2, 3, 4]])` 改成 `[[1, 2, 3, 5]]`：前三個ID沒變，快取對應的仍是同一段前文，先預測兩路仍接近、assert通過。第二步改回原本的ids，只把重算整段那一行改成 `full = model(torch.tensor([[9, 2, 3, 4]]))["logits"][:, -1]`，快取仍用 `[1,2,3]` 建立：先預測最大差異明顯變大（本例約0.064）、assert失敗。第一個ID不同，舊快取就不再對應同一段前文，不能沿用；本例只有一層，實際改變的是第一個位置的K、V。區分這兩種改動，你就知道快取保存的是哪一段計算，而非一份對所有問題都通用的答案。

原始ID中多次出現EOS（ID 2），是速度測試刻意不提早停止的結果。把ID轉回文字時，EOS這類特殊token不會顯示，所以解碼後的 `eueeuare` 與 `eredquare`（兩個模型在這個提示下生成的無意義字串）看不出EOS出現在哪裡。實驗紀錄因此另外保留整串ID：`results.models.mha.cache`與`results.models.gqa.cache`底下的`generated_ids_full`（整段重算）與`generated_ids_cached`（快取路徑）兩欄，不能只看解碼文字一樣就宣布序列相同。若兩個最高分候選非常接近，微小浮點差也可能改變選擇，因此還要同時看分數誤差（同一處的`per_step_logit_max_error`欄，逐步記下的最高logit差）與實際ID。

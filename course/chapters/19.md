# 第 19 章：三個自行訓練的成品與 Auto 整合

前面學過文字模型、感知入口、機率判斷與循環深度。現在沿三條路線做可使用的成品：既有 MoE 多模態助理、Looped 文字解題器，以及 Jev 式機率判斷服務。本章依節號順讀：19.1–19.12完成既有助理的資料、訓練與驗收；19.13對照三個成品的用途，再由19.14–19.20讀共同資料、兩個新增產品與Auto整合。

第一條路使用已訓練並公開權重的 **V2 有限多模態助理**。文字核心、三個感知入口及它們的接頭，都由本專案從零訓練，沒有沿用既有預訓練神經權重；圖片、字型與錄音則取自明確列出的資料來源。先看它真正怎麼回答，再拆開模型、資料與訓練流程，最後在[19.12](19.md#19.12)核對整份考卷的能力與不足。另兩個成品也已完成GPU訓練與固定最後測試；從[19.13](19.md#19.13)看用途，再到19.20核對成績與失敗。第20章再把視野擴到成熟模型的應用。

## 19.1 一個成品，為什麼要試好幾種問題？

先給助理兩段條件：「接下來請用兩點回答」，以及「App錯誤訊息一直重複出現」。第一句決定格式，第二句決定內容。這份公開 MoE 權重在 CPU 上實際生成了下面的回答，並產生表示回答結束的 EOS 編號。

| 交給模型的材料 | 內容 |
| --- | --- |
| 先前的 user 要求 | 接下來請用兩點回答。 |
| 先前的 assistant 確認 | 好，接下來用兩點回答。 |
| 目前的 user 問題 | App錯誤訊息一直重複出現。 |
| 模型這次的回答 | 1. 先檢查網路並重新啟動App。<br>2. 仍失敗再詢問官方客服。 |

這裡的「先前確認」是公開示範檔提供的對話歷史；最後兩點才是本次模型生成的內容。它同時用到了當前問題和先前格式。沒有圖片或聲音的這一題，先讓我們確認共同的文字入口與回答流程能運作。

<details>
<summary>操作：用自己的 CPU 重做這個公開權重例子</summary>

先安裝 [Git](https://git-scm.com/downloads) 與 [uv](https://docs.astral.sh/uv/getting-started/installation/)。第一次取得本章專案，可從終端機執行：

```bash
cd tiny-perceptron-vlm

```

已有專案的讀者從 repository 根目錄執行最後一行即可。這個純文字例子不需解開圖片與錄音資料包。接著執行：

```bash
uv run --frozen --extra cpu --extra selftrained python scripts/selftrained/chat.py \
  --model-dir outputs/selftrained-v2/public/moe-joint \
  --asset-dir outputs/selftrained-v2/data \
  --repo birdhackor/tiny-perceptron-course-models \
  --revision 979cdfacc588ad0536f1c64fff96f264571cf054 \
  --prefix selftrained/v2/moe-joint \
  --manifest-sha256 f27856892b0c46ca81ba43bfadf7051ed6bd31d848e4868a05147e5799df1e5e \
  --messages docs/selftrained/examples/v2/text.messages.json \
  --task text --device cpu --max-new-tokens 128 --threads 2
```

程式第一次會匿名取得固定版本的四份公開檔案，核對 SHA-256 指紋後讀入權重，再依訊息檔真正生成回答；後續可重用下載的檔案。這是推論，不會更新模型。輸出為 JSON，先找 `answer`，應為上表的兩點；再看 `generations[0].eos`，應為 `true`。文字中的 `\n` 表示換行。`model.selected_step` 則指出發布的權重取自這段訓練的第1,000步。

這份訊息檔的 system 設定只說明有限助理的任務，沒有放入當前問題的答案。若要看完整輸入，可直接打開[示範訊息檔](../../docs/selftrained/examples/v2/text.messages.json)。其他圖片、讀字、語音與工具的 CPU 命令及資料準備見[公開操作頁](../../docs/selftrained/v2-public-cpu-commands.md)。

</details>

接著把同一核心用在別的材料。商品圖會先經過商品入口，指定字卡經過讀字入口，錄音經過聲音入口；入口把內容變成核心可讀的向量，放進它的輸入序列。下圖的箭頭都朝向同一核心，表示它們最後使用同一份文字權重來回答。

![成品資料流示意：文字與歷史直接進入共同核心；商品、指定字卡及聲音先經過各自入口，再由同一核心回答或提出工具請求。](../figures/p6-19-start-core.svg)

一個文字例子只走了一條路。整合檢查還要改材料、改問題和改歷史，逐項看答案是否跟著條件改變。

| 本章材料 | 要核對的行為 | 使用範圍 |
| --- | --- | --- |
| 短問答、商品清單與對話歷史 | 內容、選取範圍、格式和正常結束 | 有限中文指令與教過類型的新問法、組合 |
| Fashion-MNIST 灰階商品圖 | 商品類別；兩格場景的左右或上下關係 | 褲子、包、短靴三類；位置格由呼叫程式提供 |
| 12字「大小上下左右開關入出人口」組成的字卡 | 讀出指定區域，保留字序及要求的換行 | 一個已提供的連續1–4格區域；Sans、Serif兩種已學過的字型 |
| MInDS-14 中文真人錄音 | 用聲音內容決定客服短答，再沿用對話歷史 | 地址、App錯誤、卡片問題三種意圖；輸出文字回答 |
| 小整數計算要求 | 生成合法工具請求，讀取真結果，再生成答案 | 有界的計算器往返 |

例如，把兩格商品圖左右交換，回答也應交換；把「兩點」改成「一句」，內容仍應正確而格式改變。這樣才能區分「認出素材」「選對範圍」和「照要求回答」。上面的成功案例是可重做的示範，整體成功率仍要由各項獨立題目判定。

## 19.2 為什麼成品選 MoE，卻仍保留 Dense 路線？

助理讀到「App」或一個商品向量時，每一層都要用前饋網路（FFN）轉換當前特徵。Dense 每層使用一組前饋網路；本章 MoE 每層備有四組 expert，由 router 選出兩組，按權重合併它們的輸出。expert 是可訓練的前饋網路，不是事先寫好「專門看圖」或「專門聽聲音」的程式。

成品採 MoE，是把[第15章](15.md)的路由機制放進同一位多模態助理，觀察多組規則怎麼共同學習。Dense 則提供同寬、同層數、同注意力與感知入口的另一條完整訓練路線，讓我們有具體對象理解成本和行為的取捨。

下面建立與公開成品**相同結構的隨機模型**，只數參數，不訓練也不生成答案。`parameters` 數整個助理儲存的參數；`language_parameters` 只數文字核心；最後一項是每個位置共享的文字參數加上所選 expert 的結構計數。

```python
from tiny_perceptron.selftrained.model import LimitedAssistant, SelftrainedConfig

for architecture in ("moe", "dense"):
    config = SelftrainedConfig(
        vocab_size=550,
        width=256,
        layers=4,
        heads=4,
        kv_heads=2,
        ffn_hidden=512,
        experts=4,
        top_k=2,
        max_length=512,
        architecture=architecture,
    )
    model = LimitedAssistant(config)
    report = model.description()
    print(architecture, "全部", report["parameters"], "文字", report["language_parameters"])
    print("每位置的邏輯啟用文字參數", report["active_language_parameters_per_token"])
    print("嵌入與輸出共用同一張表", model.lm.embedding.weight is model.lm.output.weight)
```

兩次最後一行都會印出 `True`。這稱為 tied weights：輸入字元嵌入與輸出候選分數使用同一張權重表，數參數時只算一次。注意力、這張表及其他共同零件，也由各位 expert 共用。

| 相同結構的計數 | MoE：四組選兩組 | Dense：一組 |
| --- | ---: | ---: |
| 整個助理的參數 | 5,447,107 | 2,288,067 |
| 其中的文字核心參數 | 5,140,224 | 1,981,184 |
| 每位置的邏輯啟用文字參數 | 3,036,928 | 1,981,184 |
| 三個感知入口及接頭的參數合計 | 306,883 | 306,883 |

「邏輯啟用」用來說明只選部分 expert，沒有計入真正運算次數、分派花費或執行時記憶體。所有四組 expert 仍要存放；同一段輸入的不同位置也可能選不同組。本章 MoE 一個位置用兩組 FFN，Dense 用一組，所以這個配對不是同計算量或同記憶體的比較。

兩條路線的最終訓練目標與選定歷程也不同，不能把得分差直接歸因於 MoE。保留 Dense 的用途，是對照兩份真實成品並看清差異；要做隔離架構因素的實驗，還需要按[15.13](15.md#15.13)另行配對條件。上面的程式確認結構與計數，模型已學會什麼則由生成考題核對。

<details>
<summary>補充：550個編號從哪裡來？</summary>

本章沿用字元 tokenizer：普通文字逐字轉成編號，另外保留角色、模態和結束等控制編號，合計550個。普通字表只由訓練文字建立，並加入事先指定的ASCII格式字元與12個讀字字元；驗證和最後考卷沒有拿來擴充字表。推論時不在字表內的字會變成未知字元，不能把這份小字表當作完整中文詞彙。實作見[tokenizer.py](../../tiny_perceptron/selftrained/tokenizer.py)，公開配置與計數見[成品紀錄](../../docs/selftrained/results/v2-final-public-results.json)。

</details>

## 19.3 同一題的不同版本，怎麼避免跑進兩份考卷？

同一張包的原圖，可以縮放成單物件題，也可以和短靴配成左右關係題。如果原圖進了訓練，縮放版卻進最後考卷，模型就可能靠見過的素材答題。「家族」在這裡指同一來源或情境及它的衍生題；先決定家族去哪份資料，再製作不同問法與版本。

下圖用包的來源A示意：單物件、配對與交換位置的題目都留在訓練份。配對只能使用已分到同一份的兩個來源；圖中的短靴也來自訓練份，不能拿驗證份的短靴和訓練份的包組成訓練題。驗證和最後考卷使用各自另留的來源，而不是把A的不同版本隨機拆散。

![資料家族切分示意：來源A的單物件、配對與換位題一起留在訓練；來源B留給驗證、來源C留給最後考卷。](../figures/p6-19-start-splits.svg)

本章的固定資料分成以下三份。題數是對話記錄數：同一張圖或錄音可能產生多筆記錄，因此題數不是原始素材數。

| 資料份 | 對話記錄數 | 用途 |
| --- | ---: | --- |
| train：訓練 | 28,876 | 參與梯度與參數更新 |
| validation：驗證 | 2,435 | 檢查學習狀況、選定檢查點 |
| test：最後考卷 | 3,734 | 定版後核對成品，不再用來選權重 |

不同材料需要不同的家族規則；只要求每筆記錄的ID不同還不夠。

| 材料 | 一起留在同一份的內容 |
| --- | --- |
| 文字與對話 | 同一改述家族、客服情境樹，以及它的格式、範圍與歷史版本 |
| 計算工具 | 同一組數字及交換順序、不同運算、工具可用性與結果回填題；問法家族也隔離 |
| 商品圖 | 先按原始商品ID與原始像素去重切分；只在同一份內配對，再製作單物件、方向與換位題 |
| 字卡 | 2–4字組合按字串隔離；同一來源家族的區域問題及訓練增強版本留在同一份 |
| 錄音 | 同一來源錄音、重複或近重複語句群組，以及由它衍生的格式、續聊與增強題 |

字卡考的是已知字元的新組合與版面。12個單字本來就共同出現在學習及單字檢查中，不能稱為新字測試；V2訓練已包含 Sans 和 Serif，考卷中的 Serif 也不能稱為陌生字型。提供的讀字區域是一個連續1–4格框，模型學的是框內辨識，沒有另外學文字偵測。

錄音則有62份訓練、15份驗證和30份最後素材。這些數字數的是**錄音**；來源沒有說話者ID，不能換寫成62人、15人、30人，或宣稱最後考卷的人從未出現在訓練中。來源轉寫可供作者整理重複群組及檢查文字題洩漏，推論輸入仍只有實際聲音和公開對話，不附逐字稿、意圖標籤或當前標準答案。

資料隔離完成後，還要看答案分佈和成對題：例如只回答「包」能猜中多少商品題，同圖換位置是否真的改變答案。零家族交集排除了指定來源的跨份重複，不能單獨證明模型使用了材料。這些檢查會在感知和最終驗收時與模型回答一起看。

<details>
<summary>補充：怎樣把資料版本固定下來？</summary>

[V2 manifest](../../docs/selftrained/v2-manifest.json)列出12個記錄檔與全部素材的路徑、大小和完整SHA-256指紋。訓練 wrapper 啟動時會核對這些檔案；不同階段沿用同一份固定資料。V2的文字、工具、字卡與聲音增強只追加訓練素材，原有驗證和最後記錄及媒體保持原檔內容。

`group_id` 是記錄裡的家族標記，[資料讀取器](../../tiny_perceptron/selftrained/dataset.py)會拒絕同一標記跨份；商品來源像素、字串與錄音群組的隔離則由各自的資料準備程式另外檢查，不能只依賴一個標記。固定資料的取得與逐檔驗證見[訓練操作頁](../../docs/selftrained/TRAINING.md#安裝與固定資料)，來源與授權見[V2資料說明](../../docs/selftrained/V2-DATA-NOTICE.md)。

## 19.4 怎麼確認下一階段真的接著上一階段學？

文字助理接上商品入口時，應該是原來的核心多了一份材料。如果下一站重新建立隨機文字權重，檔名即使也叫 `model.pt`，仍不是接續同一成品。接續訓練因此要保存**檢查點**：除了當時的權重，還可以包含更新器、隨機抽樣與目前步數等狀態。

本章從隨機初始化出發，依下圖走到最終 MoE。每支箭頭載入自己上一段依驗證選出的 `best.pt`；不是另取成熟模型或別條路線的零件。Dense也有自己的完整前段鏈，最終停在weighted joint。

![成品訓練鏈示意：隨機權重依序經過pretrain、SFT、vision、OCR、audio、joint、weighted joint與MoE native joint；每次新段載入自己的前段best權重。](../figures/p6-19-start-lineage.svg)

三個感知階段先練入口本身的辨識；到joint才一起練「讀材料後回答」。骨幹是提取特徵的部分，head是給類別或字元打分的部分。joint凍結這些感知零件，也就是保留既有權重、不在這段更新它們；仍允許更新共同文字核心，以及把感知特徵交給核心的接頭。

| 新的一段 | 這段主要學什麼 | 允許更新的模組 |
| --- | --- | --- |
| pretrain | 用有限文字練下一個編號 | 文字核心 |
| SFT | 按示範產生助理回答及工具請求 | 文字核心 |
| vision | 從三類商品像素判斷類別 | 商品入口；文字核心凍結 |
| OCR | 從指定框辨識12字及字序 | 讀字入口；文字核心凍結 |
| audio | 從完整聲學時間序列辨識三種意圖 | 聲音入口；文字核心凍結 |
| joint | 混合文字、商品、讀字、聲音與工具題 | 文字核心與感知接頭；骨幹及辨識head凍結 |
| weighted joint | 加重工具示範和數字位置的訓練誤差 | 同joint；tool權重4、numeric權重4 |
| MoE native joint | 再加重未增強的語音問答與續聊示範 | 同joint；tool權重4、numeric權重1、native voice權重4 |

末兩段仍使用同一模型和資料，只改訓練誤差的比重。驗證維持原本未加這些權重的判準；訓練目標比較重視哪種題，不會直接變成答對證據。聲音head預測的是意圖，沒有把語音轉成逐字稿的ASR。

開始新段與接著中斷點做，是兩個不同動作：

| 要做的事 | 讀入檔案 | 權重以外的狀態 |
| --- | --- | --- |
| `--init-checkpoint`：開始下一段 | 自己前段的驗證選定 `best.pt` | 重建optimizer；依該段seed重新開始抽樣；新段步數、token計數歸零 |
| `--resume`：恢復同一段 | 自己同段的 `latest.pt` | 恢復optimizer、亂數狀態（RNG）、抽題狀態（sampler）和計數；保持原目標與求解設定 |

所以把tool4/numeric4改成tool4/numeric1/native4，要開新的native段；它不能冒充原weighted段的精確續跑。`--steps`在續跑時是那一段的總目標步數，也不是額外再做的步數。

選定檔案也不一定是最後檔案。本章MoE native完成了4,000步，發布的是驗證選中的第1,000步。下面只讀取隨專案保存的紀錄，CPU與Notebook都能離線執行，不需下載權重或重做訓練。

```python
import json
from pathlib import Path

repo = next(p for p in (Path.cwd(), *Path.cwd().parents) if (p / "docs/selftrained/v2-manifest.json").is_file())
```

## 19.5 讓助理簡短、誠實與守規則，要教哪種示範？

先告訴助理「接下來請用兩點回答」，再問「App錯誤訊息一直重複出現。」本章公開 MoE 權重在 CPU 上真正生成了：

> 1. 先檢查網路並重新啟動App。  
> 2. 仍失敗再詢問官方客服。

這個回答的內容對應當前 App 問題，也符合先前要求的兩點格式。公開的[輸入訊息](../../docs/selftrained/examples/v2/text.messages.json)只含一般工作設定、格式確認與問題；目前的答案是在呼叫模型後才產生的。這是挑選出的成功驗證例，可以核對介面與生成流程，不能由一題推出所有新問法都成功。

要教出這種行為，示範不能只有「問題 → 一句好答案」，還要讓**條件改變時，答案也改變**。本輪文字訓練資料包含下列實際示範；表中是作者提供的訓練答案，與上方模型生成的回答用途不同。

| 工作條件與使用者問題 | 訓練示範回答 | 要教的差別 |
| --- | --- | --- |
| 用一句回答；「App打不開，該怎麼辦？」 | 先檢查網路並重新啟動App，仍失敗再詢問官方客服。 | 回應已教過的需求，使用指定格式 |
| 「那個問題要怎麼處理？」 | 請說明是地址、App還是卡片的問題。 | 資訊不足時先問，不自行補一個問題 |
| 計算器不可用；「算0加0是多少。」 | 計算器目前不可用，請開啟後再計算。 | 依工具狀態回答，不假裝已執行 |
| 「請預測明天天氣。」 | 這超出我的範圍，我能協助有限聊天、地址、App、卡片或加減乘問題。 | 說明這個有限助手的工作範圍 |

這裡的「誠實」有具體教法：缺條件就詢問、工具未開就說未開、範圍外就說明範圍。也要保留能直接回答的題目，否則每題都求助也可能看似謹慎。學會幾種澄清句，不等於能估計任意問題的可靠程度；成品在留出題上是否選對行為，仍要另外評分。

**監督式微調（SFT）**就是用這種示範調整參數，讓模型在相同前文下較可能生成示範回答。system 訊息寫一般工作條件，user 訊息寫請求，assistant 訊息寫希望學到的回應。本輪 SFT 更新自己的文字核心；問題與歷史仍在輸入裡，但作答代價只計 assistant 的文字與結束標記 EOS。EOS 表示這輪回答結束，也需要學，不能只學會前幾個字。

下面在 CPU 上整理一筆手寫示範，查看哪些字被列為 SFT 目標。它使用成品相同的訊息編碼器，沒有下載權重、生成回答或更新模型。

```python
from tiny_perceptron.selftrained.dataset import RecordEncoder
from tiny_perceptron.selftrained.tokenizer import CharacterTokenizer

messages = [
    {"role": "user", "content": "那個問題要怎麼處理？"},
    {"role": "assistant", "content": "請說明是地址、App還是卡片的問題。"},
]
tok = CharacterTokenizer.build([m["content"] for m in messages])
row = {"id": "teaching-demo", "task": "text", "messages": messages}
encoded = RecordEncoder(tok, ".").encode(row)
targets = [value for value in encoded["labels"] if value != -100]
print(tok.decode(targets, skip_special_tokens=False))
```

輸出是 `請說明是地址、App還是卡片的問題。<eos>`。`-100` 表示該位置不計作答代價，並沒有把使用者問題從輸入刪掉。真正訓練時，模型讀到問題與已給定的回答前綴，逐字預測下一字；真正推論時則要接著自己剛生成的字繼續回答。能把標籤整理對，只證明訓練目標的安排，不證明模型已學會。

文字示範還包含選項記憶、格式改寫與工具請求／讀回。訓練、驗證與最後題依前面的資料家族分開；驗收時分別查內容、指定範圍、格式、完整結束及澄清行為。[19.12](19.md#19.12)會列出分項結果。下一節沿用這些回答規則，只把其中一輪的文字材料換成圖片或聲音。

<summary>查證：示範、實際生成與成熟方法</summary>

訓練示範保存在固定資料包的 `text-tools-train.jsonl`；讀取與標籤安排見[成品資料編碼器](../../tiny_perceptron/selftrained/dataset.py)，各階段更新範圍見[訓練程式](../../scripts/selftrained/train.py)。上方 App 回答來自[公開 CPU 執行紀錄](../../docs/selftrained/infrastructure/v2-public-cpu-smoke-actual-review.json)，可重做的完整命令見[CPU 操作頁](../../docs/selftrained/v2-public-cpu-commands.md)。

## 19.6 圖片與聲音怎麼交給同一位助理？

下圖用的是公開 CPU 命令真正讀取的商品圖。第一題問「圖片中的服飾是什麼？」，模型生成「這是短靴。」；第二題改問「左邊是什麼？」，模型生成「左邊是褲子。」先看物件，再看位置：第二張的包在右格，不能因為圖裡有包就答包。

![公開推論的真商品素材：單物件短靴，以及左褲子右包的兩格場景；下方標示實際 CPU 生成回答。](../figures/p6-19-modal-fashion.svg)

服飾入口只學 Fashion-MNIST 的**褲子、包、短靴三類**。本輪把來源灰階商品像素放進自製場景，另外提供兩個格位的公開座標：例如左半張與右半張。程式按座標取出兩格，再把各格的像素與位置送進自行訓練的圖片入口。座標回答「看哪裡」，沒有提供「那裡是褲子」這個類別答案；這也不是模型自行偵測任意照片中的物件。

圖片入口算出物件特徵，接頭把它們轉成文字核心能讀取的向量，放進對話序列中預留的兩個圖片位置。格位座標與格位順序也進入表示，因此交換左右後，核心有機會分辨物件搬到了哪裡。這接續[10.6](10.md#10.6)的寬度轉換與[11.14](11.md#11.14)的位置保留：只留下「有褲子、有包」的平均摘要，還不夠回答「左邊是什麼」。

讀字再增加一個明確條件：使用者提供要讀的框。下面是公開命令的真字卡，綠框的原圖座標為 `[18,50,90,86]`；框內寫「大小」，上方的字不在這次回答範圍內。

![公開 OCR 推論的真字卡，綠框標出使用者提供的下方區域；該次 CPU 模型生成「大小」。](../figures/p6-19-modal-ocr.svg)

程式先依座標裁切，等比例縮放框內像素並補白邊，再交給自行訓練的讀字入口。它保留從左到右的特徵位置，接成32個輸入向量，由同一文字核心生成字串。因此「讀對字」「保留字序」「只讀框內」是三件要分開核對的事；裁切本身不會認字。

這份成品的字表是 **「大小上下左右開關入出人口」12字**，每次使用者提供一個連續、包含1–4字格的區域。字卡用 Noto Sans CJK TC 與 Noto Serif CJK TC，**兩種字體都出現在訓練中**。最後題可以檢查留出的字串、素材與版面變化，不能稱作未見字體測試；它也沒有自動找文字位置的模型。[11.18](11.md#11.18)的「先指定框，再讀框內字」在這裡成了實際推論介面。

讀字入口的預備訓練使用**CTC**（Connectionist Temporal Classification，連結式時序分類），處理「影像有32個欄位，答案卻只有幾個字」的對齊問題。訓練只給整串標準文字，不要求人工逐欄標出哪裡屬於哪個字。這是入口的學習方法；接頭仍把特徵與整組字形分數交給共同語言核心，最後回答由核心生成。

<details>
<summary>讀字入口怎麼學整串文字？</summary>

先看五個欄位的人工預測：`大、大、〈空白〉、小、小`。合併相鄰重複後是 `大、〈空白〉、小`，再移除空白符號，得到 `大小`。空白符號表示此處不輸出字，不是判斷圖片像素為白色。若答案有重複字，`大、大、〈空白〉、大、大` 會得到 `大大`；先把所有空白刪掉，反而會把兩個字誤合成一個。

同一份「大小」可以對應多種欄位預測，CTC訓練會加總能合成標準字串的那些路徑機率，再提高這個總機率。獨立檢查入口時，本成品則每欄挑最高分，再依上述規則合成字串；這個簡單解碼不保證找出總機率最高的字串，也不代替共同語言核心的回答。

方法與解碼的區別見[Graves等人的原始CTC論文](https://www.cs.toronto.edu/~graves/icml_2006.pdf)第3節；本課實作見[入口訓練目標](../../tiny_perceptron/selftrained/dataset.py)與[讀字解碼](../../tiny_perceptron/selftrained/model.py)。

</details>

聲音則保留隨時間變化的材料。公開例子使用一段 MInDS-14 中文 App 問題錄音，對話中目前的 user 文字只有「請回答這段語音問題。」；音訊附在這一輪，沒有把逐字稿或意圖標籤塞進問題。下圖的波形與色塊是**流程示意**，不是這段錄音的實測圖。

![語音流程示意：按時間排列的聲音特徵經自行訓練入口及保留分數比例的接頭，交給共享文字核心；實際生成的第一輪回答保存後，加入使用者改寫要求再續聊。](../figures/p6-19-modal-voice.svg)

固定的 log-mel 計算先把完整錄音變成按時間排列的40頻帶特徵。自行訓練的語音入口再處理時間變化，整理成16個有順序的區間向量，交給同一文字核心。這份材料只涵蓋地址更新、App 問題、卡片問題三類銀行需求，回答是專案撰寫的一般短提示，不涉及實際帳戶操作。

三種入口還有共同安排：除了內容特徵，也保留各候選類別或字形的**整組分數比例**，用可調投影接進核心。這種接頭可稱為 soft bridge，意思是還保留多個候選的程度，沒有先挑最大分數的類別，再查表貼一句固定答案。最終文字仍由文字核心逐字生成；感知分類頭的最大分數預測與最後回答，要各自評分。這個公開語音例的回答正確，獨立分類頭卻沒有選對類別，兩件事不能混稱通過。

公開 CPU 續聊也真的沿用了模型自己的回答：

| 這輪收到什麼 | 這輪實際生成什麼 |
| --- | --- |
| 先前要求「用一句回答」＋同一段 App 問題音訊 | 先檢查網路並重新啟動App，仍失敗再詢問官方客服。 |
| 保留上述真實回答，再加入「請將剛才的答覆改成兩點。」 | 1. 先檢查網路並重新啟動App。<br>2. 仍失敗再詢問官方客服。 |

第一輪生成後，程式保存原訊息、音訊路徑與這次真正的 assistant 回答；下一輪只加入新的 user 要求。音訊留在原來那輪，不重新當成目前問題，也沒有用示範答案替換第一輪。保存歷史讓核心收得到前文，使用歷史的行為則需要訓練，這正是[12.16](12.md#12.16)的兩項合作。

本輪先分別訓練圖片、讀字與語音入口，再在共同訓練中固定感知的骨幹與分類頭，更新文字核心和接頭。所有神經零件都由本專案從零訓練；聲音這條路沒有載入預訓練 ASR，也沒有先聽寫成文字。它是有限語音需求的文字回答，不能稱為通用聽寫或語音輸出。是否能依新素材改答、能否保留文字格式與續聊主題，統一用[19.12](19.md#19.12)的留出題及成對控制核對。

<summary>素材來源、公開輸入與重做位置</summary>

## 19.7 計算器算對，為什麼助理還可能答錯？

請助理「用計算器算出26×16。」公開 MoE 權重在 CPU 上先生成了乘法請求，程式真正算出416，同一模型讀回結果後再生成「結果是416。」這題需要三個動作連續完成：提出正確請求、執行工具、根據返回結果作答。

![實際公開 CPU 工具例：同一模型第一次生成26乘16的 JSON，計算器真執行返回416，再由同一模型第二次生成「結果是416。」](../figures/p6-19-modal-tool.svg)

第一份輸出是 JSON：以固定欄位記錄工具名、運算與兩個整數，讓程式可以明確讀取。這個計算器只支援0–99非負整數的加、減、乘。system 訊息說明一般格式與範圍，模型依 system 的工具條件與學過的示範，從這題選出 `multiply`、`26`、`16`；程式沒有先從問題抽出正確算式，替模型補一份呼叫。選擇工具是學習條件與作答規則的結果，不能解讀成模型已能可靠估計自己的數學信心。

| 往返位置 | 這次留下的實際內容 |
| --- | --- |
| 第一次模型生成 | `{"tool":"calculator","operation":"multiply","a":26,"b":16}` |
| 程式執行後的返回值 | `{"tool":"calculator","ok":true,"result":416}` |
| 回填到歷史 | 一則 assistant 呼叫，接一則 tool 結果訊息 |
| 同一模型第二次生成 | `結果是416。` |

執行器先檢查欄位、運算種類和整數範圍，再進行乘法；它不把模型文字交給 Python 的 `eval`。合法也不一定正確：若模型把26抄成25，請求仍可能合法，工具也會正確計算25×16，整個任務卻已偏離原題。因此「可執行」與「參數符合問題」必須分開判定。

下面只在 CPU 上重做解析與執行。`raw` 是我們手工提供的字串，程式沒有呼叫神經模型。

```python
from tiny_perceptron.selftrained.tools import parse_tool_call, execute_tool_call

raw = '{"tool":"calculator","operation":"multiply","a":26,"b":16}'
call = parse_tool_call(raw)
print("合法請求", call.to_dict())
print("真執行結果", execute_tool_call(call))
```

第二行輸出字典中的 `result` 為416。它證明這份請求能被解析並真正執行，沒有證明模型會生成它，也還沒有第二次模型回答。上方公開紀錄則保存了兩次真正生成，兩次都正常產生 EOS；第二次的輸入包含第一次的原始請求與真 tool 訊息，所以416是模型讀回後生成的答案。

工具往返要同時查：是否需要工具、是否選對工具與參數、是否真正執行、是否根據結果回答並正常結束。工具未開或缺參數的題目，要學會說明條件或詢問。另可在測試回放中替換返回值，查回答是否跟著變；這檢查讀回依賴，正常成功率仍應使用真正計算器結果。

這個26×16是挑選出的已知驗證成功例。一題真往返證明流程能運作，不能證明未見算式與問法穩定；本成品的最後工具題未達驗收門檻，完整分母與失敗位置留在[19.12](19.md#19.12)。這也回答了本節的問題：計算器只保證按收到的參數計算，參數選擇與最後文字都仍由模型負責。

## 19.8 後訓練方法很多，成品需要全部依序跑嗎？

同一段 App 問題，回答內容合理，卻沒有照「兩點」排版，應先補什麼材料？如果訓練集中沒有這種前文，補上「同一問題、不同格式要求」的示範就有直接用途。若已能回答，但兩份正確答覆中有一份更清楚，才有比較偏好的材料。方法要對應現在缺少的學習訊號。

[7.17](07.md#7.17)把大模型的常見分工說清楚：預訓練從大量文字學下一字的規律，SFT 再用對話示範教「此刻輪到助理，該怎麼回答」。本輪小成品也分段，但預訓練材料是有限的文字資料，並不是已讀過整個網路。兩段沿自己的權重接續，改變的是資料用途與計分位置；SFT 不是把前段已學的參數全部清掉。

本輪實際完成的主線是：文字預訓練 → SFT → 圖片、讀字、語音入口訓練 → 共同訓練。後面的共同訓練調整了工具與語音題的代價比重，讓這些既有示範在更新中得到更多重視；它仍使用示範目標，不是 PPO 或 DPO。公開 MoE 依共同訓練的驗證代價選出檢查點；完成全部更新不表示最後一步一定最好。完整接續與選定步數見[訓練操作頁](../../docs/selftrained/TRAINING.md)，能力則由[19.12](19.md#19.12)的最後題確認。

接下來若要改善回答，可以按資料與目的選擇方法：

| 已有的材料與目的 | 適合考慮的做法 |
| --- | --- |
| 有清楚的問題、前文與理想回答，希望學會作答或新條件 | SFT：提高示範回答的機率 |
| 同一問題有兩份回答，知道哪份更合適，希望調整相對偏好 | DPO：直接用偏好對與固定參考模型更新 |
| 希望模型產生新回答，再用可信的評分與回饋更新 | 可考慮 PPO 等強化學習方法，並檢查評分是否真的代表任務成功 |

**RLHF**指利用人類回饋改善模型的一類流程，**PPO**是可用的策略更新方法，**DPO**則是直接使用偏好對的另一條路。它們不是「SFT → RLHF → PPO → DPO」四道必經工序。[13.17](13.md#13.17)已比較兩條偏好路線；這份公開成品沒有依序套用它們，也不因此缺少一個名義上的完成步驟。

選方法後，還要先寫出希望改善的現象。例如「答覆仍正確，但更符合兩點要求」，就比較同題、同內容、不同格式的回答；若一份連主題都答錯，不能把差別只叫作風格。更新後再檢查圖片、讀字、聲音、工具及原有文字能力，才知道新行為是否以舊能力退步為代價。更多更新、較低訓練代價或較晚存檔，都不能直接替代這項比較。

[第13章](13.md#13.1)的偏好小實驗可用來練習比較與更新機制；那些局部實驗不屬於這份公開多模態成品，也不應拿來補它的能力表。

[7.20的MTP](07.md#7.20)也是可選的訓練設計：在同一前文位置增加未來token的目標，希望共同特徵學到更多後續線索。本成品仍只用下一token的交叉熵，沒有MTP分支。這次整合要追蹤同一文字核心如何接問答、圖片、讀字、聲音與工具；多加未來目標並不直接解決某條入口或工具請求的問題。原論文的結果支持它值得考慮，卻沒有證明本課約5.45M的模型會改善，因此本配方保留清楚的單步目標。

若另做MTP版本，應從設計時決定分支、目標位置、邊界與訓練預算，再以驗證資料比較。它會成為另一份有自己架構和紀錄的模型，不能在既有權重外加隨機分支，就當作成品已學會預測更多token。

選好要交付的權重後，下一節才接到推論效率：運算包裝可以換得更快，但仍需確認輸入、歷史與生成答案的意義保持一致。

## 19.9 接上較快的做法，先檢查什麼？

助理每生成一個新字，都需要知道前文。若每次把整段對話重新算一遍，會重複處理已讀過的位置；KV cache 保存各層已算好的 Key、Value，讓下一步沿用它們。但省下重算以前，必須確認前文、位置與可讀範圍仍相同，否則兩條路可能已在回答不同問題。

本章實際交付的核心採用下列設定。這些做法各自改變一部分計算，不能合成一句「最佳化後品質與速度都更好」。

| 實際選用的做法 | 在這份核心中做什麼 |
| --- | --- |
| RoPE | 旋轉 Query、Key 的特徵，讓注意力使用位置資訊。 |
| RMSNorm | 按特徵的均方根調整尺度，再使用可學的縮放係數。 |
| GQA | 4 個 Query 頭共用 2 組 Key、Value，減少這部分的權重與快取。 |
| tied embeddings | 查字與產生下一字分數共用同一張權重表。 |
| SDPA | 用 PyTorch 的縮放點積注意力介面計算注意力。 |
| top-2 MoE | 每層有 4 個 expert，每個有效 token 選其中 2 個前饋網路。 |

前幾項的機制見[第14章](14.md)與[第16章](16.md)，MoE 的路由見[第15章](15.md)。**SDPA 是介面，FlashAttention 是可能的底層運算實作**；裝置、數值格式與形狀都會影響選擇。本成品的設定記錄支持「使用 SDPA」，沒有支持「已選到 FlashAttention 核心」。同樣，Python 逐 expert 分派不等於專用稀疏運算核心。實際設定可查[最終模型記錄](../../docs/selftrained/results/v2-final-public-results.json)，運算路徑可查[模型程式](../../tiny_perceptron/selftrained/model.py)。

先用同一套實作的**局部微型示範**核對快取：模型縮成寬16、1層，仍用隨機權重；5個人工 ID 只是機制輸入，不是一道已學會的問答。一路一次讀完，另一路先讀3格、再接2格，比較最後位置的32項候選分數。

```python
import torch
from tiny_perceptron.selftrained.model import LimitedAssistant, SelftrainedConfig

torch.manual_seed(42)
config = SelftrainedConfig(vocab_size=32, width=16, layers=1, heads=2, kv_heads=1, ffn_hidden=32, top_k=2)
core = LimitedAssistant(config).eval()
ids = torch.tensor([[1, 11, 12, 13, 14]])
split = 3
with torch.no_grad():
    full = core(ids)["logits"][:, -1]
    cache = core(ids[:, :split])["cache"]
    cached = core(ids[:, split:], cache=cache)["logits"][:, -1]
print("最大分數差", (full - cached).abs().max().item())
print("同一計算", torch.allclose(full, cached, atol=1e-4, rtol=1e-4))
```

第二行應是True：程式以絕對與相對容差各 `1e-4` 比較，支持本例的兩路計算接近。第一行的最大差可隨浮點運算環境略變。兩路都使用 `eval()` 評估模式；本例模型沒有會隨訓練／評估模式改變計算的層，因此切換模式不改變本例輸出。`no_grad()` 則讓這次計算不建立求梯度的運算圖。程式沒有更新權重，也沒有量速度。

公開成品的生成預設已使用 KV cache。圖片與聲音在首次計算時編成特徵，放進完整前文；後續生成沿用快取，不重新編碼素材。另一項常見做法是[sequence packing](16.md#16.5)：把短紀錄裝到同一序列，再用遮罩隔開。這份正式訓練仍是一筆紀錄佔一列，較短列補 PAD，沒有採用 packing；前章的局部示範不能當成它已套用的證據。

[16.14的推測解碼](16.md#16.14)則先提出草稿，再由目標模型核對。本成品仍逐token生成，沒有這条草稿驗證路徑；是否採用MTP訓練與是否啟用推測解碼，應各自記錄。增加候選、測得分數接近，都不能替代真正的接受規則與速度量測。

練習只把 `split=3` 改成2，先預測兩路仍讀相同5個位置，最後分數應接近，再執行核對。若要宣稱某條路更快，下一步才是在同一硬體、同一權重與生成條件下量時間和記憶體；快取的一致性與模型的回答品質要分開評估。

## 19.10 如何把成品帶到較小的電腦？

先問電腦要放下哪些數字。MoE 每個 token 只使用部分 expert，下一個 token 卻可能選另一組，因此本實作仍把所有 expert 的權重載入記憶體。少用一部分計算，並沒有把其他權重從 RAM 移走。

這份 MoE 共有 **5,447,107 個參數，約5.447M**；Dense 共有 **2,288,067 個，約2.288M**，兩者都包括文字、影像、OCR與語音元件。M在此表示一百萬個數字。公開版以 FP32 計算，每個參數4 bytes；先估數值本身的儲存：

```python
for name, count in [("MoE", 5_447_107), ("Dense", 2_288_067)]:
    weight_bytes = count * 4
    print(name, "FP32權重bytes", weight_bytes, "約MiB", round(weight_bytes / 1024**2, 2))
```

結果約為 MoE 20.78 MiB、Dense 8.73 MiB，MiB以1024² bytes計。這只計每個可學參數一次；公開檔保存張量的安排與格式資訊也占空間，實際檔案大小要另核對。載入時也會有暫存副本，執行另需模態特徵、KV cache與工作空間。它不是整個程式的 RAM 峰值，更不能直接當成電腦最低需求。

若資源仍不足，可以沿用[第17章的量化](17.md)或[第18章的蒸餾](18.md)思路。量化以較少位元近似保存同一結構的權重；蒸餾先選較小學生，再向教師的文字或分布學習。這兩章已教過機制，但**本輪 V2 公開交付的是原浮點模型，沒有完成並驗收這份最終成品的全量量化版或蒸餾版**。

選部署版本時，應把三個問題並排：檔案多大、載入與生成占多少資源、同一任務的答案保留多少。Dense 的參數較少，最終能力也有自己的結果，見[19.12](19.md#19.12)；不能把它改稱 MoE 的蒸餾學生。兩條路線的訓練目標與歷程不同，這份比較也不能單獨證明架構造成某項差異。

練習另算「每個數字2 bytes」的理想數值儲存，預測兩個合計都減半。這一步只改算術；要採用實際低精度或量化版本，仍須轉換、存檔、重載，並重新核對任務與資源。

## 19.11 下載一份權重，就能從中斷處繼續訓練嗎？

直接回答與接續訓練，需要不同的包裹。回答要有完整神經權重、模型結構、字表和預處理規則；回到中斷的那一步，還需要 optimizer 的更新紀錄、隨機狀態、取樣位置與訓練進度。只拿到回答器的權重，不能還原這些狀態。

本章有4份公開推論輸出，固定在[Hugging Face 這一版](https://huggingface.co/birdhackor/tiny-perceptron-course-models/tree/979cdfacc588ad0536f1c64fff96f264571cf054/selftrained/v2)：模型庫為 `birdhackor/tiny-perceptron-course-models`，revision 為 `979cdfacc588ad0536f1c64fff96f264571cf054`。revision固定一份不可變的發布版本，讓後來的下載仍指向同一批檔案。

| 版本名稱 | 模型庫內的目錄 | 用途 |
| --- | --- | --- |
| `moe-pretrain` | `selftrained/v2/moe-pretrain` | 觀察文字預訓練階段的推論權重。 |
| `moe-sft` | `selftrained/v2/moe-sft` | 觀察加入對話示範後的推論權重。 |
| `moe-joint` | `selftrained/v2/moe-joint` | 本章選定的有限多模態 MoE 成品。 |
| `dense-joint` | `selftrained/v2/dense-joint` | 從自己的隨機起點訓練的 Dense 對照成品。 |

每份都包含4個檔案：`model.safetensors`保存完整神經權重，`model-config.json`描述結構，`tokenizer.json`保存字元與ID對應，`inference-manifest.json`記錄來源、預處理版本與檔案內容指紋。下載程式核對指紋，載入器再核對結構與所有權重；公開檔案不含 optimizer checkpoint。前兩份是階段比較用的權重，不具有 joint 版的完整訓練歷程與能力。

JSON中的 `generations` 保留實際生成，`model`標示選定權重。相同下載可重用；若目的地已有不同內容，程式會拒絕覆寫，請改用新的 `--model-dir`。文字示例不讀圖音資產；想試圖片、OCR、錄音與真正後續對話，按[完整CPU操作頁](../../docs/selftrained/v2-public-cpu-commands.md)先取得固定素材，再執行對應命令。該頁的7組情境用來檢查安裝與介面，都是已知的驗證示例，不是未知問題的成功率。

</details>

自己從零訓練則使用[本機訓練指引](../../docs/selftrained/TRAINING.md)的 stage wrapper。`--init-checkpoint`接自己前段已完成、驗證選出的 `best.pt`，開啟新階段與新 optimizer；`--resume`接自己同階段的 `latest.pt`，恢復 optimizer、隨機與取樣狀態，繼續到原本的總步數。wrapper只接自己建立、可信任的工作檔，核對保存的資料、設定與執行記錄，而且每次 attempt 用新目錄保存輸出。這條路已支援本機執行，不依賴作者的私人訓練儲存空間。

練習判斷兩個需求：「前一階段完成後，開啟下一階段」應選自己的 `best.pt`與 `--init-checkpoint`；「聯合訓練中斷後接回原進度」應選自己的 `latest.pt`與 `--resume`。公開 safetensors 只供推論與評測，目前 trainer 沒有把它當成訓練起點的載入器，所以不能將上方下載路徑直接代入這兩項。

## 19.12 完成整合後，怎樣回答「這個模型會什麼」？

回到最初的問題：同一個自行訓練的核心，能否讀文字、接圖片與錄音、使用工具，再保留對話要求？答案要按任務說明。模型先由[驗證資料選定](../../docs/selftrained/results/v2-final-training-source-selection.json)，固定推論權重與評分規則後，MoE與Dense各完成一次3734題的最後測試；這份最後考卷沒有再拿來訓練或挑版本。

下表集中列出主要能力。分母是**被評分的問題數**，不是互相獨立的原圖、錄音或人數。文字與客服題依固定關鍵詞及內容規則檢查語意；OCR、服飾與位置題檢查要求的答案；「真正往返」還要通過表中整條鏈。

| 有限文字與指令 | 回應範圍內問題，依歷史保留條件與必要內容。 | 464／560 | 429／560 |
| 指定區域OCR | 讀出所給文字框內的完整字串。 | 252／324 | 281／324 |
| 三類服飾 | 回答指定商品的類別。 | 357／360 | 356／360 |
| 兩格位置關係 | 回答左／右／上／下指定格位的商品類別。 | 1427／1440 | 1426／1440 |
| 語音客服回答 | 從錄音回答地址、App或卡片問題。 | 42／90 | 37／90 |
| 真正語音後續對話 | 第一輪回答正確，再用模型自己生成的歷史完成下一輪要求。 | 26／60 | 24／60 |

最後兩列回答不同問題。已提供返回值的題目省去了「模型自己提出正確請求」，所以高分能支持讀回結果，不能替真正往返補分。語音後續對話也沒有貼入標準第一輪答案；第一輪答錯，即使下一輪把錯話改成兩點格式，整條鏈仍算錯。

再回收[19.3](19.md#19.3)的答案分佈檢查：360道單物件服飾題中，褲子、包、短靴各120題。完全不看圖、固定答「這是包。」只能對120／360，也就是三分之一；這是按標準答案分佈算出的基線，不是另跑一次模型。上表的357／360與356／360超過這個固定猜法，接著還要看保持問題、改變材料或歷史時，答案是否跟著改對。

分開看入口與回答，還會發現一個有教學用的反例：兩版OCR入口的 CTC 讀字都完整辨對324／324，但共同語言核心生成的最終字串只有上表的252／324與281／324。[19.6的CTC入口](19.md#19.6)另有逐欄預測合成字串的獨立檢查：這裡的324／324是那個字串與標準答案完整相同的題數。入口辨對，不保證後面的回答器會忠實保留字序、範圍與完整內容。因此評測要追到使用者真正收到的答案，不能只用中間辨識分數代表整個助理。

本表的能力範圍也由材料決定。OCR只含12個字，使用者提供一個連續1–4格的文字框；Sans與Serif兩種字體都在訓練中出現，不是自動找文字或陌生字體測試。圖片限三類服飾與已提供的兩格位置。語音來自同一來源內的有限客服意圖：最後保留的是30份錄音，衍生出不同歷史與要求，並非30位新說話者；來源沒有 speaker ID，沒有驗收說話者隔離的泛化。新問法與未見組合的結果支持上述具體範圍，不能換成一般中文、任意照片或任意真人語音的宣稱。

原本的判準沒有因結果不理想而調低。例如文字要逐意圖達80%，OCR整串要達80%，工具真正往返要達95%；高分任務不能抵銷另一項未達標。兩版的真正工具往返都低於95%，因此**兩版都沒有通過全部能力驗收**。訓練、公開下載與最後評測完成，讓我們能查清成品；它們和能力通過是不同的結論。[完整結果](../../docs/selftrained/results/v2-final-public-results.json)、[MoE原始彙總](../../docs/selftrained/results/public-raw/moe/test/metrics.json)、[Dense原始彙總](../../docs/selftrained/results/public-raw/dense/test/metrics.json)與[檔案索引](../../docs/selftrained/results/public-raw/index.json)保留可回查的分項；[MoE判準明細](../../docs/selftrained/results/v2-moe-public-final-test-stage-index.json)與[Dense判準明細](../../docs/selftrained/results/v2-dense-public-final-test-stage-index.json)列出未達項目。

練習用人工分數看平均的差別：若一類12題全部答對，另一類6題全部答錯，按題合計與每類等權重會得到不同摘要。

```python
by_question = (12 + 0) / (12 + 6)
by_task = (1.0 + 0.0) / 2
print("按題合計", by_question, "每類等權重", by_task)
```

前者是三分之二，後者是一半；這些是假設分數，不是本模型成績。把同一種題多出幾份，會改變按題合計的比重，卻不會自動增加能力。因此交付時先列各項判準與分母，再選摘要，而不是讓總分遮住重要失敗。

這個有限成品讓我們走完從隨機權重、分階段學習到同一核心實際回答的MoE路線，並知道能力在哪裡中斷。接著在[19.13](19.md#19.13)對照三個成品的用途，再從[19.14](19.md#19.14)讀共同切分，完成Looped解題器、機率判斷器與Auto的路線。三成品走完後，[第20章](20.md)換一個起點：接手成熟 Qwen 圖文權重，由 Whisper 處理語音轉寫，再研究應用與驗收。它是成熟模型的延伸，不是本章 MoE 的接續訓練，也不替這份成品補上能力分數。

## 19.13 三個成品，分別拿來做什麼？

同一個小型客服工作台，可能同時需要三種工作：看商品或聽需求、追蹤多次修改後的狀態，以及判斷資料是否足夠。與其把所有輸出都叫「聊天」，這次讓三個成品各有清楚的輸入與驗收方式。

**A 是既有 MoE v2 有限多模態助理**。19.1–19.12會展示它的文字、圖片、字卡、客服語音與工具路線；權重與歷史固定成績沿用原版本，也保留尚未通過全部原定判準的結論。它的舊 Dense 對照仍是對照，不另算第四個主要成品。

**B 是 Looped Dense 有限文字解題器**。這次先讀明確語法的事件，例如「起始狀態2；設成5；設成1」，回答最後狀態1；也處理有限小整數算術。共享區塊可跑不同輪數，最後讀出一個答案類別。從隨機權重學起，獨立載入與使用；它不是把 MoE 的輸出換個介面，也不宣稱一般聊天能力。

**C 是 Jev 式機率判斷服務**。輸入狀態、問題與候選含義，回傳機率，可做服務選擇、資訊充分判斷及有限規準評級。它有自己的權重與推論入口；就算不接B，也能單獨拿來判斷客服材料。它的訓練與第9章契約一致，不冒充未公開的商業 Jev 配方。

| 成品 | 一個最小輸入 | 要檢查的輸出 |
| --- | --- | --- |
| A | 商品圖＋「右邊是什麼？」 | 依其有限類別與位置範圍生成回答 |
| B | 起始2，依序設成5、1 | 最後狀態類別1；實際輪數 |
| C | 「查卡片，沒給申請編號」＋「資訊充分嗎？」 | yes／no機率、選中類別與集中度 |

三個神經模型都用本專案訓練的權重，但任務與輸出形式不一樣。三個成品各有自己的推論入口，使用者依任務選擇；只有B的已驗輪數能映射為本輪的 effort 檔位，A沒有因此得到原生 effort 能力。後面的 Auto 是C與B合作的服務流程，不是第四個神經模型。

B與C已從隨機權重完成訓練，19.15–19.18使用實際留出題結果，19.20保留通過與失敗項目。閱讀不必自己重訓三個模型；短Notebook教機制，19.19另提供固定權重的下載與使用方式。

練習：要問「有沒有足夠資訊查詢」應選哪個成品？C；若已知有限語法事件、只要最後數值，則由B處理。若輸入是任意照片，不能因A接受圖片就假定它辨識所有物件。

## 19.14 同一個世界，怎樣避免三份資料互相洩題？

假設一筆事件是「起始2，後來設成5，再設成1」。B用它學最後狀態；C可能用它學「這是追蹤任務」；Auto又用它記不同輪數能否答對。如果各自隨機切資料，同一事件便可能在B的訓練、C的測試中同時出現，最後的整合分數不再代表新情境。

因此先給**事件家族**一個固定識別碼，再共同決定切分。家族包含同一底層事件的措辭改寫、不同問題及候選重排；從家族衍生的B、C與路由紀錄，全部繼承相同split。題目ID標一筆具體輸入，家族ID標它和哪些題有共同來源，兩者角色不同。

下例只示範穩定分配，不訓練模型。正式v2的比例與題數另存資料manifest；相同家族不管衍生幾筆都不換組。

```python
import hashlib


def split_of(family_id):
    bucket = int(hashlib.sha256(family_id.encode()).hexdigest()[:8], 16) % 10
    return "train" if bucket < 7 else "validation" if bucket < 9 else "test"


for variant in ["原句", "改問資訊是否充分", "候選倒序"]:
    print(variant, split_of("state:start2:set5:set1"))
```

三行應相同。這能防同家族跨組，卻不自動證明測到新推理能力：如果所有問題仍套同一句型，模型可能只熟悉語法。報告還會分開列未見事件組合、實體／措辭變化及更長事件序列；每種測試說明哪些關係見過、哪些沒有。有限語法任務可先驗收有限能力，不能改名成一般中文理解。

validation 也有不同用途。calibration 部分選機率溫度，policy 部分選輪數與門檻；最後 test 封存，到設定凍結後才評分。若已看過某批test的錯題並修訓練，那批只能作開發診斷，新的最後評估另留資料。不能不斷查同一考卷，仍稱一次最後測試。

正式v2共產生B的47,673列、C的420,110列，包含訓練、兩種開發切分及各變化測試。核心最後測試B是2998題（2956追蹤、42算術）；C是33,577題（Choice11,797、資訊充分10,890、規準10,890），來自554個世界家族。不同問題、缺欄情況與候選集合會從同一世界衍生多列，不能把列數當成同樣多個獨立世界。

實際查重還發現一個重要差別：B沒有跨組相同輸入；C則有5453種跨split相同的通用觀測，影響215,427列。例如許多不同來源世界刪掉欄位後，都會只剩同一個任務句型。這些重複觀測沒有衝突標籤，卻表示「世界家族沒跨組」不等於「模型從未看過這段文字」。因此C的高分只支持固定任務與句型，不能宣稱對全新語義或一般中文的泛化。

每個版本保存生成器、seed、世界規則、家族與題目ID、欄位說明、檔案指紋及切分統計，見[資料manifest](https://github.com/birdhackor/tiny-perceptron-vlm/blob/main/docs/lesson-products/data-v2-manifest.json)及[token與觀測稽核](https://github.com/birdhackor/tiny-perceptron-vlm/blob/main/docs/lesson-products/data-v2-token-audit.json)。合成資料不等於免查洩漏；同義重排、對稱算式或相同事件的等價編碼，也要先定義如何合併家族。

練習：`2+3`與`3+2`要不要同組？若本次希望測未見加數組合，就應用排序後的加數建立共同家族。這是測試目標決定的契約，不能等看到成績才改。

## 19.15 Looped 解題器怎樣成為獨立成品？

讀入有限事件、輸出正確答案，是B的主要工作。為了先把共享深度的效果看清楚，第一版採明確文字語法。狀態追蹤沿用[14.15](14.md#14.15)的兩盒世界：A與B各有0–7的初始值，事件依序把某盒設為指定值，或把兩盒的值交換，最後查詢其中一盒。例「A=2；B=6；事件=交換；查詢=B」的正解是2；再交換一次，B便回到6。因此重複交換要按順序處理，不能只記出現過哪些數字。

三數加法則給三個0–6整數，預測總和，例如「x=1；y=2；z=3」的正解是6。兩類題都把預測整數與正解完全相同算答對；答案集合有限，所以最後輸出各答案類別的分數，不要求先學逐字生成長說明。

tokenizer 把語法與數字轉成編號，入口把它們變成向量。共享的 Transformer 區塊讀原輸入及目前狀態，反覆更新；最後讀出位置經答案頭輸出。輸入順序仍然重要：「先設成5，再設成1」的答案是1，倒過來是5；位置資訊與改順序測試能幫我們檢查模型是否只數過哪些數字。

本版B有170,003個參數，從seed7421的隨機權重開始，在NVIDIA L4完成1000次更新，policy選中的也是第1000步。產品配方把同一題的1–5輪答案CE取平均，讓每個部署深度都收到直接監督；問題的正解沒有隨輪數改變，模型需要學的是在不同計算預算下接近同一正解。

第14章另做固定3輪與抽1／3／5輪的末端監督對照，資料、初始化與實際更新次數配對。那是檢查未直接監督終止深度的機制實驗，不混用這份產品B。完整optimizer、隨機狀態與成對checkpoint另存，且本次L4實際核對了恢復後下一步一致；只下載推論權重不包含這些續訓狀態。

交付不是只有權重檔。設定要足以重建網路；tokenizer要讓同一文字得到同一編號；推論命令要能選輪數、在CPU載入、回傳答案及實際執行設定；manifest把這些檔綁到固定版本。訓練入口另保存資料、最佳化器、隨機狀態及選權重依據，讀者才分得清繼續訓練與只作推論。

預先訂定的核心門檻是五輪狀態追蹤至少90%。凍結後的最後測試得到2928/2956，約99.05%，通過核心門檻；算術只有2/42，約4.76%，未達85%的次要目標。不能因核心通過，就把B稱成可靠的三數加法器。

平均數也會藏住子群：重複交換只有32/42；換盒子名稱後1486/2956；把事件長度拉到5–6時1245/3200。這版通過的是原A/B命名、原句型與1–4次事件的有限考卷，仍有上述子群失敗；長事件與改名只作壓力測試。這些結果均保留在[正式報告](https://github.com/birdhackor/tiny-perceptron-vlm/blob/main/docs/lesson-products/results/final-report-v1.json)。

本版low／medium／high事前固定為1／3／5輪，代表允許的工作設定，不是三個品質保證。即使1–5輪都直接受監督，一輪追蹤仍只有1598/2956，約54.06%；四輪2930/2956還略高於五輪2928/2956。這使我們能直接看見：多深度訓練促進各輪答題，但不保證每個檔位都達90%，也不保證越多輪越好。[19.18](19.md#19.18)會把相同考卷的品質與成本一起列出。

練習：把固定示範的最後一次覆寫刪掉，答案應如何變？先用世界規則求真值，再看模型輸出。這種控制關鍵事件的小變化，比只挑一個漂亮成功例更能查出是否使用材料。

## 19.16 判斷器怎樣獨立回答三種問題？

C的工作不是代替B算完再包成JSON。它從狀態、當前問題與候選意義直接產生機率，讓另一個程式可以決定顯示服務、詢問資訊或分配預算。最小世界沿用卡片、地址與App客服材料；每種工作先有可人工核對的規則。

第一種是 **Choice**：「需要哪類服務？」候選含卡片、地址、App及不適用。第二種是 **yes／no**：「對當前流程，必要資訊齊了嗎？」輸出yes機率。第三種是**有限規準評級**：例如0＝必要欄位都缺、1＝只滿足部分、2＝已全滿足，回傳各級機率。規準須按每題流程列出必要欄位，不能只看文字長短。

一個共享候選評分器可服務三者：讀狀態與問題，再把每個候選意義送進同一網路得到分數。yes／no有兩個互斥候選；等級候選則把每級意義寫清楚。這是本課可實作的條件評分設計，不是宣稱官方 Jev 內部也使用同一網路。新問題、新詞義或任意級數都不自動受支援，應列明訓練與測試範圍。

本版C有84,545個參數，從seed9041的隨機權重在L4完成800次更新，policy選中第800步。三種問題各自在calibration組用CE選溫度，本次都選0.25。交付同時綁定權重、語義ID、規準與這三個溫度；換候選順序不應偷偷換候選意義。

核心最後測試Choice為11,797/11,797、資訊充分10,890/10,890、規準10,890/10,890；倒序候選後語義選擇一致11,797/11,797。缺少所需服務候選時，以none為答案的子集是849/849。這些是[19.14](19.md#19.14)已交代觀測重複的有限考卷；倒序一致也部分來自每個候選獨立評分及語義ID平手規則，不單獨證明模型懂任務。

Choice集中度仍只量候選間集中程度，不能當作正確機率。Noul式介面直接回yes機率即可；服務決策及輪數選擇留給外層策略，與權重檔分開版本化。

驗收先要求最後留出Choice正確率至少90%，並在同題重排候選後有至少99%的語義選擇一致率。後者單獨高也可能只是穩定選錯，因此必須同時看前者。資訊充分與有限等級各報正確率、CE及Brier；另外測正解候選缺席、同狀態換問題、無關欄位及新措辭，保存高信心錯誤例。

校準的條件同樣要保留：核心Choice的CE從約0.000550降到0.00000814；換措辭後，正確率卻只剩11,493/11,797，CE更從0.183惡化到0.698。資訊充分與規準在換措辭後也各為10,773/10,890。原分布選出的溫度，可能讓新措辭上的錯誤更有信心。

例如輸入「幫我預報明天天氣」，本世界的正解是不適用（none）；模型卻選兩盒追蹤（boxes），集中度約1。這個[保存的錯誤例](https://github.com/birdhackor/tiny-perceptron-vlm/blob/main/docs/lesson-products/results/observed-failure-examples-v1.json)直接說明：集中、高分與語義判斷正確是不同的事。核心考卷零錯誤，也沒有排除分布變化時的高信心錯誤。

若同一問題集合只有一個正確候選，評分與標籤就按該契約；若有多個同樣合理答案，須修改規準或評分方式，不能靠模型猜標註者喜好。這使成品的機率有可討論的對象，而不是只把自由文字壓成固定欄位。

練習：兩份材料都有編號，但一份是查規則、一份是執行查詢。是否充分的標籤要查當前流程要求，不能用「有編號就yes」通吃。把同狀態換問題列進測試，才能抓到這種捷徑。

## 19.17 Auto 怎樣選檔，手動又怎樣優先？

現在把C接到B：先判斷題目是否屬於支援任務、必要資訊是否完整，再選B要跑的輪數。這是一個服務的 **Auto effort**；B仍負責解題，C提供可觀察的判斷，策略設定把判斷變成預算。三者不必被混成同一種模型能力。

接B時，C也要學會辨認B的材料。同一個「需要哪類服務？」問題，候選擴為卡片、地址、App、狀態追蹤、算術及不適用；相關題目也要進入訓練與驗證，依[19.14](19.md#19.14)繼承共同家族切分。不能只在使用時臨時加入候選，就當作C已理解新含義。

資訊充分也按這個有限入口的欄位契約判斷：追蹤題要求兩盒初值、事件序列與問哪一盒，算術要求三個運算元。例如「A=2，B=6；交換兩盒數值；問B」材料齊全；刪掉A的初值後，B的最後值便無法確定，C應判資訊不足，先詢問再交給解題器。標籤依世界規則準備，不先讓B猜答案再反推是否充分。客服、追蹤與算術的充分性各按自己的流程要求，不能拿「有沒有申請編號」通用於所有題目。

使用者可傳 `auto/low/medium/high`。指定固定檔時，服務用已凍結的對應設定；auto時才採策略選檔。無論選哪一種，都先檢查支援範圍與硬上限。若某個檔超出使用者上限，要依介面約定回報受限或拒絕，不能悄悄加算；也不能選了low卻偷偷跑high，再把結果算成low。

第一版使用容易查清楚的**規則Auto**。C先各作一次Choice及資訊充分判斷，以當前候選中分數最高者決定，不另加機率門檻；不支援便回unsupported，資訊不足回clarification_needed。資料齊且任務合適，才按凍結規則交給B。

本次在policy組搜尋45組事件長度界線及算術輪數，目標是在完整題目平均B輪數不超過3下，使整個流程答對率最高。選出的low界線是0、medium界線是4、算術用1輪；因此核心1–4次事件的追蹤全部用3輪，並未替這批題找到更細的分檔。5–6次事件會選5輪，但仍屬壓力測試，沒有因此變可靠。

設定凍結後，Auto在2998個完整題中答對2926題；固定medium是2927題。Auto只把42道算術各少算2輪，共少84輪，也少對1題。這是這份考卷的實際品質／工作量取捨，沒有證明Auto優於固定medium。

策略目標也要先明定，例如「在平均解題輪數不超過3的限制內，讓答對率最高」。判斷器的計算不能被免費略過；報告另外量它的時間，總時間包含C與B。若題目很簡單，C的開銷可能比直接跑B的low還大；若C錯估難度，Auto也可能輸給固定medium。

更進一步可學各預算的成功率或加算收益，但需要**新標籤**。先凍結B、tokenizer、提示、解碼與預算定義，再在路由訓練題跑各檔、記成敗；不能把Choice的集中度直接當成B會答對的機率。單次0／1只是一筆結果，要估隨機解碼的成功率還得重複。

進階路由訓練後還要重驗C原本的選項與校準能力；B一改，舊路由標籤也可能失效。因此這一版先交付規則Auto，學習式Auto另列後續里程碑。第一版是開始前選輪數，不聲稱中途可無成本改檔或續算；重新從low跑high時，兩次成本都要記。

練習：題目少了必要起始狀態，選high能解決嗎？更多計算不能補出未提供的事實；先澄清，再把新材料交給解題器，才符合這個流程。

## 19.18 三個成品要如何比較才有意義？

A能處理有限圖片與聲音，B只處理明確文字語法，C回機率判斷。如果把各自最拿手的考卷分數排成一欄，就沒有回答共同問題。比較前先問用途：是選一個合適成品、檢查Auto取捨，還是研究循環架構的因果效果？

選成品時，表格先列輸入、支援輸出、能力範圍、權重記憶體與使用成本；A用其固定歷史報告，B、C用新凍結報告，日期與資料不同須保留。這是用途導覽，不能讀成架構勝負。共同客服場景能讓讀者理解如何合作，也不能抹平任務差異。

Auto的比較則有共同考卷：同一凍結B、相同解題題目與解碼，依次測固定low、medium、high及規則Auto。每題保留答案、輪數、C的判斷、時間及是否受硬上限限制。medium必須在表裡，因為中間檔可能才是最好固定選擇。平均成本相同時比較正確率，或達同樣品質時比較成本，才知道選擇器是否值得。

回看真解、替每題挑最便宜正確檔的oracle，只是**這份固定執行紀錄的離線上界**。全部檔都錯的題仍算錯；若還要找出最佳檔，搜尋成本也不是免費。它可以提示Auto還有改善空間，不能和實際可用策略混列成部署成果。

研究loop本身，需要新訓練的匹配Dense控制：資料、起點規則、工作量及選權重方式盡量對齊，說明控制的是參數還是計算。舊A的訓練歷史不同，不能拿它來隔離共享區塊的效果。第14章的機制配方與第19章產品配方也分表呈現。

本次完整流程用同一份2998題（2956追蹤＋42算術）比較，C的拒絕也留在分母；實際C在這份完整題都接受。每列都先作兩次C判斷，再由B解題。

| 模式 | 答對／2998 | 正確率 | 平均B輪數 | CPU流程平均毫秒 |
| --- | --- | --- | --- | --- |
| low | 1598 | 53.30% | 1 | 3.63 |
| medium | 2927 | 97.63% | 3 | 4.32 |
| high | 2930 | 97.73% | 5 | 4.99 |
| Auto | 2926 | 97.60% | 2.972 | 4.37 |

品質與平均輪數用全部2998題；時間另依固定ID抽24題，每題重複3次，共72次／模式，先各暖機3次。環境是CPU、float32、2執行緒、batch1，模型已載入；計時從入口第一次結構檢查之後開始，包含兩次C及B，不含HTTP、載入及先前的檢查。這是函式內等待，不能冒充所有裝置的完整服務延遲。

C兩次平均約2.9毫秒；直接呼叫B的medium約1.30毫秒。Auto雖少用約0.93%的B輪數，本次流程平均時間並未比medium低。少量時間差會受系統波動影響，報告保留原始次數與範圍，不把它當可靠尾端延遲保證。記憶體仍要分權重與執行峰值；輪數不是秒數替代品。

練習：Auto少用一輪，卻多跑一個判斷器，總時間可能更長嗎？可能。把控制器時間加回來，再看符合實際限制的品質／成本表；別只報對方案有利的代理量。

## 19.19 下載到權重，怎樣確認自己用對版本？

同名模型經過再次訓練，答案與Auto門檻都可能改變。因此一份可使用的成品，要把**權重、網路設定、tokenizer及策略**對到同一個固定版本。下載網址只是一個入口，檔案指紋才協助我們確認拿到的是哪份內容。

新產品用兩層清單配對版本：release.json固定HF的commit、產品目錄及manifest指紋；各產品的artifact manifest再列推論檔案的大小與SHA-256。推論時先核對，再建立網路、載入權重、切成評估模式；評估模式關閉某些訓練行為，但沒有把隨機解碼自動變成確定性。解碼設定、輪數及裝置仍須一起記。首次下載成功與真正離線載入推論，是兩項不同檢查。

三個產品各有獨立推論入口：A沿用[19.11](19.md#19.11)的既有公開CPU操作；B接受有限文字與輪數；C接受狀態、問題與候選。Auto入口同時載入B、C與凍結策略，並接受effort設定。使用預訓練完成的**本課權重**作推論，不代表你正在訓練，也不代表借用了外部成熟神經模型。

若要自己重訓，先用小設定確定資料與程式能運作，再選CPU、Apple裝置的GPU運算後端MPS（Metal Performance Shaders），或NVIDIA GPU。完整作者訓練可用GPU，學生不必在筆電重跑全部正式實驗。訓練配方另記seed、更新步數、資料版本、checkpoint選擇與硬體；可續訓checkpoint還要有最佳化器與隨機狀態，不能只用推論權重假裝無縫續訓。

程式碼與生成器保存在Git；大量資料、checkpoint與推論權重放既有資料／模型儲存入口。公開檔案應有來源與授權，不能把私人token或帶憑證下載連結寫入教材。下載與上傳驗證會保留可公開的檔案hash及結果，避免把環境祕密當操作教學。

沿用[W.1](../first-steps.md#W.1)的CPU環境，在專案根目錄啟用`.venv`後執行；`download`第一次連線取得B／C，後面的命令使用本機檔案：

```bash
python -m tiny_perceptron.lesson_products download --product b
python -m tiny_perceptron.lesson_products download --product c
python -m tiny_perceptron.lesson_products solve --state '兩盒追蹤;A=2;B=6;事件=交換;查詢=B' --loops 3
python -m tiny_perceptron.lesson_products judge --state '卡片進度;申請編號=?' --question info
python -m tiny_perceptron.lesson_products auto --state '兩盒追蹤;A=2;B=6;事件=交換;查詢=B' --effort auto
```

例中的交換把A原來的2移到B，所以正確答案是2；卡片進度缺申請編號，資訊充分性的正確類別是`no`。這些短輸入讓你看懂介面，模型在其他有限輸入上仍可能答錯。B輸出答案與實際輪數，C輸出候選機率與集中度；Auto另記實際使用的兩次C和B輪數。在Auto入口指定`--effort medium`要求3輪，`--max-loops 2`則會截到2並標`budget_limited`。

[產品操作](https://github.com/birdhackor/tiny-perceptron-vlm/blob/main/docs/lesson-products/README.md)列出固定HF版本、候選ID、三種問題、本機JSON服務及重訓命令。可用`serve --port 8765`啟動同一推論函式的本機HTTP入口；它接受有限語法，不是一般聊天服務。完整訓練使用自己的新輸出目錄；只下載推論`model.pt`無法恢復原最佳化器與隨機狀態。

練習：只換了B權重，仍用舊Auto設定，為什麼需要重驗？選擇器原本根據舊B各檔表現制定，換權重後成功與成本關係可能改變。版本鎖定保護的是整個決策流程，不只是能否讀檔。

## 19.20 什麼證據才足以把候選版叫成品？

一次示範成功，證明那個輸入在那個設定下能答對；訓練loss降低，證明模型更貼近受監督材料。要交付成品，還需要它在預先指定的新題上達到最小用途，且別人能用同一版本重做推論。

本輪在2026-10-16完成驗收。模型、資料SHA、溫度與Auto規則先提交到[測試前commit](https://github.com/birdhackor/tiny-perceptron-vlm/commit/821a2c717f05ad7b57e08e88cd965e92ff0c1200)，再首次啟動最後考卷；評分後沒有用這份考卷改權重或選設定。兩位獨立工程審核者另從保存的原始分數重算B／機制／Auto與C結果。

| 事前要求 | 實際最後結果 | 判定 |
| --- | --- | --- |
| B五輪追蹤至少90% | 2928/2956，99.05% | 核心通過 |
| B算術次要目標85% | 2/42，4.76% | 未達 |
| C Choice至少90% | 11,797/11,797，100% | 核心通過 |
| C重排一致至少99% | 11,797/11,797，100% | 核心通過 |

B、C通過其預定核心門檻，算術失敗沒有被移除或降門檻。資訊充分、規準、校準、事件子群與分布變化分開報告；例如B重複交換只有32/42，整體99.05%不能代替這個子群。C的世界家族切分仍包含已披露的相同通用觀測，100%不能改名成對一般中文或Jev所有問題的理解。

A的固定報告已指出未達全部原定能力判準；新增B、C不會改寫這個歷史結論。若新產品沒有達核心門檻，就標為候選或實驗，檢查錯誤、在授權預算內改善，不能因為三份檔案已上傳便宣布三成品完成。若資料規則或測試範圍要改，另開版本、說明理由，不在看完答案後悄悄降低門檻。

最後報告應接起四段證據：資料怎樣產生與隔離，模型怎樣訓練及選權重，凍結後如何評估，下載者能否實際使用。同時保存失敗例與限制，例如長度超界、錯誤但自信、改問句後失準，讓讀者知道何時應澄清或換工具。正式數字不以人工表格或手工狀態更新代替。

最後測試的結果仍受樣本與訓練seed影響。剛好跨過門檻，不代表每一種實體、長度或問法都可靠；報告須列實際樣本數、分任務結果與適用範圍。若在不同seed重訓，另外保存版本，不用最好一次覆蓋原始失敗。GPU正式訓練與CPU短練習各有目的，後者不代表完整訓練只能使用CPU。

閱讀這份教材時，可以先跑短小機制Notebook，再按[19.19](19.md#19.19)下載固定版本測自己的有限輸入。完整[最後報告](https://github.com/birdhackor/tiny-perceptron-vlm/blob/main/docs/lesson-products/results/final-report-v1.json)包含1–6輪曲線、分任務與子群、校準前後、變化測試及Auto成本；公開配套另附可重算成績的逐題原始分數。想研究架構才重做匹配實驗；想改服務才重做資料、校準與政策。三條路都從清楚的問題開始，沿著版本與證據判斷結果。

練習在新報告到位後找一個失敗例：先按世界規則寫出正解，再檢查是哪一層出錯——資訊不足、候選規準、模型判斷、預算選擇，還是執行版本。只有找到層次，修正才對得到問題。
